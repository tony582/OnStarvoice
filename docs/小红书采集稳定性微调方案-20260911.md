# 小红书采集稳定性微调方案

日期：2026-09-11  
状态：待实施方案  
适用范围：StarVoice 小红书搜索、关键词详情增强、无人值守恢复、相关状态与诊断。

## 1. 目标与实施顺序

围绕现有采集链路做两批修正。第一批解决正常关键词被反复打断的问题；第二批让等待、失败和后台繁忙的原因能够准确显示、定位。

| 批次 | 改动 | 完成后的行为 |
| --- | --- | --- |
| 第一批 · P0 | 识别搜索仍可见、详情已不可用的帖子 | 该帖子单独结算，其他帖子继续采集 |
| 第一批 · P0 | 打通帖子结果、关键词结算和换设备恢复 | 成功与不可用结果被保留，只恢复真正未完成的部分 |
| 第一批 · P0 | 适配小红书不同搜索页和时间筛选 | 自动搜索遵循当前账号实际可用的页面；确认筛选生效后才采集 |
| 第二批 · P1 | 准确展示自动恢复的等待原因 | 明确谁可接、谁不能接、现在卡在哪一步 |
| 第二批 · P1 | 修正报错分级和诊断导出 | 能直接看到最新任务失败的阶段和原因 |
| 第二批 · P1 | 数据库繁忙提示和负载诊断 | 区分请求排队、连接异常和慢查询，并减少重复请求 |

数据库并发参数是否调整，依据负载证据单独决定。若执行时再次出现影响多个功能的数据库繁忙，应先处理服务恢复，再继续采集验证。

核心验收例子：一个关键词有 20 条待处理帖子，其中 1 条在搜索里仍可见、详情已不可用，最后应显示“19 条采集完成，1 条不可用”，并结束本轮关键词处理。不能因为这 1 条不可用，让所有设备轮流重跑整个词。此数字仅为验收示例。

## 2. 依据与结论边界

本方案依据 9 月 10 日会话中的截图、诊断和现场检查，以及 9 月 11 日对 0.4.8 源码的复核。运行状态均为当时快照，不代表设备此刻的状态。

源码基线：`d1925abfc0baf335392d4e9a16c0999c258abcd6`，扩展版本 0.4.8。

| 问题 | 已有证据 | 需要保留的判断边界 |
| --- | --- | --- |
| 成都接任务很快失败 | 安吉星的一次执行约 26 秒结束，错误为 `XHS_SEARCH_TIME_FILTER_UNVERIFIED`；现场筛选调用返回 `panel_not_opened`，页面筛选数据未初始化 | 这次失败指向搜索筛选；不能由此前数据库报错推定它也是数据库问题 |
| 自动搜索与手动搜索页面不同 | 出现普通搜索页和 `/search_result_ai`；自动流程主要通过拼接地址跳转，且保留当前搜索路由及参数 | 已观察到不同页面形态；尚未证明所有新搜索页都失效，也未证明地址跳转是唯一原因。另一张截图中新页面已显示“已筛选” |
| 帖子仍能搜到，详情不能打开 | “Vo83——你会不会为车联网买单”在搜索结果中可见，打开后出现“该内容暂时无法查看”，侧栏仍按详情采集失败重试 | 可确认当时详情不可用；该提示本身不足以断定作者永久删除 |
| 不可用识别存在缺口 | 0.4.8 识别器对上述短提示及“首页文字＋短提示”均返回空；现有关键词详情增强路径未完整接入目标不可用结算 | 已有识别器可复用，需要补场景和调用链，不能只加一条页面文案匹配 |
| 安吉星反复恢复 | 9 月 10 日 22:52–22:53 快照中，7 次尝试为 6 次“采集增强未完整完成”、1 次筛选未验证 | 不能据此断定 6 次增强失败全部由同一帖子造成；应补帖子级记录才能逐次核对 |
| 有空闲设备却显示等待 | 当时 8 台设备池中，7 台已在本轮尝试过；唯一未尝试的“木星”忙于另一任务。规则限制本轮重复领取 | 原因涉及该工作项的领取资格，不等于所有设备都忙。“7/16”也不是完成进度 |
| 扩展错误页很多条警告 | 包括互动数提取、视频元素缺失、状态上报超时及已结束执行的清理提示 | 警告不都等于任务失败；应按任务、时间和阶段关联 |
| “数据库容量暂时不可用” | 代码确有数据库请求分类并发门限，默认进程预算 10，关键／普通／报表分别 4／4／2；排队超时或队列满会返回容量错误 | 表示请求处理名额暂时不足，不是数据库磁盘容量耗尽；是否需要扩容必须另看负载 |

## 3. 第一批：修复采集和结算

### 3.1 帖子不可用：识别、留痕、继续

复用现有目标页面识别器，把关键词增强、普通单篇采集和定向采集使用的不可用结果统一起来。

识别覆盖打开详情后的弹层、短暂提示、错误页及返回首页的过程。证据必须关联本次请求的帖子 ID、目标地址和时间，不能把正文中引用的“删除”等词，或其他标签页的提示当成目标状态。

| 实际情况 | 记录与展示 | 本轮处理 | 后续处理 |
| --- | --- | --- | --- |
| 平台对目标明确提示已删除 | 已删除；保留平台提示及时间 | 单独结算，停止自动增强 | 后续搜索仍保留匹配关系，免重复增强；可人工复查，成功后恢复 |
| 目标显示“该内容暂时无法查看”等明确不可用提示，但无永久删除证据 | 当前不可用；详情未获取 | 单独结算，本轮不在其他设备上反复打开 | 下一次计划运行最多复查一次；若恢复可访问，正常增强 |
| 要求登录、验证码或安全验证 | 账号／访问受限 | 按现有安全与人工处理规则执行 | 不写成全局删帖，也不通过换设备规避验证 |
| 网络超时、页面尚未完成加载、采集脚本异常 | 技术失败，保留具体原因 | 只对该帖做有限重试 | 用完预算后保留未完成状态与错误 |

同一次父任务内，以“客户＋平台＋帖子 ID”去重不可用处理，跨关键词和跨设备继承结果。账号受限结果另带账号范围，不能扩散为所有账号都不可访问。

暂时不可用的去重只影响本轮任务；明确删除可持久保留状态和证据。两者均保留原有正文、搜索摘要、历史采集和客户标注，不删除业务记录。恢复访问后，更新可用性并保留变化记录。

二维码本身不作为帖子不可用的证据。先识别登录、验证码及安全验证；只有与目标关联的明确不可用提示，才进入“当前不可用”结算。修正现有将部分“暂时不可浏览＋扫码查看”布局直接归为“已删除”的映射。

**用户可见结果：** 当前卡片的“采集增强失败，自动重试 2 次”改为对应的“当前不可用，本轮已跳过”或“平台提示已删除”；保留一次人工复查入口。搜索列表仍能命中该帖子，不应因此漏掉其他帖子或整个关键词。

### 3.2 按帖子结算，只恢复未完成部分

现有代码已经有按失败帖子收集重试 ID、有限自动补试及上报队列。此次补通这些结果在关键词汇总和服务器恢复链路中的传递，不新增一套独立重试系统。

每条帖子保留独立结果：采集完成、业务规则跳过、详情不可用、技术失败待恢复、技术失败已用完重试。可用性和采集完整度分别记录，不能把不可用计入“成功获取详情”。

关键词结算规则：

1. 搜索与筛选已确认完成，全部帖子结果为采集完成、业务规则跳过或详情不可用，且无待人工处理问题：结束本轮正常处理；不可用数量单列。
2. 仅剩技术失败：只重试或交接这些帖子；成功和不可用的帖子不重置。
3. 搜索尚未完成：恢复搜索进度，并继承已经处理的帖子结果，避免重复增强。
4. 存在必须人工处理的问题：显示待处理状态与原因。技术重试耗尽：结束自动恢复，形成“部分完成／失败”终态，保留失败帖子及原因，不继续排队，也不计作全部成功。
5. 所有帖子均不可用：显示“本轮检查完成，N 条不可用，0 条详情采集成功”；与“筛选后没有结果”区别展示。

持久化优先复用现有检查点与结果结构，最少包含目标 ID、结果类别、证据时间、剩余待处理 ID 和尝试标识。换设备后从已确认结果继续；新一轮计划不误用旧的“暂时不可用”去重。

现有单设备帖子补试次数先保持。跨设备交接必须继承实际消耗，不能让“换设备”自动刷新同一帖子的预算；不可用业务结果不再触发下一次技术恢复。真实故障仍保留既有恢复上限。

终态同步复用现有上报队列，确认服务器已持久化后再显示同步完成；重发必须幂等，旧执行的迟到回报不能覆盖新执行的结果或让已结束任务重新运行。

### 3.3 搜索与时间筛选适配

以“同一浏览器、同一账号、同一关键词、同一时间范围”的手动操作为对照，分别验证普通搜索页和新搜索页。目标是入口、筛选语义及结果刷新一致，不要求不同账号的结果数量或排序完全相同。

改动点：

- 统一侧栏与后台重复的搜索地址／入口处理，识别实际进入的页面类型。
- 优先沿用站内搜索的完整初始化流程；直接地址跳转仅用于已验证支持的页面，避免继承无关旧参数或筛选状态。
- 为已观察到的不同搜索页面分别处理筛选入口、面板加载和时间选项，不强制把新路由改回旧路由。
- 在页面加载、筛选面板可用后操作；对初始化慢的情况做有限等待与重新进入。明确不支持的页面展示兼容性问题，避免误报成“没有结果”。
- 继续要求“时间条件已选中＋搜索结果已刷新”的证据。筛选无法验证时，不采集时间范围不明的结果。
- 保留具体失败原因，如“筛选面板未出现”“时间选项未选中”“结果刷新未确认”，不在上报时统一丢成一个泛化错误。

成都的快失败需用相同账号和页面路径复验。只有自动搜索、筛选、采集、服务器入库全部完成，才能判定修复；单独看到筛选按钮或页面打开不足以验收。

## 4. 第二批：恢复说明、诊断和数据库繁忙

### 4.1 恢复状态说明

保留既有设备池、两轮恢复上限和安全限制，先修正信息展示。服务器根据实际领取条件返回等待原因，前端不通过“总空闲数”自行推断。

应区分：等待符合条件的设备空闲、本轮其他空闲设备已经尝试、等待冷却、没有在线且兼容的设备、上次执行尚未关闭、已经下发等待领取、设备正在处理、已用完自动恢复。

“恢复 7/16”显示为“已尝试 7 次，上限 16 次”。原设备与下一接收设备分开展示；尚未领取时不显示成已分配。仅在有确定计时时显示下一次评估时间，不把它承诺为开始执行时间。

针对当时快照，合理的说明是：“本轮已有 7 台设备尝试；剩余可接设备木星正在执行其他任务，等待它空闲。”该文字须随实时领取资格变化。

若第一批完成后，仍存在长期等待某个忙碌或离线设备导致无法进入下一轮的情况，再单独验证是否需要“等待上限后重新评估轮次”的策略。此次不以提高 16 次上限或无条件放开重复领取来解决单帖失败。

### 4.2 错误分级与诊断导出

| 当前表现 | 微调要求 |
| --- | --- |
| 收藏数／评论数没提取到，日志警告且可能回填为 0 | 区分“确实为 0”与“未获取”；未获取时保留历史值或未知状态，避免覆盖正确数据。可选字段缺失不直接拖垮整个关键词 |
| 视频元素未找到 | 结合已有媒体备用提取的最终结果定级；正文、帖子身份和所需媒体仍未取得时保留真实失败 |
| “无人值守状态上报超时” | 区分侧栏到扩展后台的确认超时、后台排队、服务器请求超时及保存失败。超时不等于服务器一定失败 |
| `Stopping stale unattended attempt: terminal` | 正常结束后的清理降为信息；涉及旧执行覆盖、状态冲突时才告警 |
| 导出中的错误与最新失败对不上 | 从最新执行及关键词检查点补出首个阻断原因，并显示后续连带错误；历史告警按任务归属分开 |

诊断最少提供：设备、扩展版本、任务／尝试 ID、关键词、失败阶段、错误代码、具体原因、实际页面类型、筛选证据摘要、失败帖子 ID、上报耗时、下一步处理方式。链接中的访问令牌和账号敏感信息脱敏，不导出整页内容代替必要证据。

先沿用现有上报队列与重发能力，核对确认点及排队耗时；不通过一味加长 10 秒超时掩盖阻塞。迟到确认和重复提交分别验证，避免误判后重跑造成更多压力。

### 4.3 数据库请求容量

保留数据库分类请求门限。当前已有各类并发数、队列数快照，应接入诊断，并补齐等待耗时、拒绝原因、连接池占用及具体请求阶段。

先做三项修正：

1. 按实际原因替换“数据库容量暂时不可用”：`queue_timeout` 显示“服务繁忙，请求排队超时”，`queue_full` 显示“服务繁忙，请求暂未受理”。连接异常与查询超时分别显示对应原因；只有请求确实正在重试时才显示“正在重试”。内部保留请求类别和原因代码。
2. 对重复的列表刷新、状态查询合并请求并在繁忙时退避，避免多个页面和设备同步重复请求。
3. 写入失败使用已有可靠上报链路恢复；不能先显示已同步再丢弃失败。核对慢查询是否确实占住处理名额。

若观测确认普通请求长期满额而其他预留长期闲置，再评估分类预算、等待时间及空闲名额借用。调整必须维持关键任务上报与终态保存的能力，并通过负载验证；此方案不预设扩大数据库连接数。

## 5. 验收用例

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| A1 | 普通搜索页与新搜索页，手动／自动执行相同筛选 | 页面已初始化，时间条件和刷新均有证据；不采集范围不明的结果 |
| A2 | 面板延迟出现、选项未选中、刷新未确认 | 分别给出具体原因，有限恢复；失败不显示为 0 条正常完成 |
| A3 | 筛选后确实没有结果 | 验证筛选和空结果状态后，按 0 条正常结束 |
| A4 | 搜索保留目标，详情短暂提示不可用后回首页 | 捕获与目标关联的证据，记录当前不可用，继续其他帖子 |
| A5 | 明确删除、暂时不可用、登录验证、网络故障 | 四类结果不混淆；正文引用错误文案不会误触发；账号限制不扩散到其他账号 |
| A6 | 20 条中 19 条成功、1 条不可用；同帖在其他关键词再次出现 | 19 条成功＋1 条不可用；本轮同帖不重复增强，关键词匹配关系仍保留 |
| A7 | 全部候选不可用 | 本轮检查结束，成功详情为 0、不可用为实际数量；不伪装成无搜索结果 |
| A8 | 一个帖子技术失败后恢复；或恢复预算耗尽 | 只处理未完成帖子，成功不重采；预算耗尽仍如实显示未完成 |
| A9 | 执行中断后换设备接续 | 已确认结果和已用重试预算继承，未完成部分继续；迟到旧回报不能覆盖结果 |
| A10 | 下一次计划复查暂时不可用帖子，覆盖恢复和仍不可用两种结果 | 恢复访问则正常采集并保留历史；仍不可用且跨关键词或换设备时，本轮累计最多复查一次，保留匹配关系，不触发重复增强或技术恢复 |
| A11 | 8 台设备中 7 台本轮已尝试、1 台忙碌 | 等待原因、可领取设备和实际命令一致；领取后状态随之更新 |
| A12 | 上报确认超过原等待时间，之后成功；重复上报 | 既有结果不丢失、不重复写入、不因确认迟到重跑整个关键词 |
| A13 | 互动数据缺失、媒体使用备用提取、执行正常清理 | 未知值不覆盖已知值；可选缺失与真实失败分级正确 |
| A14 | 导出最近一次成都筛选失败或帖子增强失败 | 导出直接包含对应任务、阶段和具体原因，无需翻旧警告猜测 |
| A15 | 普通查询拥塞并伴随采集结果上报 | 能看到请求类别及排队原因；关键上报和终态保存得到验证，重试无丢失和重复 |

先补与上述边界相关的回归用例，再做真实浏览器验证。涉及任务恢复和结算的修改，应同时核对父任务、关键词工作项、尝试、命令与持久化结果；不能仅以父任务“完成”作为通过依据。

## 6. 实施与交付

1. 从已核对的 0.4.8 发布基线建立隔离分支，复用既有模块与测试；实施前再确认目标环境版本是否已变化。
2. 第一批同时交付不可用识别、帖子结果传递、关键词结算与搜索适配；扩展和服务器涉及的字段保持版本兼容。旧扩展无法提供证据时，不根据一条泛化错误直接批量改写历史状态。

第一批完成的判定是：正常搜索可执行；不可用帖子不再导致整词循环；真实技术失败仍能恢复并留下可核对的结果。第二批完成的判定是：用户能从页面或一次诊断导出看清当前阻断点。
