# 评论"采全"调研:抖音 vs 小红书

> 分支 `feat/comment-completeness`。结论:**两个平台是同一个道理**,缺口一样,只是 DOM 选择器不同。

## 一、现状(代码实锤)

| | 小红书 | 抖音 |
|---|---|---|
| 采集入口 | `utils/capture/comments.js`(通用) | `utils/capture/douyin-comments.js`(专用) |
| 顶层评论 | `autoScrollLoad` 滚动加载,stall/最大次数停 | 同 |
| 子评论(回复) | **不展开**(`comments.js:659`「不主动展开回复层级」) | **不展开**(`douyin-comments.js:3749` 把「展开回复/收起」当噪声跳过) |
| 加载上限 | `maxDetectedItems`(评论加载上限) | 同 |

**两边都只采"自动加载出来的顶层评论",刻意跳过折叠的回复。** 所以"采不全"在两个平台表现一致。

## 二、两块缺口

1. **子评论(回复)没采** —— 最大头。
   - 抖音实测:一条 69「评论」的帖,滚到底顶层 = 49 条,差的 ~20 条是回复,藏在 **6 个「展开N条回复」**触发器里(`div.YJKsQai6`)。抖音的「评论数」是**含回复**的。
   - 小红书同理:回复藏在「展开 N 条回复 / 查看 N 条回复」里。
2. **顶层评论滚动可能停早** —— 次要。
   - `autoScrollLoad` 在 stall(连续无新增)/ 最大滚动次数 / 最大时长 时停。大评论区若 stall 阈值偏紧,可能没滚到底(曾见 57 条只采到 28)。

## 三、取全方案

### A. 子评论展开(两平台都要做,DOM 不同)
在顶层评论滚动过程中:
1. 识别每条评论下的「展开/查看 N 条回复」触发器
   - 抖音:`div.YJKsQai6` 等,文本 `^展开\d+条回复`;
   - 小红书:文本 `展开 N 条回复 / 查看 N 条回复`(选择器待实测)。
2. 逐个**点击展开** → 等回复渲染 → 采集(作为该评论的子评论 / 或平铺为评论)。
3. 处理二级「展开更多回复 / 查看更多回复」,循环到「收起」出现 / 无更多。
4. 去重(回复可能与已采项重叠)。

> ⚠️ **代价**:每条有回复的评论都要点开+等加载,**采集会明显变慢**(一条帖几十次点击)。建议做成**可选项**或**限流**(如:只展开"含负面顶层评论"下的回复、或每条最多展开 M 层),避免大帖卡死。

### B. 顶层滚动放宽(两平台通用,低风险)
调 `autoScrollLoad` 的 stall 判定(`REQUIRED_STALL_ROUNDS` / `FORCE_STOP_STALL_ROUNDS` / 最大滚动次数),让大评论区更彻底地滚到底。低风险、先做。

## 四、建议优先级

1. **先做 B(滚动放宽)**:低风险,确保顶层评论尽量采全(解决"57 采到 28"这类)。
2. **再做 A(回复展开)**:做成「采集增强」里的一个**可选开关**(默认关,大帖才开),并限流。先在抖音真实采集页**实测点击与回复渲染的 DOM**(新标签页复现不准,需对真实流程调),再推广到小红书。

## 五、待实测(实现时)
- 抖音「展开N条回复」点击后回复渲染成什么节点(是否仍是 `[data-e2e="comment-item"]`、还是子容器)。
- 小红书回复触发器的精确选择器与渲染结构。
- 两平台「展开更多回复」的二级触发与「收起」收尾。
