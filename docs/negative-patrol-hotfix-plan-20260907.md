## A. 服务器保护与逐帖派发

### A1. 修复重查询

1. 改写 captureTaskBusinessRootVisibilitySql 的 canonical.id::text 关联，使合法 UUID 比较可用主键索引；使用安全表达式处理非法/空值，不能依赖 WHERE 条件书写顺序保护强转。保持同租户、逻辑/物理轮次、NULL、origin_agent_id 与 parent_task_id 去重语义。对原 SQL 与新 SQL 做相同数据集的结果等价测试。
2. 对已证明受 JIT 拖累的 overview 查询，在同一事务/连接内 SET LOCAL jit=off 和执行超时；事务结束释放设置。不能在连接 A 设置、连接 B 查询，也不能只用 JavaScript 超时把 SQL 留在数据库运行。
3. overview 返回只负责展示。过期命令处理使用已有 reconcilePendingCaptureCommands 的有界维护入口，明确注册启动/周期执行；领取时保留当前命令有效性复核。确认离线 Agent 的旧命令仍可收敛之后，才移除 overview 每次先维护的事务。
4. DispatchPage 改为上一请求完成后再安排下一次；隐藏页暂停、失败退避、手动刷新合并在途请求。服务端相同租户、同等授权与同参数请求合并，缓存只供展示，带更新时间，不用于权限和派发判断。
5. 预览/overview 都按执行计划只补必要索引，先限制返回范围再读展示详情；不为“加速”删除业务去重或直接全量返回。

### A2. 数据库容量与控制通道

采用总连接预算不增加的分组执行器方案，避免只给 overview 加限制却仍被其他非关键任务占满：

- reporting：overview、预览、列表聚合等重读；
- general：创建/新领取、非关键维护、评论/AI 后处理；
- critical：认证、基础心跳与状态回执、已采集结果的短事务持久化、stop/cancel 的写入/交付/确认。

在 db/pool.js 与 db/query.js 增加统一分类执行器，路由/后台工作在入口标记类别，事务固定使用同一个 client；未分类工作进入 general，不自动挤入 critical。首选分组池，各池上限之和不超过当前总预算；多进程按总实例数分摊，不能每个实例各拿整机额度。现有业务表、租户隔离和事务原子性不变。

停止/取消与基础心跳先使用受保护短事务完成；新领取使用另一短事务，限流或领取失败只返回“暂不分配新工作”，不能回滚已完成的状态上报或阻断 stop。critical 中的回传只落可靠数据和回执，不执行评论分类或 AI。

所有类别都有有界等待与真正的 SQL/锁超时。应用已超时但数据库可能提交的写操作进入“结果未知”，依原幂等身份恢复；事务失败先回滚，坏连接不得继续放回池。超额看板返回受控繁忙与退避时间，不能无限等连接。

### A3. 选定服务器逐帖交付（R1、R2、R3）

复用现有父任务、capture_task_items、attempt 和单帖 child/command 结构。现有弹性领取已经会生成 targets 只有一帖的 v1 命令，沿用此协议，不给浏览器新增每帖校验请求。

- 所有新负面巡查先批量写父任务和待执行 items；每次首次交付只包含一帖。
- 固定模式在 item.metadata 保存 pinnedAgentId，只有指定 Agent 可领；它离线则等候，不自动转交。多节点固定模式先确定各帖绑定。不要把会随 attempt 改动的 assigned_agent_id 当永久绑定。
- 弹性模式按候选 Agent 范围领取。人工重分配必须显式修改绑定并留审计，仍经过同一准入。
- 同时控制整机和租户的活跃帖子执行数、单位时间首次准入数；重试和人工继续也计入。命令重送用同一身份，不重复扣额。
- 在命令实际首次交付处复核准入，不能只限制任务创建。需要新执行的 create/resume 都走此边界；stop/cancel 豁免新执行额度。
- 同一短事务中按统一顺序非阻塞取得整机预算、租户预算、Agent 槽、parent/item；锁冲突立即退出，不持连接排队。然后原子写准入、item/attempt、child/command。实现时检查所有参与路径的锁顺序并做并发回归。
- 给 capture_agent_commands 增加 admitted_at、admission_released_at 及必要的未释放/近期准入索引。并发占用按不同 execution task 归并，速率按首次执行准入计数；同一执行的重复命令不制造双份活跃占用。额度在可靠终态或停止对账后释放，不能只因 expires_at 到期视为空闲。
- 准入时间代表服务器许可时间，不宣称网络延迟下客户端实际启动间隔绝对相同；活跃占用上限约束可能迟到的执行，验收仍记录真实帖子开始时间。
- 整机过载时 items 留队，提示 server_busy 与下次检查时间，不算采集失败、不耗重试次数。恢复后渐进放量；停止后不得再交付该范围的 create/resume。

### A4. 存量大包和滚动升级

旧大包已经进入浏览器后，服务器无法靠停止新命令限制包内帖子，必须在正式切换时收口：

| 存量状态 | 处理 |
|---|---|
| pending，且确认无交付/执行证据 | 与命令交付互斥，撤销旧包；把尚未执行项迁入逐帖队列，保留父任务、原请求键和历史映射 |
| acknowledged、已交付或正在运行 | 保守计入占用，保留回传与 stop，不自动重建；确认停采/完成及结果对账后迁移剩余项 |
| 离线、交付历史不明 | 标记待确认并保守占用；不得仅凭无心跳当作未执行 |
| 已可靠完成 | 保留历史及结果，不重发 |

未收口的旧包会阻断新队列放量；不静默丢弃旧任务，也不把旧包每帖限速当作新代码已经保证。恢复后的新状态可供原 requestKey 幂等返回。迁移和发布前后都验证 selectedRecordIds、已完成项与剩余项没有重复或丢失。

切换期间统一关闭新执行入口；必须确认旧派发进程和旧后处理进程已退出、存量占用回填完成，新代码才放量。旧进程不会遵守新准入或领取令牌，不能在混跑时假定保护已生效。过渡期间保留兼容的回传与 stop；数据库连接预算包含同时存在的新旧进程，不能因滚动发布临时翻倍。此屏障是正式发布步骤，本轮不操作。

### A5. 评论后处理改为持久化记录驱动（R4）

本轮进一步确认已有基础：insertObservation 在同一事务保存 record_observations.payload 和 queued receipt；comment-workflow.js 的 reprocessPendingCommentWorkflowReceipts 已由 ai-media-runtime 调用。采用这些现有记录，不再引入一套业务队列。

1. 新回传在同事务保存可完整重放的规范化评论输入、来源及 queued 状态；兼容读取旧 payload 格式。仅有“预计评论数”不算输入已保存。入口保存成功才能回复“数据已接收、后处理排队”。
2. 删除无限保存完整记录闭包的 commentWorkflowQueue。内存只持有有界的 observation ID 提示；即使提示丢失，周期扫描和启动恢复可从持久化 queued 工作继续。周期扫描必须有索引、分页、并发和执行时间预算。
3. 统一在线处理与恢复的领取入口。用行锁/领取令牌原子领取，记录 worker、lease、重试时间；长工作续约，完成/失败更新必须匹配本次令牌，旧 worker 不能覆盖重领结果。复用评论唯一键保证重试不重复入库。
4. 将每帖评论入库、AI 精炼分阶段计账。重启、AI 失败不能把已入库评论变成“未收到”；不能把 queued 当作全部完成。现有恢复流程读取最新主记录时，须优先用该 observation 的输入快照，避免不同轮次混用正文/评论。
5. 观测 queued/running 数、持久化字节、最老等待、处理速率和内存 ID 队列长度。暂停新派发的高水位必须低于持久化硬上限，为在途回传预留余量。
6. 硬上限按规范化输入字节和工作数量原子预留：预算检查/预留与 observation、queued receipt 写入同一事务，使用小型预算记录保证并发不会共同越限；回滚退还，后处理完成结算释放，幂等重传不重复占额，并支持持久化对账。硬上限或磁盘余量不足时，未能可靠落库的单项明确返回可重试，batch 逐项保留成功/失败语义；客户端保留未确认数据并退避。已经确认的数据不能因过载被淘汰。已落库但 HTTP 响应未知的重试必须复用来源采集身份，评论/后处理幂等，不重复生成业务结果。
7. 为 receipt 增加必要的 lease token/expiry、next_attempt_at、retry_count 和规范化输入版本；控制字段迁移保持加法兼容，不更改已有业务终态含义。已持久化工作在切换/回滚期间不得丢失或被两个处理器无限重复领取。

### A6. 隔离验收的初始保护参数

以下是待压测的保守起始配置，不是生产容量测量结果；实现时落为可配置且有上下界的参数，实测报告决定发布值。

| 参数 | 起始值/规则 |
|---|---|
| 数据库连接总预算 | 10：critical 4、general 4、reporting 2；按部署实例总和核算 |
| 整机/租户活跃巡查 | 2 / 1 个帖子执行 |
| 首次准入速度 | 整机每 10 秒最多 1 帖，不累积突发额度 |
| 领取事务/锁等待 | 500 ms / 50 ms，冲突直接留队 |
| reporting SQL 超时 | 2 秒，客户端超时大于数据库取消/回滚预算 |
| 新领取过载暂停 | 连接等待连续两次超过 100 ms，或后处理达到高水位；观测缺失时暂停新增许可 |
| 渐进恢复 | 连续 60 秒低于恢复水位，再逐步恢复；恢复阈值低于暂停阈值 |
| 过载停止目标 | 在线且可通信设备，从 stop API 被接受到停采不超过 15 秒；离线显示待确认，不虚报已停 |
| 后处理处理并发/内存提示 | 整机 1 个处理者；最多 100 个 observation ID，持久化扫描兜底 |
| 后处理水位候选 | 1000 个未完成 observation 或 128 MiB 待处理载荷暂停新派发；硬上限 2000 个或 256 MiB；按真实单帖大小和磁盘余量调低，不能把这些数值当安全保证 |

CPU/内存低频采样与事件循环延迟作为附加熔断指标，报警和采样自身不能高频扫全表。关键端点和停采延迟、释放连接情况分别验收，不以总请求量或健康检查代替。

### A7. 创建减负

预览不读未展示的历史基线；创建只复核选中 ID、不重复 COUNT；创建时基线批量读取；items/attempt 参数化批量写入并有界分块。资格复核与落库保持原子性，缩短持锁时间。此优化不能替代 A1—A6。

## B. 负面预览、分页与提交

### B1. 选定资格决策表（R5）

把“命中当前负面”和“能否下发”明确区分。主列表显示时间范围内命中的负面；暂不能执行的记录显示原因且不可选，不能靠隐藏让用户误以为没查到。

| 顺序 | 条件 | 命中/下发规则 |
|---|---|---|
| 1 | 不属于当前租户，平台或所选发布时间/显式关键词、互动量条件不符 | 不命中；租户隔离不可绕过 |
| 2 | 存在合法人工情感覆盖（对象 value 或兼容旧字符串） | 使用该值，不被 records 中后续 AI 情感推翻 |
| 3 | 没有人工情感覆盖 | 使用 records.sentiment 当前值 |
| 4 | 有效情感为中性/正面/未判断 | 不进入负面列表 |
| 5 | 有效情感为负面 | 命中；历史 ai_result.relevance 或自动生成的 business_visibility 不能单独否决人工负面，也不能替代当前情感 |
| 6 | 存在明确人工无关排除或已归档 | 仍显示当前负面及“暂不下发”具体原因，解除对应状态后才可选 |
| 7 | 存在待审误报 | 已有可信人工负面时只显示反馈提示，不阻止下发；无人工作出情感确认时暂缓不可选；误报复核不自动改情感 |
| 8 | 官方内容、已确认删除/不可用、原帖无法定位 | 显示不可执行原因，不下发 |
| 9 | 人工覆盖存在但格式非法，或人工来源无法可信解释 | 不自动回退 AI 后允许执行；按当前可读值显示异常/待核对，不可选并记录诊断 |

人工情感、独立人工排除、误报、归档是不同维度，不比较不可靠的跨字段时间来互相撤销。同一维度按当前保存值；缺失 updatedAt 不推断先后，也不用 records.updated_at 代替人工字段更新时间。新的人工负面不会自动撤销归档或人工无关；反馈 reviewed/summarized/dismissed 只改变反馈复核状态。

现有 manual-fields 不支持 relevance；历史人工排除若仍有效，提供聚焦的、受审计的解除排除入口，只移除该人工排除，不隐式改情感。归档与误报沿用原有操作。未经人工确认的 AI 无关、自动过滤不得伪装成“人工排除”。

预览与创建共用同一资格服务，返回 effectiveSentiment、sentimentSource、eligibilityReason。基于人工负面重新分析/采集时也使用同一保护规则更新投影；旧 AI 原始结果保留供追溯，不篡改成用户判断。发现字段矛盾先明确修正写入链，不仅在 UI 更换标签。

### B2. 时间和范围

按界面所示“发布时间”，Asia/Shanghai，起始日 00:00 含，截止日次日 00:00 不含；不改用采集时间。人工改发布日期按有效人工值/规范化 published_ts 保持一致。缺失发布时间的记录不能假装属于所选时间，提供可诊断的缺失原因。

保留单次下发最多 100 帖；预览默认每页 50，可继续加载整个范围。使用 published_ts、id 的稳定游标顺序，跨页去重；全选明确为当前页，跨页已选保留但总数不超过 100，超过则提示分批，不自动再建第二个任务。

每次响应的总数/列表来自同一查询快照，分别给出命中数、可下发数、暂缓数及当前页数。跨页期间发生人工修改时，不承诺所有页仍是同一历史快照；刷新重新取得当前名单，创建最终按当前资格复核。

### B3. 旧请求失效

preview 绑定 request generation 与租户/平台/日期/关键词/互动量/带入 ID 等条件快照。任何条件变更让旧响应失效；旧 finally 也不能清除新请求的 loading。重新预览失败不保留可提交的旧名单。页码/游标也属于请求身份，不能串页。

对用户异常样本核对 recordId、有效人工情感、数据库返回和界面显示，并记录请求条件。这个追踪和上述回归可同时推进；没有现场证据时只声明已修复明确代码路径，不宣布原异常根因已经证实。

### B4. 选定“提交结果未知”的恢复路径（R6）

发送前按登录用户＋租户持久化不可变的 requestKey、完整输入快照、输入哈希和状态，不保存认证凭证。页面只维护这一持久化记录的投影。

| 状态 | 可执行操作 |
|---|---|
| draft | 可改选择与条件 |
| submitting | 冻结所有入口，包含全选、候选行、分页与筛选 |
| unknown（超时、断网、关闭弹窗/刷新） | 原键和快照保留，先恢复原请求；不能改键重建 |
| confirmed | 持久化 taskId 后再刷新列表；列表刷新失败不重新创建 |
| rejected_before_create | 服务器明确表示未创建后才能解锁编辑；网络/500/解析失败不是此状态 |
| conflict / 重新登录所需 | 保留记录并显示恢复原因，不自动删除或更换身份 |

恢复复用同一 POST /negative-patrol/tasks、完全相同的键与快照：后端先返回已有任务，或在确实未提交时用原键完成。恢复 POST 可能完成原用户提交，界面应明确显示“确认上次提交”；不是只读查询。跨租户/退出登录后不在新租户重放，原用户重新登录才能恢复。

资格变化返回具体变更原因并要求刷新，不替换为另一批帖子；沿用现有请求字段 recordIds，新建巡查仅接收用户明确选中的 ID，拒绝字段缺失和空数组，避免后端自动挑选一批。多页仍只提交用户实际选中且当前可执行的 ID。

## C. 标签页、锁与待回执

### C1. 后台掌握创建与所有权（R9）

只对 negative_post_patrol 启用本次生命周期入口；其余共享巡查工作流维持原行为并做回归。

执行开始时按 requestId+attemptId 串行：
1. 预留本地待回执容量；
2. 获取执行锁的同一受保护存储操作中绑定物理轮次：沿用 captureTaskId = requestId::attemptId、captureTaskAttemptId = attemptId，登记表另存 requestId、attemptId、lockId、holder 与执行页归属；不能只新增会被锁规范化丢弃的字段；
3. 保存创建意图，然后由后台先开带随机归属标记的扩展占位页；
4. 登记 tabId 后再导航目标平台，执行页不自行绕过后台创建。

会话令牌使用 storage.session，登记使用独立 storage.local 命名空间。当前 manifest 已含 unlimitedStorage，但仍设置应用自己的空间上限并处理写失败。浏览器重启导致归属无法证明时不按旧 tabId 关页；同一次 Worker 休眠/恢复不丢登记。创建后登记失败的占位页可按标记补偿清理，未登记不得开始采集。

### C2. 终态的确定收尾顺序

本次已确认的旧顺序缺口：后台收到终态后先关扩展执行页；帖子清理和释放锁却依赖该页后续 finally。改成后台恢复式收尾：

确认本轮内容采集停止并暂停媒体 → 原子保存终态、完整待回执和清理阶段 → 尝试一次云端回执 → 回收本轮帖子页 → 精确释放本轮锁 → 最后关闭执行页。

每一步记录状态并可幂等重入。网络失败不能阻挡已有可靠本地结果后的关页；但本地结果保存失败不能销毁唯一完整结果所在的执行上下文。页面关闭失败时保留登记，不能确认内容已停止则不释放执行额度或启动下一轮。

复用 runAuthoritativeControlStorageMutation、releaseExactCaptureExecutionLockSnapshot。释放必须匹配 lockId、holder、captureTaskId 和 captureTaskAttemptId，并与登记表一致；旧清理晚到不能释放新锁或关闭新页面。非关键云端 UI 更新不能成为本地收尾永久阻塞点。

### C3. 独立有界待回执队列（R8）

新增 targetedTerminalOutbox.v1，按 Agent 身份、commandId、requestId、attemptId 存储完整冻结结果、确认状态、重试时间及 payload hash。它与最近 50 条命令历史缓存分离，不依赖 current request，也不受旧历史 TTL 清理。

- 候选预算为最多 64 条、8 MiB，任一达到即停止本设备新执行。它是待验收上限，不是 unlimitedStorage 允许无限增长的理由。
- 执行前按最大合法单帖回执预留空间；回执最大字节必须在扩展与服务端协议中一致约束。超过预留或写盘失败时保留完整本地来源并停新执行，不截断证据、不淘汰未确认项。
- 当次终态消息立即尝试一次；后台启动、现有云端 alarm 和心跳恢复成功触发补报，每次最多 1 条，指数退避加抖动，不额外高频轮询。
- 新增服务端回执兼容能力：按 commandId/attempt/hash 验证并回显确认身份，允许同一已接收结果幂等确认。当前接口只回 ok、commandId、idempotent，不能视为已有完整确认能力。服务端先发布校验与确认回显，双方能力协商通过后再启用新扩展队列；旧扩展保留原响应兼容。客户端收到匹配身份的明确确认才释放队列空间，不能将旧响应解释为完整身份/hash 已确认。409 冲突或旧轮被替代不等于成功，保留证据进入对账，不无限重采/重试。
- 新轮可以在预算和执行锁允许时开始，旧轮结果仍独立可补报。回滚到不认识新队列的扩展前，必须排空或完成对账。

### C4. 验证码与人工重试（R7）

保留单帖 result 的既有 failed + requiresManualAction 表达，负面 run 汇总明确产生已有 needs_action，并停止后续执行。清理以显式保留原因判断，不能只靠普通 failed/needs_action 字符串推断。

needs_action 是已结束的旧 attempt，不复活它。后台确认内容停止后保存结果、保留帖子页、精确释放旧锁，并可关闭旧执行页。人工处理完成后，新建经过服务端准入的新 attempt：

- 同设备、同帖子且旧页归属可证明：后台原子转移页面所有权，再启动新执行页；旧 attempt 的清理令牌随交接失效。
- 跨设备：不转移 tab。旧现场不自动关闭不明用户页面，标注为待人工处理；不宣称跨设备可回收所有旧页。
- 接管未解决前不不断开新页；普通同步故障在可靠保存结果后正常收尾。

真实安全错误到 needs_action 的云端任务/attempt 汇总兼容性必须验证；若服务端契约不接受该组合，先做兼容支持再启用扩展，不能仅在测试中直接构造 needs_action。
