# 任务编排与状态模型

本文面向产品、开发、测试和运维人员，说明 StarVoice 当前稳定版的云端任务
编排模型、Agent 执行协议、状态聚合、恢复策略和定时计划。内容以
`server/routes/capture-cloud*`、`server/services/capture-*` 及迁移
`041_capture_orchestration.sql` 之后的实现为准。

## 1. 设计目标与稳定边界

任务中心解决的是“把一项业务工作可靠地交给一个或多个浏览器 Agent，并能
在云端查看、重试、继续和追踪结果”，而不是迁移浏览器的实时 UI 状态。

当前稳定支持：

- 一个浏览器配置文件作为一个独立 Agent；
- 一次性关键词采集与设备本地无人值守计划；
- 多 Agent 将关键词或帖子工作项均衡拆分；
- Agent 离线时云端保留命令，上线后领取；
- 结构化进度、结果、检查点和失败原因回传；
- 可重试失败项、人工继续、空闲 Agent 接力；
- 小红书、抖音的关键词采集；
- 负面帖子定向巡查；
- 关注博主作品巡查；
- 官方账号作品与评论巡查；
- 定时计划、执行历史、快照历史和安全事件人工介入。

当前不应承诺：

- 把一台浏览器中正在打开的页面无缝迁移到另一台电脑；
- 浏览器进程关闭后仍在本机执行；
- 所有平台页面结构变化都能自动兼容；
- 只凭错误文案推断风控状态；
- 在没有心跳的情况下把 Agent 展示为实时在线；
- 任务失败后无限重试；
- 自动解决验证码或代替人工完成安全验证。

## 2. 核心对象

```text
租户 Tenant
  └── 设备分组（客户可理解为一台电脑）
       └── Agent（一个浏览器配置文件中的 Extension）
            ├── 心跳 / 能力 / 当前账号
            ├── 云端命令
            └── 执行槽

父任务 / 编排任务 Orchestration
  ├── 工作项 Work Item（关键词、帖子、账号等最小业务单位）
  │    └── 工作项尝试 Work Item Attempt
  ├── 子任务 Capture Task（交给一个 Agent 的执行批次）
  │    └── 任务尝试 Task Attempt
  ├── Agent Command（待领取指令）
  └── Snapshot / Checkpoint（进度快照与继续位置）
```

### 2.1 设备与 Agent

- “同一台电脑”只是管理端分组概念，真正的执行节点是浏览器 Agent。
- Chrome、Edge 或不同 Chrome Profile 会分别注册为不同 Agent。
- Agent 身份由租户、浏览器客户端 UUID、激活环境等共同约束。
- Agent Token 只能访问 Agent 接口，不能替代管理端登录。
- 管理端允许为 Agent 设置客户可识别名称、负责平台和账号绑定。

### 2.2 在线判定

服务器以最近心跳为准：

- 最近心跳在两分钟内：在线；
- 超过两分钟没有心跳：离线；
- 浏览器窗口存在但 Extension 没有心跳：仍应判为离线；
- 页面打开不代表 Agent 空闲，还要检查执行槽和当前任务。

在线状态是“近期可通信”的判断，不是任务必然成功的保证。平台登录失效、
安全验证、页面改版或账号风控仍可能导致任务失败或需要人工处理。

### 2.3 工作项与子任务

工作项是编排和接力的最小单位：

- 关键词采集：一个关键词一个工作项；
- 负面巡查：一篇目标帖子一个工作项；
- 关注博主/官方账号巡查：按账号或作品生成相应工作项；
- 每个工作项在同一时刻只归属一个 Agent 尝试。

子任务是某个 Agent 一次领取和执行的一组工作项。父任务用于聚合所有子任务
的进度，避免把每条内部同步或每次尝试都作为业务任务展示。

## 3. 创建与分配

### 3.1 通用约束

- 关键词最多 300 个；
- 单次可选择的 Agent 最多 50 个；
- 一个编排任务只处理一个平台；
- 平台值统一为 `xiaohongshu` 或 `douyin`；
- 空关键词、重复空白和无效 Agent 会在创建阶段被拒绝或清理；
- Agent 必须属于当前租户，不能跨租户分配；
- 任务请求会生成稳定请求哈希，用于识别重复提交。

### 3.2 多 Agent 分配

默认采用连续、互斥、尽量均衡的拆分：

1. 保留用户提交的工作项顺序；
2. 工作项只分配给一个 Agent；
3. 各 Agent 数量差不超过 1；
4. 工作项少于 Agent 数量时，不创建空子任务；
5. 用户在确认页手动调整的 Agent 归属优先于默认规则。

例如 13 个关键词分配给 3 个 Agent，结果为 `5 / 4 / 4`。这能保证任务总量
不重复，又能让“第几个词、由谁执行”具备可解释性。

### 3.3 增强采集参数

增强能力只在任务明确启用详情采集时下发。常见参数包括：

- AI 相关性预筛选；
- 自动同步后台；
- 博主信息；
- 评论与评论上限；
- 客资筛选；
- 跳过已完成增强内容。

管理端创建任务和 Extension 本地创建任务最终应形成同一任务配置结构。任务
详情应以保存后的云端配置为准，不能仅依赖创建页面的视觉开关。

## 4. 执行协议

### 4.1 命令生命周期

云端为 Agent 创建命令后，典型流程为：

```text
pending
  → Agent 心跳领取
acknowledged
  → Extension 接受并开始
completed / failed / expired
```

命令状态：

| 状态 | 含义 |
|---|---|
| `pending` | 已入队，等待目标 Agent 上线领取 |
| `acknowledged` | Agent 已确认收到 |
| `completed` | Agent 已完成命令并回传 |
| `failed` | Agent 明确回传失败 |
| `expired` | 命令超过有效期，不能再执行 |

离线 Agent 的 `pending` 命令不会消失，但如果设备已经换租户、重装后身份变更
或永远不再上线，应由管理员停止/迁移任务并清理失效节点，而不是无限等待。

### 4.2 执行槽

每个 Agent 有互斥执行槽，避免同一浏览器同时运行多个破坏页面状态的任务。
任务完成、失败、中断或超时后必须释放。若 UI 显示空闲但持续无法领取，应
检查：

- 旧命令是否未结算；
- 执行槽锁是否过期或残留；
- Extension 版本是否支持任务工作流；
- Agent Token 是否已因重绑定而失效。

### 4.3 心跳、快照与业务进度

Agent 心跳承担：

- 在线状态；
- 版本、浏览器、操作系统和能力声明；
- 当前任务和执行槽摘要；
- 任务进度与检查点；
- 当前登录社交账号的最佳努力识别；
- 当日账号用量事件。

快照是云端观察和恢复依据，但不是浏览器页面的完整复制。服务端会清理和限制
心跳/快照内容，避免任意大对象或敏感值直接进入数据库。

检查点至少应表达：

- 当前工作项；
- 已完成、已跳过和失败工作项；
- 当前阶段；
- 可继续的位置；
- 结构化错误码和是否需要人工介入。

## 5. 状态模型

### 5.1 父任务 / 子任务状态

`capture_tasks` 当前可能出现：

| 状态 | 业务含义 |
|---|---|
| `pending` | 已创建，尚未形成可执行命令 |
| `waiting_device` | 已分配，等待 Agent 上线 |
| `claimed` | Agent 已领取 |
| `running` | 正在执行 |
| `recovering` | 正在恢复或重试 |
| `interrupted` | 执行被中断，保留恢复条件 |
| `resume_requested` | 用户已请求继续，等待执行 |
| `needs_action` | 需要人工介入，例如安全验证 |
| `completed` | 全部成功 |
| `completed_with_warnings` | 完成但包含跳过或非阻断警告 |
| `completed_with_failures` | 已结束，但存在失败工作项 |
| `failed` | 任务整体失败 |
| `canceled` | 用户或系统取消 |
| `skipped` | 没有需要执行的业务内容 |
| `superseded` | 已被新的任务或重分配替代 |

任务尝试状态比任务状态更窄：

`claimed`、`running`、`recovering`、`completed`、
`completed_with_warnings`、`completed_with_failures`、`failed`、
`canceled`、`interrupted`。

### 5.2 工作项状态

`capture_task_items`：

| 状态 | 含义 |
|---|---|
| `assigned` | 已分配给 Agent |
| `dispatch_pending` | 等待生成/投递命令 |
| `dispatched` | 命令已投递 |
| `waiting_device` | 等待设备上线 |
| `running` | 正在处理 |
| `retryable` | 当前尝试失败，可按规则重试 |
| `needs_action` | 需要人工介入 |
| `completed` | 成功完成 |
| `completed_with_warnings` | 有结果，但包含警告 |
| `failed` | 达到失败条件 |
| `skipped` | 合理跳过，例如在筛选范围内没有结果 |
| `canceled` | 已取消 |

工作项尝试还可能处于 `pending`、`accepted`、`interrupted` 等协议状态。

### 5.3 状态聚合

父任务只按真实子项状态聚合，不推测 Extension 当前页面：

1. 任一子项正在执行，父任务保持 `running`；
2. 任一子项需要人工处理，父任务进入 `needs_action`；
3. 所有子项终态且存在失败，父任务为 `completed_with_failures`；
4. 没有失败但有警告或跳过，父任务为 `completed_with_warnings`；
5. 所有子项成功，父任务为 `completed`；
6. 所有子项终止且主要结果为取消，父任务为 `canceled`。

“搜索结果为空”“发布时间不在范围内”“帖子已删除”不应一概记为系统失败：

- 正常无结果：`skipped` 或带警告完成；
- 帖子已删除/不可用：记录结构化可用性状态，定向巡查可带警告完成；
- 页面超时、标识不匹配、接口错误：根据错误码进入重试或失败；
- 验证码/安全挑战：进入 `needs_action`，等待人工决定。

## 6. 重试、继续与接力

### 6.1 自动重试

工作项默认最多尝试 2 次。只有明确标记为可重试的错误才重试，例如短暂页面
未就绪或服务异常。达到最大次数后进入失败或需要处理。

以下情况不能盲目自动重试：

- 验证码或安全挑战；
- 账号登录失效；
- 目标作品标识持续不一致；
- 用户明确停止；
- Agent Token 已失效；
- 平台不支持该工作流。

### 6.2 真正的“继续”

继续任务必须从服务器保存的工作项和检查点恢复：

- 已完成工作项不重跑；
- `retryable`、`interrupted` 或指定失败项进入新尝试；
- 正在执行的工作项不会重复分配；
- 生成新的尝试和命令，保留旧尝试历史；
- 父任务进度由最新工作项状态重新聚合。

如果 Extension 只保存了“当前关键词索引”而没有把完成结果同步到云端，继续
可能从上一个已确认检查点开始。这是设计边界，不等于页面滚动位置恢复。

### 6.3 空闲 Agent 接力

任务可启用空闲接力：

1. 原 Agent 发生可接力的中断或失败；
2. 服务端选择同租户、同平台、具备相应能力的空闲 Agent；
3. 仅迁移未完成工作项；
4. 新 Agent 创建新尝试和命令；
5. 原 Agent 后续迟到回传不能覆盖新尝试结果。

安全验证默认需要人工确认后才可接力，避免把同一平台风控快速扩散到更多账号。

## 7. 定时与无人值守计划

### 7.1 计划状态

计划状态为：

- `active`：可生成下一次运行；
- `paused`：暂停但保留配置；
- `completed`：指定日期或轮次已完成；
- `canceled`：人工取消，不再调度。

### 7.2 计划类型

- 每日计划；
- 指定日期列表；
- 每日支持随机延迟，最大 240 分钟；
- 指定日期最多 400 个；
- 默认单次编排最大运行轮次为 1；
- 默认跳过重叠运行；
- 调度时区固定为 `Asia/Shanghai`；
- 迟到宽限默认为 360 分钟；
- 每日计划最多向前生成约 370 天。

指定日期全部过去后，计划应显示“已结束/无后续排期”，而不是继续显示为可
运行。管理端应同时展示运行日期、关键词列表、下一次和上一次运行。

## 8. 专项巡查工作流

### 8.1 负面帖子定向巡查

- 输入为已筛选的目标帖子；
- 支持多 Agent 分片，避免单账号集中访问；
- 打开目标详情、校验作品标识、采集详情和可选评论；
- 作品已删除或不可用时记录可用性，不采集下一条推荐内容；
- Extension 应打开暗色运行状态页，展示当前帖子、进度和异常；
- 结果进入负面巡查和舆情分析，不应自动转工单。

### 8.2 关注博主作品巡查

- “关注的博主”保留为独立业务；
- 根据已登记主页生成作品巡查任务；
- 可按近期时间范围、最大作品数和 Agent 能力执行；
- 博主作品发现和官方账号评论巡查不能混为同一流程。

### 8.3 官方账号评论巡查

- 官方账号必须在后台登记主页链接和平台；
- 单次最多巡查 20 篇作品、每篇最多读取 100 条评论；
- 发布时间范围最长 30 天；
- 列表页不可靠地提供发布时间时，必须进入作品详情校验，不能仅凭列表顺序；
- 结果只属于目标官方账号，不得把搜索结果或相关推荐误认成官方作品；
- 未配置主页链接时阻止创建任务并提示补全资料；
- Agent 必须声明 `remoteTaskCreate`、定向作品采集和官方账号详情发布时间能力。

## 9. 幂等、并发与迟到回传

- 创建请求以业务字段和工作项/Agent 顺序计算请求哈希；随机 ID 和时间戳不
  参与哈希。
- 每个 Agent 只有一个互斥执行槽。
- 每个工作项尝试有自己的目标标识；回传作品 ID 与目标不一致时拒绝云端写回。
- 重分配后旧命令和旧尝试仍保留审计记录，但不能覆盖当前工作项。
- 快照历史采用追加方式保存，不能只覆盖最后一条。
- 清理失败项是归档/移动业务状态，不应删除真实尝试和错误证据。

## 10. 排查指南

### 10.1 “Agent 在线但收不到任务”

依次确认：

1. 心跳是否在两分钟内；
2. Agent 是否属于当前租户；
3. Agent Token 是否有效；
4. 任务平台是否在 Agent 能力列表；
5. 执行槽是否被旧任务占用；
6. 命令是否 `pending`、过期或已被其他实例领取；
7. Extension 版本是否支持工作流；
8. 浏览器配置文件是否与后台节点名称对应。

### 10.2 “继续后又从前一个词开始”

检查最近一次云端检查点，而不是只看 Extension UI：

- 前一关键词是否完成并成功回传；
- 快照是否晚于业务结果；
- 是否重用了旧尝试；
- 是否因断网导致完成事件未到达服务器；
- 重分配时是否只选择未完成工作项。

### 10.3 “任务显示失败但页面看起来采集成功”

检查：

- 回传作品 ID 与目标 ID；
- 页面是否自动播放到下一条；
- 结果是否写入当前尝试而非旧尝试；
- 评论开关和评论上限是否实际下发；
- 云端聚合是否读取最新工作项状态；
- 是否只是管理端缓存了上一次状态。

### 10.4 只读验证

生产上优先通过管理端、API 日志和只读 SQL 验证。数据库表结构以迁移为准：

```sql
SELECT status, count(*)
FROM capture_tasks
WHERE tenant_id = $1
GROUP BY status
ORDER BY status;
```

不要直接修改任务状态“让界面好看”。修复状态应走服务层，确保工作项、尝试、
命令和父任务聚合一致。

## 11. 变更检查清单

修改任务模型时至少验证：

- [ ] 一次性单 Agent 任务；
- [ ] 多 Agent 的互斥均衡分配；
- [ ] Agent 离线后上线领取；
- [ ] 停止、继续和仅重试失败项；
- [ ] 原 Agent 迟到回传不会覆盖接力结果；
- [ ] 验证码进入人工处理而不是无限重试；
- [ ] 帖子删除/无结果按业务状态记录；
- [ ] 指定日期计划结束后不再生成任务；
- [ ] 父任务状态与所有工作项状态一致；
- [ ] 租户间看不到彼此的 Agent、任务和结果；
- [ ] 旧版 Extension 收到不支持的命令时明确失败，不静默执行错误流程。
