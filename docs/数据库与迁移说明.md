# 数据库与迁移说明

本文说明 StarVoice 当前 PostgreSQL 数据模型、租户隔离、迁移执行规则、备份
恢复和安全变更流程。实际结构以 `server/db/migrations/*.sql` 为唯一依据；
本文不替代迁移文件。

> 2026-08-14 生产只读核对：最新已执行迁移为 `066_tenant_comment_risk_attention.sql`。P2-A1 限定 Server 发布没有新增或执行数据库迁移。

## 1. 数据库定位

StarVoice 使用 PostgreSQL 保存：

- 租户、用户、账号与工作区配置；
- 舆情内容、评论、作者、互动快照；
- 分类、人工反馈、标签、分析结果；
- 销售线索、工单和处理轨迹；
- Agent、激活与社交账号绑定；
- 云端采集任务、工作项、尝试、命令、快照和计划；
- 邮件提醒队列和投递记录；
- OCR、转写和舆情分析元数据。

图片、封面、临时音频等二进制文件不直接存入数据库。数据库保存其路径或
元数据，真实文件位于 `MEDIA_DIR` 或对应静态目录。数据库备份和媒体目录
备份必须配套考虑。

## 2. 连接与启动

主要环境变量：

```dotenv
DATABASE_URL=postgres://USER:PASSWORD@HOST:5432/onstarvoice
PG_POOL_MAX=10
PG_IDLE_TIMEOUT_MS=30000
PG_CONNECT_TIMEOUT_MS=5000
```

生产环境必须显式设置 `DATABASE_URL`。代码中的本地连接兜底只用于开发，
不能作为生产配置。

服务启动顺序为：

1. 校验数据库连接；
2. 运行未执行迁移；
3. 在数据库尚无平台管理员时执行首次管理员引导；
4. 启动 HTTP 服务和后台任务。

因此，数据库不可达或迁移失败会阻止服务正常启动。这比“应用先运行、稍后再
迁移”安全，但意味着每次发布都必须在部署前备份并审核新迁移。

## 3. 租户隔离

### 3.1 当前实现

多数业务表包含 `tenant_id`，管理端会话、Agent Token 和服务层查询共同限定
租户。租户切换时，后台请求通过受控的租户上下文访问数据。

当前稳定边界：

- 隔离主要由应用层查询条件保证；
- 当前没有宣称启用 PostgreSQL Row Level Security；
- 数据库账号一旦可以绕过应用直接查询，就不受应用层隔离保护；
- 平台管理员的跨租户能力应只用于受控运维；
- 历史导入数据可能使用默认 OnStar 租户兜底，迁移或复制前必须核对归属。

### 3.2 开发要求

新增租户业务表或查询时必须：

1. 表中明确保存 `tenant_id`；
2. 唯一索引包含租户维度，除非数据确实全局唯一；
3. 所有读、写、更新、删除都以租户为条件；
4. JOIN 不能只按业务 ID，应同时约束租户；
5. 后台任务逐租户执行，不能把一个租户设置复用于另一个租户；
6. 测试至少建立两个租户，验证交叉读取为空。

不要依赖“ID 很随机，所以撞不到”实现隔离。

## 4. 迁移机制

入口为：

```bash
cd server
npm run migrate
# 等价于 node db/migrate.js
```

这是会执行写入、未登记迁移和既有回填的入口，只能用于明确获批的迁移实施或隔离数据库预演，不能作为“无迁移发布”的发布后只读验证命令。

`server/db/migrate.js` 的执行规则：

- 自动创建 `schema_migrations(version, applied_at)`；
- 按 SQL 文件名字典序执行；
- 使用完整文件名作为迁移版本；
- 已记录的迁移不会重复执行；
- 每个迁移在独立事务中执行；
- 成功后写入 `schema_migrations`；
- 失败时回滚当前迁移并停止；
- 文件名包含 `reset` 的迁移默认跳过；
- 只有 `ALLOW_RESET_MIGRATIONS=1` 才会执行 reset 迁移。

迁移编号从 `016` 跳到 `018` 是历史事实，不是待补空位。不要重命名已经执行
过的迁移，也不要新建 `017` 试图“修正”顺序，因为生产库按完整文件名记录。

## 6. 新增迁移规范

### 6.1 文件

1. 使用下一个未占用三位编号；
2. 文件名采用 `NNN_lower_snake_case.sql`；
3. 一个迁移聚焦一个业务变化；
4. 已进入共享或生产环境的迁移永不改名、删除或改写；
5. 修正旧迁移时创建新迁移；
6. SQL 必须能在当前生产版本结构上执行。

### 6.2 SQL 安全

推荐：

```sql
ALTER TABLE example
  ADD COLUMN IF NOT EXISTS new_field TEXT;

CREATE INDEX IF NOT EXISTS idx_example_tenant_created
  ON example (tenant_id, created_at DESC);
```

注意：

- 大表新增非空列应先允许空值或提供安全默认值，再分阶段回填；
- 大表建索引可能锁表，必要时设计维护窗口；
- 类型收窄、列重命名和删除字段需要兼容期；
- 回填必须按租户、批次和可恢复检查点执行；
- 不在迁移中调用不稳定外部 API；
- 不把生产客户特定数据修复混入通用结构迁移。

### 6.3 reset 迁移

reset 迁移可能清空、重建或覆盖数据。执行前必须：

1. 明确目标数据库；
2. 生成并验证可恢复备份；
3. 阅读完整 SQL；
4. 记录受影响表和预计行数；
5. 在副本数据库演练；
6. 获得明确的生产变更授权；
7. 临时设置 `ALLOW_RESET_MIGRATIONS=1`；
8. 完成后恢复为 `0`。

不要把 `ALLOW_RESET_MIGRATIONS=1` 长期写进生产环境。

## 7. 备份

### 7.1 数据库

推荐自定义格式：

```bash
pg_dump \
  --format=custom \
  --no-owner \
  --no-acl \
  --file=onstarvoice-$(date +%Y%m%d-%H%M%S).dump \
  "$DATABASE_URL"
```

验证备份可读：

```bash
pg_restore --list onstarvoice-YYYYMMDD-HHMMSS.dump | head
```

生产备份至少记录：

- 创建时间与时区；
- 源主机、数据库名和迁移版本；
- 文件路径、大小和校验值；
- 对应 Git 提交；
- 保留策略；
- 最近一次恢复演练结果。

### 7.2 媒体

数据库备份不包含 `MEDIA_DIR`。应独立备份：

```bash
tar -czf onstarvoice-media-$(date +%Y%m%d-%H%M%S).tar.gz \
  /opt/onstarvoice/media
```

实际路径以生产 `.env` 为准。恢复时数据库记录与媒体文件应来自一致时间点。

## 8. 恢复与演练

不要第一次在生产事故中验证备份。每次演练使用带 release ID 的唯一新库名，例如 `onstarvoice_restore_<release_id>`。先只读确认 `pg_database` 中不存在该名称；若已存在就停止并换新名称，禁止用固定库名加 `dropdb --if-exists` 删除以前的演练/事故证据。创建空的新验证库后，才使用 `pg_restore --exit-on-error --clean --if-exists --no-owner --no-acl` 恢复指定备份；这里的 `--clean` 只能指向刚创建且确认为空的验证库，绝不能指向生产库。

这里的 `postgres` 是执行受控恢复的管理身份，`onstarvoice` 是恢复库所有者和
应用登录角色。已有环境若使用其他已确认的独立角色，应同时替换 `--owner`、
`--role` 和隔离环境的连接串，不要只改其中一处。

验证：

```sql
SELECT now();
SELECT count(*) FROM schema_migrations;
SELECT version, applied_at
FROM schema_migrations
ORDER BY applied_at DESC
LIMIT 10;
```

再使用隔离环境连接恢复库，检查登录、租户、内容、任务和工单。确认无误后才能
制定生产恢复切换。

## 9. 租户复制与数据修复

“把客户租户复制到测试租户”属于一次性受控数据操作，不是普通管理端能力。
安全步骤：

1. 备份整个生产库；
2. 明确源租户和目标租户 ID；
3. 列出所有包含 `tenant_id` 的关联表；
4. 决定目标租户现有数据是保留、归档还是覆盖；
5. 为主键、外键、唯一键建立 ID 映射；
6. 不复制密码、会话、Agent Token、激活码、SMTP/LLM 密钥；
7. 不把源租户 Agent 或命令直接绑定到目标租户；
8. 在事务或隔离副本中执行；
9. 按表核对数量和抽样内容；
10. 验证源租户数据未变化；
11. 保存操作清单和回滚点。

直接修改 `tenant_id` 会破坏隔离和外键关系，禁止作为快捷复制方式。

## 10. 常用只读检查

### 10.1 当前迁移

```sql
SELECT version, applied_at
FROM schema_migrations
ORDER BY applied_at DESC;
```

### 10.2 表和大小

```sql
SELECT
  schemaname,
  relname,
  pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

### 10.3 长事务

```sql
SELECT
  pid,
  usename,
  state,
  now() - xact_start AS xact_age,
  left(query, 200) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

### 10.4 连接数

```sql
SELECT state, count(*)
FROM pg_stat_activity
WHERE datname = current_database()
GROUP BY state;
```

所有生产诊断优先使用只读查询。执行 `UPDATE`、`DELETE`、`TRUNCATE`、
`DROP`、直接改任务状态或跨租户复制前，必须另行审核和备份。

## 11. 发布验证

迁移的连续执行/幂等性只在隔离数据库预演，不在生产发布后通过再次执行迁移入口验证。生产应核对本次启动日志的数据库初始化和 migration 结果，再只读查询 `schema_migrations` 与关键计数，并同发布前冻结清单比较。

应验证：

- [ ] 启动日志没有数据库或 migration 错误；
- [ ] 只有迁移明确进入白名单时，目标版本才新增到 `schema_migrations`；无迁移批次没有新增登记；
- [ ] 服务能启动并通过 `/api/health`，且已单独核对 PM2、数据库、日志和业务状态；
- [ ] 新字段在旧代码路径下兼容；
- [ ] 两个租户的隔离测试通过；
- [ ] 任务、内容、评论、工单等关键计数无异常跳变；
- [ ] 持久化媒体仍可访问；
- [ ] 未意外执行 reset 迁移。

## 12. 已知风险

- 应用层租户隔离依赖每条查询正确携带 `tenant_id`；
- 自动迁移与应用启动耦合，错误迁移会阻止发布；
- SQL 事务能回滚当前迁移，但不能自动回滚外部文件或已经执行的历史发布；
- reset 迁移具有破坏性；
- 数据库与媒体分开备份可能产生时间点不一致；
- `schema_migrations` 记录的是执行事实，不证明业务数据语义正确；
- 一次生产备份存在不等于可恢复，必须做恢复演练。
