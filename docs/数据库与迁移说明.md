## 1. 数据库定位

StarVoice 使用 PostgreSQL 保存：

- 租户、用户、账号与工作区配置；
- 舆情内容、评论、作者、互动快照；
- 分类、人工反馈、标签、分析结果；
- 销售线索、工单和处理轨迹；
- Agent、激活与社交账号绑定；
- 云端采集任务、工作项、尝试、命令、快照和计划；
- 邮件提醒队列和投递记录；
- OCR、转写和舆情分析元数据。

图片、封面、临时音频等二进制文件不直接存入数据库。数据库保存其路径或
元数据，真实文件位于 `MEDIA_DIR` 或对应静态目录。数据库备份和媒体目录
备份必须配套考虑。

## 2. 连接与启动

主要环境变量：

```dotenv
DATABASE_URL=postgres://USER:PASSWORD@HOST:5432/onstarvoice
PG_POOL_MAX=10
PG_IDLE_TIMEOUT_MS=30000
PG_CONNECT_TIMEOUT_MS=5000
```

生产环境必须显式设置非空 `DATABASE_URL`。P2-D Maintenance 在取得任何进程锁、迁移锁或访问数据库前校验该值；缺失或只含空白会以 `MAINTENANCE_DATABASE_URL_REQUIRED` fail-closed。代码中的本地连接兜底只用于开发，不能作为生产配置。

兼容 `all` 的 P2-D 主线代码启动顺序为：

1. 取得 Scheduler 与 AI/Media 进程角色锁；
2. 取得数据库级迁移锁，校验迁移 checksum 并运行未执行的非 reset 迁移；
3. 通过 Maintenance registry 执行阻塞式 publish timestamp 兼容维护；
4. 在数据库尚无平台管理员时执行首次管理员引导；
5. 启动 HTTP 服务和后台任务，并按原有 immediate/15 秒/25 秒时序运行兼容维护 adapter。

独立 `api`、`scheduler`、`ai-media` 角色只做版本与 checksum readiness，不运行迁移、bootstrap 或历史 one-shot。数据库不可达、迁移缺失、checksum 未 adoption 或不匹配都会阻止这些角色就绪。生产仍是现有 `all`，上述 P2-D 行为尚未部署。

## 3. 租户隔离

### 3.1 当前实现

多数业务表包含 `tenant_id`，管理端会话、Agent Token 和服务层查询共同限定
租户。租户切换时，后台请求通过受控的租户上下文访问数据。

当前稳定边界：

- 隔离主要由应用层查询条件保证；
- 当前没有宣称启用 PostgreSQL Row Level Security；
- 数据库账号一旦可以绕过应用直接查询，就不受应用层隔离保护；
- 平台管理员的跨租户能力应只用于受控运维；
- 历史导入数据可能使用默认 OnStar 租户兜底，迁移或复制前必须核对归属。

### 3.2 开发要求

新增租户业务表或查询时必须：

1. 表中明确保存 `tenant_id`；
2. 唯一索引包含租户维度，除非数据确实全局唯一；
3. 所有读、写、更新、删除都以租户为条件；
4. JOIN 不能只按业务 ID，应同时约束租户；
5. 后台任务逐租户执行，不能把一个租户设置复用于另一个租户；
6. 测试至少建立两个租户，验证交叉读取为空。

不要依赖“ID 很随机，所以撞不到”实现隔离。

## 4. 迁移机制

P2-D 主线代码的唯一**显式/人工**迁移入口是短生命周期 Maintenance CLI：

```bash
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- migrate
```

兼容 `all` 启动仍会在初始化阶段调用受锁、受 checksum 保护的 `runMigrations()`；它不是 operator 命令，也绝不会自动执行 v066 checksum adoption。`node server/db/migrate.js` 直接入口已禁用。Maintenance `migrate` 会执行写入和未登记的非 reset 迁移，只能用于明确获批的迁移实施或隔离数据库预演；只读核验使用 `verify`：

```bash
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- verify
```

生产 `NODE_ENV=production` 必须同时显式设置 `PROCESS_ROLE=maintenance` 和非空 `DATABASE_URL`。缺失/空白连接串会在取得任何锁或访问数据库前以 `MAINTENANCE_DATABASE_URL_REQUIRED` 拒绝，不会使用本地默认库。非生产虽然可以从入口默认出 Maintenance 角色并使用本地连接兜底，文档示例仍显式填写角色和测试库，避免把开发默认带进发布流程。

`server/db/migrate.js` 的执行规则：

- 在任何 tracker 查询或写入前取得同一数据库范围的 PostgreSQL session advisory lock；等待有界，超时 fail-closed；
- 自动创建或升级 `schema_migrations(version, applied_at, checksum_sha256, checksum_recorded_at)`；
- 按 SQL 文件名字典序执行；
- 使用完整文件名作为迁移版本；
- 计算每个文件精确字节的 SHA-256；已记录迁移的 checksum 缺失或不匹配时 fail-closed；
- 已记录且 checksum 匹配的迁移不会重复执行；
- 每个迁移在独立事务中执行；
- 成功后同时写入版本、checksum 和记录时间；
- 失败时回滚当前迁移并停止；
- 文件名包含 `reset` 的迁移永不从普通迁移路径执行；
- `ALLOW_RESET_MIGRATIONS=1` 不再是授权开关，反而会触发 `DATABASE_RESET_MIGRATIONS_DISABLED` 并停止。

### 4.1 v066 冻结基线与首次 adoption

`server/db/migration-baseline-v066.json` 冻结 `main@c47800f3184effc9e6ef05aedba9f37a81053886` 时 65 个历史 SQL 文件的文件名、类型与 SHA-256。它用于防止仓库中的 001–066 被静默改写，也为旧库首次补 checksum 提供固定锚点。

旧 `schema_migrations` 没有 checksum 列或已执行 SQL 的 checksum 为 NULL 时，普通 `all` 启动和普通 `migrate` 都会拒绝自动信任。checksum adoption 只存在于 Maintenance CLI；只有确认生产受控环境里 `DATABASE_URL` 显式非空且指向目标库，并完成数据库备份、冻结发布内容、停止旧 migrator/长期进程、取得明确授权后，才可显式执行：

```bash
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- \
  migrate --adopt-v066-checksums
```

该命令会在迁移锁内升级 tracker、为 v066 冻结清单中已经登记的 SQL 版本写入 checksum，并继续应用缺失的非 reset 迁移（当前候选包括 067）。它不会删除历史非 SQL marker，也不会给未知 marker 伪造 SQL checksum。

首次 adoption 有一个无法消除的历史限制：它只能确认“从现在开始用 `c47800f` 的冻结字节作为比较锚点”，不能反向证明某个旧环境当年实际执行的 SQL 字节与该锚点完全相同。adoption 前仍须把生产已登记版本、发布档案、备份和仓库冻结清单做人工比对，不能把命令成功当作历史取证完成。

迁移编号从 `016` 跳到 `018` 是历史事实，不是待补空位。不要重命名已经执行
过的迁移，也不要新建 `017` 试图“修正”顺序，因为生产库按完整文件名记录。

## 6. Maintenance CLI（P2-D 已进主线、未部署）

支持的固定命令为：

```bash
# 应用未执行的非 reset 迁移；不会自动 adoption 旧 checksum
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- migrate

# 只读校验版本与 checksum
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- verify

# 只接受编译进 registry 的 task id，不接受任意 SQL 或文件路径
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- run <allowlisted-task-id>

# 顺序执行固定的启动恢复任务集合
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- startup-reconcile

# 仅在配置完整且确需引导管理员时使用
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- bootstrap-admin
```

当前 allowlist 包含：

- `publish-ts-backfill-v1`；
- `opinion-analysis-stale-repair`；
- `comment-promotion-reconcile`；
- `comment-safety-semantic-reclassify-v1`；
- `recent-media-backfill`；
- `saicgm-scope-relabel-v3`；
- `comments-workflow-backfill`；
- `legacy-sqljs-import`；
- `bootstrap-admin`。

为兼容新旧版本双向回滚，三个既有 once 任务使用固定 bridge：如果旧 `schema_migrations` marker 已存在，新代码在 `maintenance_runs` 记为 `adopted`，不重复执行，也不删除或改写旧行；如果新代码先成功执行任务，则在**同一条 SQL 语句**中把对应 `maintenance_runs` 行更新为 `succeeded` 并插入该任务的 legacy marker，保证成功审计与旧版本防重标记原子出现。已完成记录若因历史异常缺 marker，runner 会在 task lock 内补齐。

| Maintenance task | 历史 marker |
|---|---|
| `publish-ts-backfill-v1` | `publish_ts_backfill_v1` |
| `comment-safety-semantic-reclassify-v1` | `comment_safety_semantic_reclassify_v1` |
| `saicgm-scope-relabel-v3` | `relabel_saicgm_scope_v3` |

这只是有限的 rollback bridge，不允许为新任务继续写 marker；最终映射、任务版本、原子写入和 idempotency 规则始终以 `server/maintenance/registry.js` 与 `server/maintenance/runner.js` 为准。

`saicgm-scope-relabel-v3` 现在对部分失败 fail-closed：任一记录重判失败都会让本次 Maintenance run 记为 `failed`，错误码为 `MAINTENANCE_TASK_PARTIAL_FAILURE`，不会写 `succeeded` 或 rollback marker；此前已成功处理的单项也不会自动反向回滚。该 once 的任何 prior `failed` 或遗留 `running` 都会让后续调用以 `MAINTENANCE_TASK_RESTORE_REQUIRED` 阻断。未来获批上线后必须观察 `maintenance_runs`、错误摘要和 `[Relabel]` 日志；一旦出现上述状态，立即保持所有长期进程与写入入口停止，恢复该任务执行前的整库备份，确认 failed/running ledger 与业务数据一起回到执行前状态，再重新取得授权。禁止自动重跑、手工补 success/marker，或失败后直接切回并启动旧 `all`；旧代码没有该恢复门禁，且缺失 marker 时可能再次执行部分任务。

除 `bootstrap-admin` 外，上述业务数据任务均要求离线确认；`startup-reconcile` 也始终要求：

```bash
MAINTENANCE_OFFLINE_CONFIRMED=1 PROCESS_ROLE=maintenance \
  npm --prefix server run maintenance -- startup-reconcile
```

离线命令会尝试取得 Scheduler 与 AI/Media 两把进程角色锁，任务自身还会取得 task lock。这能拒绝仍持相同执行权锁的新进程，却不能证明当前未部署旧代码的 API/Worker、旧 migrator、外部流量或人工脚本已经停止。`MAINTENANCE_OFFLINE_CONFIRMED=1` 是操作者声明，不是自动检测；执行前仍必须人工停止并确认所有旧长期进程和写入入口，禁止只设置变量就继续。

两个历史 operator 脚本已经收口为固定 allowlist task：

```bash
MAINTENANCE_OFFLINE_CONFIRMED=1 PROCESS_ROLE=maintenance \
  npm --prefix server run migrate:legacy

MAINTENANCE_OFFLINE_CONFIRMED=1 PROCESS_ROLE=maintenance \
  npm --prefix server run comments:backfill
```

`migrate:legacy` 精确路由到 once task `legacy-sqljs-import`，`comments:backfill` 精确路由到 repeatable task `comments-workflow-backfill`。两者都经过生产 `DATABASE_URL` 门禁、Scheduler/AI 执行权锁、各自 task lock、schema/checksum readiness 与 `maintenance_runs` 审计。legacy import 只读取代码固定路径的 sql.js 文件；文件缺失以 `LEGACY_SQLJS_DATABASE_NOT_FOUND` 记为 failed，不记 success。该特定错误允许操作者补齐固定文件、复核来源并重新授权后重试；任何其他 failed 或遗留 running 都会触发 `MAINTENANCE_TASK_RESTORE_REQUIRED`，必须恢复任务前整库备份并确认失败 ledger 随恢复消失后才能再执行。alerts 使用来源派生的确定性 UUID 和 `ON CONFLICT` 幂等 upsert 来降低重复写入风险，但不能据此宣称任意失败都可直接安全重试；once 只有完整成功后才会在后续调用中跳过。直接执行 `server/scripts/migrate-sqljs-to-postgres.js` 或 `server/scripts/backfill-comments-workflow.js` 会以退出码 2 拒绝，不能绕过 Maintenance。

legacy import 的 record upsert 显式使用 `localizeMedia: false`，不会在锁释放后留下媒体下载/落库后台工作。需要媒体落地时，另行批准并运行受锁、受 `maintenance_runs` 审计的 `recent-media-backfill`，不能把媒体外连偷偷并入 legacy 导入窗口。

`PROCESS_ROLE=maintenance npm --prefix server run user:create-admin -- <email> <password> [name]` 仍是参数化 operator 入口，不是 `maintenance_runs` task。生产必须显式提供非空 `DATABASE_URL`，并先通过 schema/checksum readiness；创建用户仍需单独授权并保管命令行凭据，不能把角色/readiness 通过当作创建授权。优先使用不把密码暴露在 shell 历史中的受控方式执行。

`server/scripts/import-extension-csv.js` 也保留为带来源、租户等参数的独立 importer，不属于 Maintenance registry，也不写 `maintenance_runs`。帮助和省略 `--commit` 的 dry-run 只读取/解析 CSV 并输出预览，不连接数据库；dry-run 成功不能证明目标库、角色锁或 checksum readiness 正常。只有明确加入 `--commit` 的写入路径才要求显式 `PROCESS_ROLE=maintenance`、生产非空 `DATABASE_URL` 与 `MAINTENANCE_OFFLINE_CONFIRMED=1`，随后先取得 `all` 的 Scheduler/AI 执行权锁，再通过 `connectRuntimeDb()` 校验 schema/checksum readiness；结束时先关闭普通数据库连接，再释放执行权锁。CSV record upsert 同样固定 `localizeMedia: false`；媒体落地必须另行批准 `recent-media-backfill`，避免锁释放后出现未受控后台外连/写库。

CSV `--commit` 必须单独批准来源文件、目标租户、备份和预计行数，并人工确认旧 API/Worker/写入入口已经停止；环境变量和锁本身不能代替该确认。整个导入不是跨全部行的单一事务，单行失败后此前成功写入的行不会自动回滚；应保存最终统计和错误清单，先核对部分结果，再决定是否重试。不要把 dry-run、角色通过或锁取得解释成导入授权。

`server/scripts/repair-*.sql` 和 tenant-specific repair SQL 仅作为历史证据保留，未开放为 Maintenance 的任意 SQL/file-path 执行能力，**禁止直接在生产执行**。确需新的修复时必须新建目标固定、可测试、可审计的 allowlist task 或另行审批的迁移，而不是复用历史脚本。

兼容 `all` 暂时通过同一 registry 保留历史恢复时序，避免架构治理直接造成 crash-recovery 回归：publish timestamp 在数据库初始化中阻塞执行；舆情分析 stale repair 为 immediate；评论 reconcile/reclassify 为 15 秒；媒体 backfill 与 SAIC-GM relabel 为 25 秒。该 adapter 只属于兼容 `all`，split 角色不调用；删除兼容 adapter 属于后续 P2-E/独立生产变更，不在 P2-D 中完成。

## 7. 新增迁移规范

### 7.1 文件

1. 使用下一个未占用三位编号；
2. 文件名采用 `NNN_lower_snake_case.sql`；
3. 一个迁移聚焦一个业务变化；
4. 已进入共享或生产环境的迁移永不改名、删除或改写；
5. 修正旧迁移时创建新迁移；
6. SQL 必须能在当前生产版本结构上执行。

### 7.2 SQL 安全

推荐：

```sql
ALTER TABLE example
  ADD COLUMN IF NOT EXISTS new_field TEXT;

CREATE INDEX IF NOT EXISTS idx_example_tenant_created
  ON example (tenant_id, created_at DESC);
```

注意：

- 大表新增非空列应先允许空值或提供安全默认值，再分阶段回填；
- 大表建索引可能锁表，必要时设计维护窗口；
- 类型收窄、列重命名和删除字段需要兼容期；
- 回填必须按租户、批次和可恢复检查点执行；
- 不在迁移中调用不稳定外部 API；
- 不把生产客户特定数据修复混入通用结构迁移。

### 7.3 reset 迁移

reset 迁移可能清空、重建或覆盖数据。执行前必须：

1. 明确目标数据库；
2. 生成并验证可恢复备份；
3. 阅读完整 SQL；
4. 记录受影响表和预计行数；
5. 在副本数据库演练；
6. 获得明确的生产变更授权；
7. 设计并审查独立、目标固定、可审计的 Maintenance 工作流；
8. 由第二人复核目标、谓词、备份和回滚材料后再另行授权执行。

P2-D 主线代码当前没有通用 reset 执行器；`ALLOW_RESET_MIGRATIONS=1` 会 fail-closed，不会执行 reset。不要通过直接 `psql`、改迁移器、伪造 `schema_migrations` 或恢复旧入口绕过该边界。

## 8. 备份

### 8.1 数据库

推荐自定义格式：

```bash
pg_dump \
  --format=custom \
  --no-owner \
  --no-acl \
  --file=onstarvoice-$(date +%Y%m%d-%H%M%S).dump \
  "$DATABASE_URL"
```

验证备份可读：

```bash
pg_restore --list onstarvoice-YYYYMMDD-HHMMSS.dump | head
```

生产备份至少记录：

- 创建时间与时区；
- 源主机、数据库名和迁移版本；
- 文件路径、大小和校验值；
- 对应 Git 提交；
- 保留策略；
- 最近一次恢复演练结果。

### 8.2 媒体

数据库备份不包含 `MEDIA_DIR`。应独立备份：

```bash
tar -czf onstarvoice-media-$(date +%Y%m%d-%H%M%S).tar.gz \
  /opt/onstarvoice/media
```

实际路径以生产 `.env` 为准。恢复时数据库记录与媒体文件应来自一致时间点。

## 9. 恢复与演练

不要第一次在生产事故中验证备份。每次演练使用带 release ID 的唯一新库名，例如 `onstarvoice_restore_<release_id>`。先只读确认 `pg_database` 中不存在该名称；若已存在就停止并换新名称，禁止用固定库名加 `dropdb --if-exists` 删除以前的演练/事故证据。创建空的新验证库后，才使用 `pg_restore --exit-on-error --clean --if-exists --no-owner --no-acl` 恢复指定备份；这里的 `--clean` 只能指向刚创建且确认为空的验证库，绝不能指向生产库。

这里的 `postgres` 是执行受控恢复的管理身份，`onstarvoice` 是恢复库所有者和
应用登录角色。已有环境若使用其他已确认的独立角色，应同时替换 `--owner`、
`--role` 和隔离环境的连接串，不要只改其中一处。

验证：

```sql
SELECT now();
SELECT count(*) FROM schema_migrations;
SELECT version, applied_at
FROM schema_migrations
ORDER BY applied_at DESC
LIMIT 10;
```

恢复源已经完成 P2-D adoption/067 时，再额外验证治理元数据；当前 066 生产库还没有这些列和表，不要直接运行：

```sql
SELECT version, applied_at, checksum_sha256, checksum_recorded_at
FROM schema_migrations
ORDER BY applied_at DESC
LIMIT 10;

SELECT task_id, task_version, run_kind, status, source,
       started_at, finished_at, error_code
FROM maintenance_runs
ORDER BY started_at DESC
LIMIT 20;
```

再使用隔离环境连接恢复库，检查登录、租户、内容、任务和工单。确认无误后才能
制定生产恢复切换。

## 10. 租户复制与数据修复

“把客户租户复制到测试租户”属于一次性受控数据操作，不是普通管理端能力。
安全步骤：

1. 备份整个生产库；
2. 明确源租户和目标租户 ID；
3. 列出所有包含 `tenant_id` 的关联表；
4. 决定目标租户现有数据是保留、归档还是覆盖；
5. 为主键、外键、唯一键建立 ID 映射；
6. 不复制密码、会话、Agent Token、激活码、SMTP/LLM 密钥；
7. 不把源租户 Agent 或命令直接绑定到目标租户；
8. 在事务或隔离副本中执行；
9. 按表核对数量和抽样内容；
10. 验证源租户数据未变化；
11. 保存操作清单和回滚点。

直接修改 `tenant_id` 会破坏隔离和外键关系，禁止作为快捷复制方式。

## 11. 常用只读检查

### 11.1 当前迁移

```sql
SELECT version, applied_at
FROM schema_migrations
ORDER BY applied_at DESC;
```

已经完成 P2-D adoption/067 的数据库再运行：

```sql
SELECT version, applied_at, checksum_sha256, checksum_recorded_at
FROM schema_migrations
ORDER BY applied_at DESC;
```

### 11.2 表和大小

```sql
SELECT
  schemaname,
  relname,
  pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

### 11.3 长事务

```sql
SELECT
  pid,
  usename,
  state,
  now() - xact_start AS xact_age,
  left(query, 200) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

### 11.4 连接数

```sql
SELECT state, count(*)
FROM pg_stat_activity
WHERE datname = current_database()
GROUP BY state;
```

所有生产诊断优先使用只读查询。执行 `UPDATE`、`DELETE`、`TRUNCATE`、
`DROP`、直接改任务状态或跨租户复制前，必须另行审核和备份。

## 12. 发布验证

迁移的连续执行、并发与幂等性只在隔离数据库预演，不在生产发布后通过再次执行写入入口验证。P2-D 主线代码未来获批部署后应先运行 Maintenance `verify`，再只读查询 `schema_migrations`、`maintenance_runs` 与关键计数，并同发布前冻结清单比较；当前生产尚无该 CLI，仍只能使用现有只读 SQL 和启动日志。两种口径都不得通过 `migrate` 伪装只读验证。

应验证：

- [ ] 启动日志没有数据库或 migration 错误；
- [ ] `verify` 或等价只读 SQL 证明所有已要求迁移都有非空、匹配的 checksum；
- [ ] 只有迁移明确进入白名单时，目标版本才新增到 `schema_migrations`；无迁移批次没有新增登记；
- [ ] allowlisted Maintenance task 的结果写入 `maintenance_runs`；只有三个固定 legacy once bridge 可同步保留/写入旧 marker，其他新任务没有向 `schema_migrations` 写 marker；
- [ ] SAIC-GM relabel 没有 `MAINTENANCE_TASK_PARTIAL_FAILURE` 或 prior running/failed；如有，长期进程保持停止，未自动重跑或启动旧 `all`，已恢复任务前整库备份并确认 ledger/业务数据同步回退后再重新授权；
- [ ] 服务能启动并通过 `/api/health`，且已单独核对 PM2、数据库、日志和业务状态；
- [ ] 新字段在旧代码路径下兼容；
- [ ] 两个租户的隔离测试通过；
- [ ] 任务、内容、评论、工单等关键计数无异常跳变；
- [ ] 持久化媒体仍可访问；
- [ ] 未意外执行 reset 迁移。

## 13. 已知风险

- 应用层租户隔离依赖每条查询正确携带 `tenant_id`；
- 兼容 `all` 仍把受锁迁移与应用启动耦合，错误迁移或未显式 adoption 的旧 checksum 会阻止启动；
- SQL 事务能回滚当前迁移，但不能自动回滚外部文件或已经执行的历史发布；
- reset 迁移具有破坏性；
- 数据库与媒体分开备份可能产生时间点不一致；
- `schema_migrations` 的版本与 checksum 只证明登记和当前字节锚点，不证明业务数据语义正确；首次 v066 adoption 也不能证明历史实际执行字节；
- `MAINTENANCE_OFFLINE_CONFIRMED=1` 和 advisory lock 不能自动证明旧 API/Worker/migrator 或外部写入已停止；
- legacy import 的非“固定文件缺失” failed 或遗留 running 要求恢复任务前整库备份，不能靠手工改 ledger/marker 或直接重试恢复一致性；
- SAIC-GM once 的任何 prior failed/running 同样要求保持停机并恢复任务前整库备份，不能回滚代码后启动旧 `all` 绕过新门禁；
- 一次生产备份存在不等于可恢复，必须做恢复演练。
