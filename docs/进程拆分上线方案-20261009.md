# 进程拆分（split 拓扑）上线方案 — 2026-10-09

> 分支：`refactor/arch-process-split-20261009`（基于 `main@4581e2e`）
> 性质：解除 P2-C 留下的 split 发布阻断，把生产从单进程 `all` 切到 `api + scheduler + ai-media` 三进程。代码层面改动很小，主要是归属、清单、PM2 配置与演练证据。
> 部署状态：**尚未部署**。生产切换需要用户点名主机后执行 `deploy/deploy.sh`。

## 1. 为什么现在做

生产一直是一个 Node 进程承担 HTTP、调度器和 AI 处理。采集写入高峰时，看板查询、Agent 心跳和 AI 标注都挤在同一个事件循环和同一个连接池里；09-29 看板繁忙、心跳语句读十万页等问题都发生在这个共享点上。P2-C 已经把三个角色的入口、PostgreSQL 角色锁、PG NOTIFY 唤醒和优雅 drain 写好并通过隔离库测试，只差四个「只在兼容模式跑」的启动修复没有 split 归属，以及门禁脚本硬编码拒绝 split。

## 2. 改了什么

### 2.1 启动修复的归属（`server/runtime/ai-media-runtime.js`）

| 任务 | 原来 | 现在 | 依据 |
|---|---|---|---|
| 评论重处理 + 一次性安全语义重分类（每 60 秒） | 仅 `all` | ai-media，两种拓扑都跑 | `reprocessPendingComments` 持数据库处理者租约；重分类由 `schema_migrations` 标志守住 |
| 近 24 小时封面/正文图回填（启动后 25 秒一次） | 仅 `all` | ai-media，两种拓扑都跑 | 查询条件天然幂等（只补 `cover_local` 为空的） |
| 话题剖析卡住清理 | 仅 `all` 启动时把全部 pending/running 置 failed | 新增周期清扫：ai-media 启动 90 秒后、之后每 5 分钟，把 **updated_at 超过 30 分钟未推进**的剖析置 failed；兼容模式仍保留启动即全清 | 剖析在 API 进程里跑，每个阶段写 progress 刷新 updated_at；split 下 ai-media 不能把 API 正在推进的剖析当成死的 |
| 上汽通用历史重判 | 仅 `all` | 仍仅 `all` | 历史一次性、跨全部租户，生产标志早已写入；独立 worker 不应再碰 |

`failStaleAnalyses` 新增 `{ olderThanMinutes }` 参数；不传即原来的启动收尸行为，错误文案分别为「服务重启导致剖析中断」与「剖析超过 N 分钟未推进,已自动终止」。

### 2.2 清单与门禁

- `deploy/process-topology.production.json` → split：`onstarvoice-api` / `onstarvoice-scheduler` / `onstarvoice-ai-media` 各 1。
- 新增 `deploy/process-topology.compatibility.json`（单进程 `onstarvoice`）作为回退清单。`process-topology.split.candidate.json` 暂时保留以免 CI 现有步骤找不到文件。
- `scripts/check-process-topology.mjs`：split 与 compatibility 都视为可部署（仍拒绝混合、多 `all`、重复执行权、角色数不对）。**此文件与 `.github/workflows/ci.yml` 的修改被本机自动模式拦下（判定为改 CI 门禁），需要用户批准后再改**；在此之前 `tests/process-topology-contract.test.mjs` 的 2 个用例与 `deploy.sh` 的预检都会失败。

### 2.3 PM2 与发布脚本

- 新增 `deploy/ecosystem.config.cjs`：读取清单生成 PM2 应用，每个进程显式 `PROCESS_ROLE`、`NODE_ENV=production`、`kill_timeout=35s`（给 30 秒 drain 留余量）、锁竞争失败时指数退避；split 角色额外带 `PG_DATABASE_INSTANCE_COUNT=3`、`PG_POOL_MAX=30`（`server/db/pool.js` 要求独立角色必须声明实例数；30÷3=10，与原单进程默认预算相同）。PM2 设的环境变量优先于 `.env`。
- `deploy/deploy.sh`：先本地跑两份清单预检 → **核对线上 `.env` 的每个键本地副本都有，缺一个就停**（10-09 覆盖事故的直接防线）→ 构建 admin → 同步 server/admin/images 以及 `deploy/` 下三份文件 → 覆盖前在线上留 `.env.before-deploy-<时间戳>` 备份 → 远端 `npm install` + **迁移只在此跑一次** → 只停掉两份清单里有名字的 PM2 进程（`onstarvoice` 与 split 三个；不按前缀删，避免误伤同机其它应用），等退出、释放角色锁 → `pm2 start ecosystem` → `pm2 save` → 轮询 `/api/health/ready` 最长 60 秒，非 200 则打印日志并退出 1。
- 回退：`DEPLOY.md` 8.1，用 `PROCESS_TOPOLOGY_MANIFEST=…compatibility.json` 起单进程。

### 2.4 顺手修的

- `tests/server-cron-runtime.test.mjs`：10-08 加月报定时任务后没更新的两条断言（9 个调度任务、11 个合计）。
- `tests/server-capture-cloud-contract.test.mjs`：状态集合搬家后改为核对领域模块源码。

### 3.3 `all → split → all` 演练（新库 `onstarvoice_test_drill_20261009`，`NODE_ENV=production`，端口 3123）

| 步骤 | 结果 |
|---|---|
| 迁移一次 | ok |
| 起 `all` | 1 秒内 ready；角色锁 2 把（scheduler+ai-media 同一会话）；SIGTERM 后 rc=0，锁 0 |
| 起 api/scheduler/ai-media | 1 秒内 ready；api 无锁且无 Cron 日志；scheduler/ai-media 各持本角色锁并各自启动 Cron；ai-media **没有**执行启动收尸 |
| 第二个 scheduler | rc=1，`process-role lock is already held: scheduler`，原锁仍 2 把 |
| 周期清扫 SQL | 预埋两条 running（45 分钟前 / 刚才），`failStaleAnalyses({olderThanMinutes:30})` 只置 failed 1 条 |
| SIGTERM 三进程 | 各 rc=0，锁 0 |
| 回到 `all` | ready；启动收尸把 2c 留下的那条新 running 置 failed（符合兼容语义） |
| ecosystem 渲染 | production → 三进程；`PROCESS_TOPOLOGY_MANIFEST=compatibility` → `onstarvoice:all:index.js` |

未验证的：真实 PM2（本机未装）。

生产预检（10-09 13:08，只读）：Node 18.20.8、PM2 6.0.14（支持 `.cjs` 配置）；PostgreSQL `max_connections=100`、当时 13 个会话、库 5150 MB；**内存 1.6 GB、无 swap、可用约 640 MB**，单进程跑一小时 RSS 206 MB；本机实测三角色空闲 RSS api 121 / scheduler 138 / ai-media 122 MB（单进程 138 MB），拆分后预计合计比现在多约 260 MB。据此把 PM2 内存上限定为 api 350M / scheduler 260M / ai-media 300M（原单进程 400M）。单进程自 12:05 起 restarts=17 是 11:42 事故崩溃循环加人工重启的累计，12:05 后无重启。这台机器内存是硬约束，长期应考虑把 ECS 升到 4 GB。

## 4. 生产切换步骤

1. **`server/.env.production` 已是线上那份**（用户 10-09 12:05 拷回主工作区，27 键，含 `PROCESS_ROLE=all`、`PG_GENERAL_WAIT_MS`）；`deploy.sh` 现在还会在发布前核对键覆盖。`PROCESS_ROLE` 留在 `.env` 里无妨，PM2 注入的值优先。

5. 发布后核对（DEPLOY.md 5.1）：三个进程 online、没有残留 `onstarvoice`、scheduler/ai-media 日志各持本角色锁、`/api/health/ready` 200、`SELECT count(*) FROM pg_locks WHERE locktype='advisory'` 为 2、Agent 心跳正常、观察至少 11 分钟覆盖 1/5/10 分钟调度周期。
6. 出问题且确认是进程拓扑而非代码问题 → DEPLOY.md 8.1 回退到单进程。

## 5. 明确未做

- P2-D：迁移专用锁与 checksum。现在迁移仍只由 `deploy.sh` 在起进程前串行跑一次，不能并发跑两个迁移进程。
- 健康端点只在 API 进程；scheduler/ai-media 的健康靠 PM2 状态和日志。
- 三进程的连接池预算暂按 10/10/10 平分；若观察到 API 进程 general 闸口排队，再按角色调 `SPLIT_DATABASE_ENV`。
- 周期清扫阈值 30 分钟是经验值：剖析每个阶段都会刷新 updated_at，单阶段超过 30 分钟不推进基本就是挂了。
