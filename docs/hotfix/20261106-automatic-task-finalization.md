# 任务终态后的自动收尾修复

分支：`codex/fix-task-finalization-20261106`，基于已发布的 0.4.30 与发布记录提交 `8173bc9`。本文记录候选修复，不代表生产节点已经安装或现场恢复。

## 现场与原因边界

11 月 6 日晚，用户报告 Edge「计算器」的 ibuick 任务侧栏显示已结束，但调试连接与旧采集页面仍保留。22:18 的只读生产核验显示，该旧执行已交接给其他节点；停止核对连续 8 次返回 `checkpoint_reports_pending`，第三次后出现人工检查提示。

该原因同时涵盖：持久进度队列尚未排空、队列身份无法确认，以及退役回执尚未证明上传完成。因此不能仅凭截图或服务端原因码断言仍在采集，也不能把 pendingTabs=0 当作数据已安全上传。真正的本地队列与内存上传状态没有通过受支持接口读取，本次不把模拟复现冒充现场根因已确认。

0.4.30 的后台队列检查与此前基线 `3051664` 相同；sidebar 退役/最终补报链路亦没有在下午发布中直接改动。确认的是这条链路存在可独立复现的缺陷，尚不能据此判断下午发布与现场卡住之间的因果关系。下午验收没有覆盖此类真实任务终态后的收尾过程。

## 修复内容

1. **合法队列更新不再被判身份未知。** writer 设计为同一轮次复用 storageKey、更新 revision；reader 原先却要求 key 后缀等于新 revision。现在允许合法原位更新，仍核验完整 request/attempt/id、revision 和 checkpoint，坏行或读失败继续阻止关闭。
2. **持久状态回执与慢浏览器清理解耦。** 首次终态必须先完成 request/ledger 持久化与清理重试调度，再确认写入；资源清理推迟到下一事件轮执行。已持久终态的同 request/attempt checkpoint 重放可直接收到 `accepted:false, reason:terminal`，避免被慢清理所占的 mutation 队列拖过 10 秒通信期限。它不产生关闭证明、不释放资源、不修改新轮次。
3. **补报按任务和轮次隔离。** 退役与最终补报只等待自己的 requestId + attemptId，其他任务或后续轮次仍保留各自的队列。启动时的全局扫描保留，删除仍需要现有明确确认/终止拒绝和 revision 对账。
4. **退役回执丢失后自动重试。** 无上传队列分支此前在三次发送失败后保留 retired 标记，却不再发最终回执。现在自动重试并复用有期限的消息发送，固定旧轮次身份；未退出的生产者、上传失败、阻塞队列和本轮未确认数据仍不能声明已冲刷完成。

服务端人工升级规则、关闭证明、身份隔离、采集结果、采集计划和生产数据库均未修改。本次不通过隐藏提示、丢弃未确认数据或伪造“页面已停止”解决卡住。
