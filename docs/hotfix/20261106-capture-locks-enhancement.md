## 1. 命令回执与心跳的数据库锁顺序

旧回执路径先持有父任务行锁，再等待 Agent 执行槽；心跳路径先持有执行槽，再投影父任务。并发时形成互相等待。生产日志中的 advisory lock 第一键与 `capture_agent_execution_slot` 一致。

回执路径现按以下顺序取锁：编排控制锁 → Agent 执行槽 → Agent 授权重查 → 父任务 → 子任务 → 命令。保留控制互斥、授权检查、租户隔离和回执幂等。没有放宽锁超时或取消并发保护。

真实 PostgreSQL 并发回归通过持有心跳执行槽、发起两个节点的回执、再运行实际父任务投影来复现该顺序冲突。基线返回 503；修复后两个回执均成功且重复回执只产生一次事件。另覆盖槽忙时完整回滚、释放后重试、等待中撤销授权、跨租户命令拒绝。

该修复针对已复现的锁顺序冲突。它不证明生产中所有任务行锁等待都已消失；上线后的锁等待量和 5xx 趋势仍需验收。

## 2. 增强只补未完成阶段

增强调用内保存已确认的正文和博主阶段结果，评论失败后复用这部分结果并合并已采到的评论。缓存绑定记录、目标作品、任务及采集配置，只在当前增强调用内使用；后续巡查不能把旧快照当作本轮结果。

重试仍打开并验证目标页面，保留安全检查、取消、作品身份校验和评论提交保护。成功的正文/博主结果先保存，但整条记录在评论未完成时仍保留失败状态。

- 同一记录的评论阶段最多启动两次，内部页面恢复与外层补采共享次数。
- 从首次额外重试开始计算累计 10 分钟的重试窗口，并把评论请求时长限制在剩余预算内。
- 首次采集保持原配置。10 分钟不是整个批次的硬时限，也不截断已在执行的页面操作。

## 3. 阻止耗尽后重新跑整个关键词

增强重试耗尽时上报明确的 `ENHANCEMENT_RETRY_EXHAUSTED`，保留未完成记录、失败阶段和停止原因。关键词检查点及云端工作项保留失败结果。

弹性队列、旧跨节点调度、值守恢复均识别该终止结果，不自动启动新一轮完整关键词采集。安全验证、取消和未确认停止优先级不变；操作员仍可主动点击“重试失败关键词”。

真实数据库回归确认：一个增强耗尽的执行结束后，父任务为 `completed_with_failures`，另一空闲节点不会领取该关键词，不新增第二个 create 命令；值守恢复不创建恢复任务；显式手动重试后能重新领取。
