# 评论回执积压导致负面巡查等待派发

## 根因与线上证据

2026-09-16 早上的小红书、抖音各 13 个关键词采集项已完成，负面巡查仍在等待派发。两个计划均启用。

评论回执的领取条件使用 `comment_workflow_updated_at = $3::timestamptz` 防止旧任务覆盖新回执。PostgreSQL 时间戳保留微秒，`pg` 默认将其解析为只保留毫秒的 JavaScript `Date`。例如线上 `2026-09-08 21:35:47.649821+08` 经过解析后变成 `2026-09-08T13:35:47.649Z`，原值与领取参数不相等。未成功领取的回执被跳过，后台重复扫描仍无法消化积压。

当时全局评论待处理量为 1,028（1,027 queued、1 failed），超过负面巡查准入上限 1,000，触发 `post_processing_count_high_water`。此限制作用于两个平台，导致采集结束后负面巡查一起等待。

本次人工恢复已通过正常回执处理流程消化 100 条，全部成功，将积压降至 928。正常派发随后恢复。最后两个技术超时项重试完成，线上父任务现为小红书 29/29、抖音 22/22，均 completed。原线上服务尚未包含本修复，最后复查仍有 928 条评论回执待处理；任务完成与评论积压清空是两个独立结果。

## 修复范围

- 分支：`codex/hotfix-comment-receipt-precision-20260916`。
- 从当前生产发布清单提交 `c96e7dd6d40ae0b1d0a6157f28c859ece836028d` 建立独立工作目录。已核对线上 `comment-workflow.js` 和 `capture-cloud.js` 文件哈希与该提交一致。

- 保留全局处理租约、逐回执领取令牌、精确版本校验、重试退避、队列宽限期和每批最多 25 条。
- 无数据库迁移、全局日期解析器修改、准入阈值调整或 Extension 变更。

## 验证

使用新建的本地隔离 PostgreSQL 17.9 测试库，未在生产库运行测试。

新增 `tests/integration/postgres/comment-workflow-receipts.integration.mjs`，调用真实回执处理器及真实负面巡查派发流程，验证：

1. queued、租约过期的 running、重试到期的 failed 均能处理含微秒的回执，毫秒整值同样正常；评论实际入库，重复处理不会新增评论。
2. 有效租约、未来重试时间和队列宽限期仍阻止提前领取。
3. 候选查询完成后，将真实数据库版本从 `.123456` 更新为 `.123457`；旧候选无法领取，下一次处理保存新内容。
4. 26 条积压分为 25 条和 1 条处理，批次上限有效。
5. 测试环境将容量阈值设为 1，真实派发先因评论积压受限；回执入库、容量释放后，同一待派发项通过正常流程生成持久化命令。测试结束恢复环境设置。

- Node 24.12.0 和生产兼容运行时 Node 18.20.8 全量 Node 回归：各 2,525/2,525 通过，Extension 快照检查通过。
- 既有负面巡查公平派发、结果重放、无人值守巡查 PostgreSQL 集成测试：64/64 通过。
- 修改文件的 Node 24/18 语法检查、仓库卫生检查及差异空白检查通过。
