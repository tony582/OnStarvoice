# 无人值守自愈方案（2026-11-07）

分支：`codex/feat-unattended-self-heal-20261106`，基于 0.4.31 候选 `fcedca6`（含停止确认收尾修复）。

## 目标

一个关键词算完成的条件：搜索完成，并且搜到的每条帖子都落在以下三种结果之一：

- 已完整采集并入库；
- 平台确认已删除或不可见，记为不可用；
- 被筛选规则排除。

失败只留给机器无法自证的情况，包括账号掉登录、平台验证码，以及所有健康节点都试过仍失败的帖子。其余情况一律自动换节点处理，不等人。

## 现状证据（生产只读，11-07 10:50）

- **失败集中在 Windows 节点。** 10 天内采集增强耗尽 10 次，9 次在 Windows 节点：小红书木星/火星、抖音地球/月球。
- **近 7 天工作项成功率差距明显：**

  | 平台 | Windows 节点 | macOS 节点 |
  |---|---|---|
  | 小红书 | 木星 20/44，火星 8/27 | 88–97% |
  | 抖音 | 地球 30/142，月球 26/102 | 85–88% |

  手机补详情失败也集中在地球（41 次未入库）和土星（42 次指令过期）。
- **今晚的批次：**
  - 小红书 3 个失败词都在 Windows：安吉星（火星，21 帖未完成）、至境哨兵（木星，12 帖）、别克APP（木星，2 帖）。
  - 抖音 4 个失败词：3 个在地球/月球，1 个在西瓜。
- **机制缺口：**
  1. 帖子级失败只在原节点重试，用完即终态（0.4.30 起），不会交给别的节点。
  2. 自动领活没有节点健康度，坏节点照常领活。目前只有手动重试弹窗会按健康度排序。
  3. 服务端数据库忙（`DbCapacityError`）时，上传结果被标成不可重试，扩展立刻把记录记为失败，批次结束后也不会自动补传。
  4. 手机补详情只要没入库就直接"需要处理"，不重试，也不换节点。
  5. 补采时间预算用完时，没来得及试的帖子被统计成"打不开页面"，误导排查。

## 改动

### S1 节点×平台健康度（服务端）

**隔离条件**：同一节点在同一平台上同时满足以下四条，就暂停领取该平台的自动工作。

1. 近 72 小时最近 10 次已结束的尝试中，至少有 6 次有效样本。人为取消、换代接力、抖音空结果不算样本。
2. 成功率低于 50%。
3. 最近一次不是成功。
4. 同平台其他节点近 6 小时成功率比它高 30 个百分点以上。这一条保证平台整体出问题时不会把所有节点都关掉。

**探测与恢复**：被隔离的节点每 60 分钟可以领一条探测任务，探测成功就立即恢复。

**兜底**：工作项等待超过 20 分钟、没有其他节点领走时，被隔离的节点也可以领，避免没人做。

**作用范围**：关键词、负面巡查、关注内容的弹性领活，以及手机补详情派发。其他平台不受影响。

**回放验证**：按这套规则回放近 10 天数据，地球/月球约 170 次失败尝试会被挡下，macOS 节点基本不受影响。

### S2 帖子级换节点补采（扩展 + 服务端）

1. 采集增强耗尽时，扩展上报失败帖子的作品号和链接，作为补采目标。
2. 服务端收到后，在有补采额度时，不再把关键词记为失败，而是记为可接力，并附上补采目标。领活规则本来就会排除上一次的节点，所以补采会换节点。
3. 新节点（需新能力标记）领到这类工作项后，跳过搜索，只打开这些帖子补采详情和评论，然后按原步骤上报完成。
4. 旧版节点不会领补采任务，避免误把整个词重搜一遍。
5. 每个关键词最多换节点补采 2 次。仍失败的帖子保留为失败，并写明每个节点的原因。

### S3 上传失败自动重传（扩展 + 服务端）

- **服务端**：数据库忙、评论处理排队这两类结果改为可重试；整请求的数据库忙返回 503。
- **扩展**：
  - 遵从服务端的"可重试"标记，把 503 和"数据库忙"视为暂时失败。
  - 流式上传对这类失败延长退避重试。
  - 运行结束前对可重试的失败记录再补传一轮。

### S4 手机补详情自动重试（服务端 + 扩展）

- **自动换节点**：没入库且不是登录或验证码原因的，自动排回队列，排除已失败的节点，最多 2 次。指令过期同样处理。
- **转人工**：2 次都失败，或登录、验证码原因的，才进"需要处理"。
- **留证**："已离开目标作品"时记录落地页的作品号和页面类型，便于判断是被跳转还是串号。

### S5 失败归类修正（扩展）

预算用完而没尝试的帖子归类为"预算用完未尝试"，不再记成"打不开页面"。它们会进入 S2 补采。

### S6 收尾修复小瑕疵（扩展）

退役回执被后台明确拒收后停止重发。

## 不做的事

- 不放宽单节点重试预算。放宽会回到下午之前长时间重复采集的问题。
- 不整词换节点重搜。
- 不把未入库的结果改成成功。完成必须有入库回执。

## 验收

- 单元测试和 PostgreSQL 集成测试覆盖每条新规则，包括失败路径：
  - 坏节点被隔离，探测成功后恢复；
  - 平台整体故障时不隔离；
  - 补采换节点后关键词转为完成；
  - 补采两次仍失败才终态；
  - 旧节点不领补采；
  - 数据库忙重传；
  - 手机补详情换节点重试。
- 全量 Node 回归和 CI 全绿。
- 上线后连续观察 3 轮日常巡检，标准是"需要处理"只剩登录或验证码类，且每个失败帖子都有去向。

## 实施状态（11-07）

S1–S6 已在 `codex/feat-unattended-self-heal-20261106` 实现，版本 0.4.32（含未单独发布的 0.4.31 收尾修复）。

- **S1**：`server/services/capture-agent-platform-health.js`。弹性领活和手机补详情派发都先查健康度；读取超时 750 ms 时放行，不挡领活。指定节点的工作不受隔离。
- **S2**：耗尽时上报 `failedTargets`（最多 200 条）。服务端 `server/services/capture-keyword-repair.js` 把关键词记为 `KEYWORD_REPAIR_PENDING` 并换节点；带 `keywordRepairTargetsV1` 能力的节点跳过搜索，只补这些帖子。同一快照重放不会多算次数。旧节点等满 60 分钟才可领，避免没人做。修复了扩展任务账本和云端快照丢掉 `enhancementFailure` 的问题，这是生产上补采信息为空的原因。
- **S3**：数据库忙在单条同步里返回 `server_busy` 并标记可重试，整请求返回 503 和 Retry-After。扩展在运行结束前分别于 15 秒、45 秒补传可重试的失败记录。
- **S4**：`server/services/capture-discovery/auto-retry.js`。未入库的补详情自动排回队列，排除失败节点 30 分钟，最多 2 次；没有原因的完成快照先等 3 分钟迟到回执。下发未确认（指令过期）同样换节点。重放的终态快照不会二次排队或转人工。迟到的入库回执仍能完成原任务。
- **S5**：预算用完时阶段记为 `retry_budget`。
- **S6**：后台回答 `not_unattended_runner` 时退役回执不再重发，待上传数据照常传完。
- 落地页：「已离开目标作品」的报错带上落地页地址和实际作品号。

验证：完整 Node 回归、PostgreSQL 集成 546/546、发布工具模拟 11/11。发布工具在 `scripts/releases/self-heal-0432/`，替换 11 个文件、新建 3 个文件，重启 api 和 scheduler，不做迁移、不改配置。
