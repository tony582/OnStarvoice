# 手机采集精简：登录只查一次、返回不再核对筛选、作品页不再点「展开」（2026-10-02）

分支：`codex/feat-android-lean-capture-20261002`，基线 `main`（`921279b`）。服务端 1 处入库规则（`9761b7c`），Android Runner `0.2.8` → `0.2.9`（`8950583`）。没有数据库迁移，没有新配置项。用户 2026-10-02 下午确认「改吧，新建分支」。

## 为什么改

用户问：进了首页为什么还要进「我」；每采一条都重新确认筛选似乎没用；只要把链接交给采集器、节点打开链接采集，平台自然知道是否采过，为什么还要读文字。

对照代码和手机 9 天的记录（2026-09-24 至 10-02，474 次任务、1,137 条作品），平均每条作品 44 秒，大部分花在三类「确认」上，而这三类确认从未查出过问题：

| 确认 | 做法 | 9 天里查出过问题吗 |
| --- | --- | --- |
| 每个关键词开始前去「我」页证明已登录 | 读屏、点「我」、等「抖音号 + 编辑主页」、点「首页」、等搜索入口 | 一次「没登录」都没有；这一步自己出错 1 次，另有 60 多次超时失败正死在这一步 |
| 每采完一条，回结果页后重新核对筛选 | 打开筛选面板、读全部分组、关上 | 1,137 条里筛选一次都没变过 |
| 作品页文案折叠时点「展开」，与卡片全文逐字比对；服务端再拿卡片全文和节点采到的正文比对 | 点「展开」（复制链接前后又各重读一次），偶尔点到 #话题 或弹出文案面板 | 作品身份最终由链接解析出的作品 ID 决定（1,428 条发现、820 个作品，重复都靠 ID 认出）；当天上午上传队列堵死也是因为它要求完整文案 |

## 改了什么

### 服务端（`server/services/capture-discovery/`）

| 文件 | 改动 |
| --- | --- |
| `ui-binding.js` | `matchesUiBoundRecord` 不再比对文案。保留作者（去掉一个开头的 @，表情保留）和作品类型（记录 URL 里的 note/video 与手机看到的一致）。作品身份本身由入库时「记录的平台和 external_id 必须等于由链接解析出的候选」保证（`detail-receipt.js`） |
| `repository.js`、`management.js` | 判断已有记录时不再读 `title`、`content` |
| `validation.js` | 只改注释：`titleHint` 是搜索卡片上的文字，仅用于后台展示；仍要求非空、上限 20,000、原样保存（事件内容参与哈希，任何改写都会让已存事件重放时冲突） |
| `web/admin/.../presentation.ts` | `existing_record_identity_mismatch` 的说明改为「作者或作品类型不一致」 |

这个改动只会把原来的「拒绝」变成「接受」，不会产生新的拒绝；Runner 0.2.8 发来的事件形状与哈希不变。所以服务端先部署、Runner 后换，或者反过来，都安全。

### Android Runner 0.2.9

1. **登录只在必要时查。** 登录证明只保存在 Runner 进程内存里（`profile-adapter.mjs` 的 `loginProof`），不落盘：Runner 启动后的第一个任务去「我」页查一次；Runner 自己重新拉起抖音后（`douyin-foreground.mjs` 新增启动计数 `launches`，在发出启动命令前加一）下一个任务再查一次。其它任务只回到抖音首页：已在首页就什么都不点；在别的主标签页就点一下「首页」。每次读屏仍会检查登录和验证提示（`assertDouyinScreen`），出现就停止。去「我」页查失败的不会留下证明，下个任务再查。
2. **返回结果页不再核对筛选。** `returnToResults` 只确认回到了本关键词的结果页（关键词、选中「综合」、没有筛选面板）。搜索后、出错恢复（`recoverResults`）后、接管现有搜索（`adoptCurrentSearch`）时照旧完整核对筛选。
3. **作品页不再点「展开」。** `detailMatchesCard` 是打开作品时和复制链接前后共用的唯一判断：作者必须一致；文案与卡片完全一致即可（已展开、以「收起」结尾的视频文案去掉这个标签后也必须完全一致）；或者是折叠的视频文案（文案节点可点击，以「… 展开」结尾），去掉这个界面标签后可见的部分必须是卡片文案的开头。图文作品仍要求完全一致（它们从来没有折叠过）。删除了展开、文案面板处理和按元素坐标点击的代码（`expandAndVerify`、`readCaptionPanel`、`tapIdNearEnd`、`elementRect`、`tapElementAt`）。

## 已知取舍（用户已确认）

- 没有弹出提示的掉线，要等某次读屏出现登录或验证提示时才会被发现。
- 不是 Runner 自己拉起的抖音重启（人手动重开、抖音崩溃后系统重启它）不会让证明失效。
- 作品页里如果有东西重置了筛选，要到下一次出错恢复或下一个关键词才会发现。
- 节点采到的正文如果不完整，不会再因为文案对不上被拒绝入库（作品 ID、作者、作品类型仍会核对）。

## 审查

发布前用 5 个独立审查方向（作品身份、登录证明、筛选与返回流程、服务端与存量数据、测试质量）审查 `8950583`，每条发现再由另一个审查者尝试反驳。7 条发现中 4 条成立：

- 已展开（以「收起」结尾）的视频文案只要求「可见部分是开头」，会放过同作者、文案恰好以「收起」结尾的另一条作品（两个方向各报一次）。已改回完全一致（`934b7c9`），并补拒绝用例。
- 返回结果页依赖的「选中综合」「没有筛选面板」两项没有测试。已补。
- 任务因屏幕出现登录或验证提示而停下后，内存里的登录证明不会作废，下一个任务仍不去「我」页。这超出用户确认的规则（只在 Runner 启动和 Runner 重新拉起抖音时重查），未改，作为选项交给用户；提示本身每次读屏仍会拦住。

被反驳的 3 条：README 链接的文档不存在（已在工作区）、旧规则下标记的需处理需求无法重算（不是本次造成，且没有影响）、哈希断言只和自身比较（偏弱但不是缺陷）。
