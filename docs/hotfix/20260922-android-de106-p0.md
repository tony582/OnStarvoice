## 会话与稳定性证据

以下时间均为北京时间。调试中实际改变的设置和观测结果分别记录，不把一次配置调整等同于长期修复。

| 会话 | 事实与结论 |
| --- | --- |
| 第一次 | 21:47:41，ActivityManager 记录 `Killing io.appium.uiautomator2.server (adj 0): busy background app`，随后 instrumentation 退出；crash buffer 未见 Java 堆栈。 |
| 第二次 | 使用 `noReset=true`、`fullReset=false`、`autoLaunch=false`、`skipUnlock=true`、`skipLogcatCapture=true`、`mockLocationApp=null`，并设 `waitForIdleTimeout=500ms`。完成一条图文分享复制、marker 替换及原剪贴板恢复；在尝试打开筛选前再次退出，缩短 idle 没有解决稳定性。 |
| 第三次 | 22:18:13 开始，22:35:32 进程被杀，持续 17 分 19 秒；原因是 `10474 is an excessive screen wakelock holder`，与第一次的原因不同。该会话完成了搜索、筛选与列表到详情核对，但不能记为稳定性通过。 |
| 第四次 | 22:38:02 建成，设置 `wakeLockTimeout=0` 后完成下节 UI 闭环。22:40:41 结束核查时会话返回 `invalid session id`、helper PID 为空且无屏幕锁。本次只有约 2 分钟短测，未跨过第三次的 17 分 19 秒观察窗口，不能认定长期稳定性修复。 |

第二次退出后，用户在手机本机完成解锁，未向执行器提供锁屏密码。设备凭据页面与本问题无关，未修改。随后在“手机管理 → 省电优化 → 应用耗电优化”中，仅将 Appium Settings、`io.appium.uiautomator2.server`、`io.appium.uiautomator2.server.test` 三个应用的行内开关由 true 改为 false，并逐项读回确认；顶部全局开关和其他应用未修改。调整后未再观察到 `busy background app`，但第三次仍出现上述 wakelock 终止，不能据此宣称后台限制已全部解除。

第四次通过 GET settings 确认 `wakeLockTimeout=0`、`waitForIdleTimeout=500ms`、`enableMultiWindows=true`、`ignoreUnimportantViews=false`、`allowInvisibleElements=false`。`dumpsys power` 显示 `Wake Locks: size=0`，没有 `UiAutomator2:ScreenKeeper`。手机原有 `stay_on_while_plugged_in=3`、AC 供电状态及 `screen_off_timeout=1800000` 未改动。

## 实际页面与作品身份核对

以下动作由独立 P0 校准脚本完成，不代表生产 Runner 已实现该页面 profile：

1. 自动输入中文“别克壁纸”并提交搜索，综合结果出现 4 张可读作品卡，含标题、作者及相对发布时间。
2. 启用 `enableMultiWindows=true` 后可读取筛选弹窗；点击并读回“最新发布”“一天内”的已选中状态，关闭后列表更新。
3. 第四次从结果列表打开首张图文卡，确认详情完整标题、作者与列表完全一致。
4. 写入并读回一次性剪贴板 marker，点击分享链接，确认新剪贴板已替换 marker。分享文本含当前作者及被截短的文案，复制后详情仍与原作品匹配。
5. 返回原关键词列表，重新打开筛选，确认“最新发布”“一天内”仍选中。

上述证明一次 UI 操作闭环和部分身份线索。分享文案与完整正文不完全相同，已确认有截短；不能据此前缀直接放行，也未证明串帖。第二条作品的 `fullExternalIdentityAccepted=false`，未作为已验证候选接收。本记录不保存剪贴板正文。

另对第二次会话取得的第一条分享短链及用户原有短链分别作 HEAD 核对，两者均返回 302，去除跟踪参数后指向同一官方地址 `https://www.iesdouyin.com/share/slides/7687942022607741007/`。该条作品编号已对上；浏览器补详情尚未实测，也未完成 20 条作品验收。
