# 安卓手机发现：上线范围与剩余验收

更新：2026-09-23。代码位于独立 hotfix；候选版本 0.4.13，尚未推送或部署。候选源码标识以发布产物清单为准。

## 首次上线交付什么

单台 Smartisan DE106、Android 8.1、抖音 40.6.0，USB 接到 Mac。操作者在调度中心创建每批 1–2 个关键词的任务，默认综合排序、一天内；手机自行搜索、翻页和获取作品链接，既有 PC Extension 补详情与评论。常规执行不要求 Codex 或大模型全程操控手机。

这次先交付单手机的小范围试点。任务中断时，系统保护暂停，由操作者确认旧手机会话停止后恢复；不承诺插回 USB 自动续跑。每天 05:30 定时下发、13 个关键词自动编排以及整夜无人值守属于下一交付节点，当前没有接入。

## 调度界面怎样处理断线

- **先确认旧操作已停止：** 接稳 USB 并解锁。在连接手机的电脑上停止旧 Runner，检查原控制会话和手机辅助进程确实停止，再用本机 `close` 命令提交该次检查证据。网页不能用“我已确认”复选框强制解除占用。
- **可以恢复原任务：** 原操作已确认关闭、原时限尚未用完；点击恢复，由服务端签发新的 attempt／revision，历史证据保留。
- **可先排队，等待手机就绪：** 允许提交恢复，但需启动执行器并使手机就绪才会执行；等待仍消耗原时限。
- **原批次时限已用完：** 原任务不能恢复。已经找到的内容保留，需要新建批次继续搜索。
- **本批次已停止：** 停止请求不会被恢复撤销。只停止手机发现时，已有候选仍可补详情；停止整批同时撤销本批的详情需求。

### 本机停稳确认的操作依据

命令和证据格式见 [Runner 停止、断线和重启](../../runners/android/README.md#停止断线和重启)。在该节点实际状态目录运行 `status`、`stop`，等待旧 Runner 退出；不能仅凭进程退出就断言手机已停稳。

检查必须对应 SQLite 中保留的那次手机会话和设备编号。已知 Appium session 应独立核对无效，手机 helper 也必须结束。HTTP 500 或未知响应都不等于会话已关闭。会话状态无法确认时，只能处置已证明专属于本测试节点的 Appium 进程，再核对端口和 helper；不能关闭其他用户会话。

由实际检查人填写 `method`、`evidenceId`、`verifiedBy`、`verifiedAt`，调用本机 `close --evidence-file`；服务端确认 `deviceHeld=false` 后再启动 Runner、刷新调度中心并恢复。不得只修改数据库、删除锁或编造证据。此前真实拔插已证明此路径可以恢复；让普通操作者独立完成新界面与本机检查的组合，仍待现场验收。

## 自动晨巡的后续交付

晨巡上线还需接入定时计划与关键词编排，处理主机重启后的受控启动，提供可识别的异常通知，并验证整夜运行、断线后保护暂停／恢复和登录失效处理。现有 PC 晨巡保持原协议；手机节点只领取手机任务。完成这些功能后再连续进行真实晨巡验收，不用本次手动创建小批次的成绩替代。
