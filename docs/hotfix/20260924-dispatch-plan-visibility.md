# 调度中心计划漏显修复

生产基线为 `79ca6a9`（运行代码包含 `976a0c6`），Extension 仍为 0.4.14。

## 问题

看板先读取最近 100 条任务，再由页面挑出计划模板。2026-09-24 核查时，小红书提前跑和抖音提前跑分别排在 103、106 位，两个仍启用的计划因此从「计划」消失；更早的归档计划也未显示。

## 修改

- 在同一看板只读事务内，从 `capture_orchestration_schedules` 独立读取当前租户的全部计划模板，不受最近任务数量和历史日期限制。
- 最近执行列表排除计划模板，避免重复和占用执行列表名额。维持现有页面接口，页面下次刷新即可显示计划。
- 计划状态、归档时间和下次运行时间来自计划表，保留原模板 ID、排期和执行详情入口。
- 发布仅包含 `server/routes/capture-cloud.js` 和新增的 `server/services/capture-schedule-projection.js`。没有数据库迁移、业务数据变更、Extension 或 Admin 静态资源变更。

## 验证

- 使用生产同版 Node 18.20.8，新增真实 HTTP + 本机隔离 PostgreSQL 回归先在原版复现漏显。
- 修复后，在 350 条新任务之前创建的启用、暂停、归档、结束计划全部可读；默认 100、显式 10 和 200 条执行上限均不挤掉计划，也不产生重复。
- 验证跨租户禁止访问、历史计数不变、完整计划和模板数据逐字段保持不变、没有新增事件或任务指令。
- 新增计划回归和既有历史集成测试：12 项通过。采集云端相关回归：113 项通过。修改的生产模块语法检查通过。

## 发布与回滚

发布前再次核对线上基线文件哈希，保留原文件和新增文件清单。新增服务模块先放入，原子切换路由文件，再重启后端并核对健康和计划页面。回滚恢复原路由文件并重启，无需改动数据库。线上验收另记发布证据。
