# 手机卡片 AI 预筛：先按卡片文字判相关，明显无关的不点开（2026-10-03）

分支：`codex/feat-android-card-prefilter-20261003`，基线 `main`（`5b7081b`）。服务端新增 1 个 Android 控制路由（`a37b52f`），Android Runner `0.2.9` → `0.3.0`（`494a840`）。没有数据库迁移，没有新配置项，没有改扩展和后台。用户 2026-10-03 确认「需要做的，太多噪音了」，并说明「确实需要看文本，否则采集器压力有点大，最好筛一遍再给节点」。

## 为什么改

手机每点开一条作品要约 17 秒（0.2.9 真机实测），复制到的链接再交给浏览器节点补详情。但手机交上来的作品大部分和租户无关：10-02 手机新发现 65 条，AI 标注后 59 条无关，进内容分诊的只有个位数。浏览器那边早就有「采集增强 → AI 精准筛选」：列表阶段先把卡片标题、作者交给服务端相关性预筛，明显无关的不进详情采集。手机没有用上它。

这和 10-02 去掉的「文案比对」不是一回事：那次去掉的是拿卡片文案去核对作品页是不是同一条（作品身份，现在由链接决定）；这次读卡片文字是为了判断值不值得点开（相关性）。

## 做法

沿用浏览器已有的预筛服务（`server/services/relevance-prefilter.js` 的 `prefilterRelevanceBatch`），同一套提示词、阈值、缓存、每日额度和决策记录；手机只多了一个能用设备令牌调用的入口。

### 服务端

| 文件 | 改动 |
| --- | --- |
| `android-control/mobile-tasks.js` | `mobileRelevancePrefilterEnabled(planSnapshot)`：计划的 `captureSettings.autoDetailCaptureAfterListCapture` 和 `enableAiRelevancePrefilter` 都严格为 `true` 才开（就是浏览器的「AI 精准筛选」开关）；没有计划快照的单独试跑一律关 |
| `android-control/leases.js` | 领取和持有中重复领取的任务都带 `relevancePrefilter: {enabled}`，取自子任务的计划快照 |
| `android-control/prefilter.js`（新） | 校验请求（最多 8 张卡；卡片 ID 必须是 64 位小写十六进制，即手机对 `[标题, 作者]` 的 sha256）→ 单独一个短事务核对尝试仍是当前的、设备仍被持有、属于手机工作流，取出工作项的关键词和开关，提交 → 事务外调用预筛：关键词用工作项自己的（不用手机发来的），模式 `conservative`，阈值 0.97，`externalId` 为空（卡片还不是记录，不会去改 `records.business_visibility`），幂等键 `android:<attemptId>:<requestId>`，`taskId / runId / keywordRunId` 记成本次发现运行和工作项，方便按任务查决策 |
| `routes/android-control.js` | `POST /api/capture-cloud/android/agent/prefilter`，与 poll 同一条认证链；所有失败都答 `{ok:false, error, failOpen:true}`：数据库繁忙 429（Retry-After 1）、每日额度用完 429（Retry-After 60）、校验或尝试不对用原状态码、其它 503 |
| `android-control/recovery.js` | 回执统计保留 `prefilterSkipped / prefilterJudged / prefilterUnjudged` |

模型调用可能要 20 秒，绝不能在锁着工作项和尝试行的事务里等（续租会排在后面超时）。集成测试在「模型」挂起时实际续租、领取、`FOR UPDATE NOWAIT` 锁两行都成功；把调用挪进事务后这条测试会失败。

### Android Runner 0.3.0

1. 每读到一页结果，先把本页新卡片（没见过的）按顺序、每次最多 8 张、一次只发一个请求交给服务端，30 秒超时；然后才逐张点开。
2. **只有完全符合扩展的跳过规则才不点开**：`status = ok`、`modelDecision = skip`、`tenantRelevance = irrelevant`、置信度是 0–1 的有限数、没有受保护信号、`executionDisposition = skip_full_capture`，且标题能作为跳过依据（至少 2 个字、不是「无标题」之类的占位文字）。比扩展的写法只会更严，不会更松。
3. **其余一律照常点开**：请求出错、超时、返回格式不对、少了或重复某张卡、计划开关关着。连续 2 次请求失败，或服务端答开关关着，本任务后面不再请求；服务端答了 200 但一张卡都没判出来（模型超时或出错时就是这样）也算一次失败。预筛失败从不结束任务，也不要求关闭设备。
4. 请求前和请求返回后都检查停止；请求挂着时被停止，任务以「已取消」结束，不会再点开卡片。
5. 被跳过的卡片记为「见过」（空页判断不变），不占卡片和链接预算，不算点开失败。
6. 统计多三项：`prefilterSkipped / prefilterJudged / prefilterUnjudged`（只在开关开着的任务里出现）。一键启动窗口的结果行加「AI 跳过 N 条无关」。本机诊断单独一个环（`diagnostics:prefilter`，每次请求一条：张数、耗时、失败码、被跳过的标题和模型理由），`diagnose` 显示最近 20 条和每个关键词的 `aiSkipped`；卡片标题不上传。
7. 没有开关、或没有传预筛的运行与 0.2.9 完全一样：同样的设备操作、同样的统计字段。

### 兼容

- 新服务端 + 旧 Runner 0.2.9：旧版不认识 `relevancePrefilter`，不会调用新路由，行为不变。
- 新 Runner 0.3.0 + 旧服务端：任务里没有开关，不会请求；即使请求，404 也按失败处理、全部点开。
- 所以先部署服务端、等手机空闲再换 Runner。

### 额度

预筛按租户每天 5,000 条（`relevance_prefilter_daily_item_limit`，与浏览器共用；缓存命中也计数）。生产 14 天里单日最多 1,380 条（浏览器）。被跳过的卡片几乎不花时间、也不占帖子上限，所以结果很深的关键词在 15 分钟里最多可能送 100–200 张卡去判断；现在手机计划用「一天内」，多数关键词只有 0–3 条结果，每天增加几十到几百条，额度够用。用完时服务端答 429：手机全部照常点开，浏览器对未受保护的作品推迟补详情（原有行为）。如果手机计划改成更宽的发布时间，要先看每天的决策条数，必要时调高该租户的额度。

## 审查

发布前用 4 个独立方向（跳过安全、Runner 任务生命周期、服务端路由与服务、部署兼容与测试质量）审查 `a37b52f` + `494a840`，每个方向的发现再由另一个审查者逐条尝试反驳。共 12 条发现，其中 5 条成立，合并重复后是 4 个问题：

- **模型故障绕过熔断（中）**：服务端在模型超时或出错时仍答 200、每张卡都是「未判断」，旧代码把它当成功、清零失败计数，于是模型故障期间每页都要白等最多约 28 秒再全部点开，吃掉关键词的时间预算。已改：一张卡都没判出来的回答算一次失败请求，连续两次熔断（失败码 `prefilter_unjudged`），补测试（改动前失败）。
- **共享预筛服务写 jsonb 时可能因截断的表情失败（低，原有问题）**：模型给的理由、证据用普通 `slice` 截断后直接 `JSON.stringify` 写进 jsonb，切在表情中间会被 PostgreSQL 拒绝（22P02），整批决策和缓存丢失，手机和浏览器都按失败放行。不是本次引入、浏览器同样存在，已另开任务修。
- **缓存键不含租户监控范围（低，原有问题，留给用户定）**：14 天缓存按关键词、意图、卡片内容和模型取键；管理员放宽 `brand_business_context` 后，旧的「无关」最多还会被沿用 14 天。浏览器那边记录还在（可重判），手机上被跳过的卡片不会留下记录，所以这段时间里这张卡不会被采到。可选做法：缓存键加入租户范围指纹（会影响浏览器共用路径），或在放宽范围时清空该租户的预筛缓存。未改。
- **额度估算偏乐观（低）**：见上面「额度」一节，已改正文字。

被反驳的 7 条：手机跳过不留记录（这是本次的设计：不点开就拿不到作品链接，用户确认要「先筛再给节点」）；模型要原样回显 64 位卡片 ID（推测，回显错只会让卡片照常点开）；额度会被手机用完（3 条，以现在的「一天内」计划不会发生，且用完也是放行，第 4 条同类发现按「估算偏乐观」成立）；没有测试 30 秒超时和守护进程接线（代码正确，属于缺少回归保护；30 秒超时已补测试，改动前失败；接线在换版后看本机诊断的 `card_prefilter` 记录核对）。

修复后：Runner 262 / 262。
