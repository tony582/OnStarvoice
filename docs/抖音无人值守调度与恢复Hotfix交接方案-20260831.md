# StarVoice 0.4 无人值守、AI、Debug 与小红书原文 Hotfix 交接方案（2026-08-31）

## 0. 文档用途

这是一份给后续 Codex 对话或开发者直接执行的技术交接，不是已经完成的修复，也不是生产变更授权。

目标是修复抖音无人值守任务中反复出现的以下问题：

- 有在线、空闲且兼容的 Agent，但失败词长期没有真实分配；
- 一个账号遇到验证码后，当前关键词甚至整个批次被连带阻塞；
- `source_local_closure_proof_unavailable`、冷却倒计时或终态心跳形成无限等待；
- `SEARCH_FILTER_APPLICATION_FAILED`、`unattended_begin_fence_changed` 等技术故障快速耗尽候选池；
- 管理端显示“正在自动恢复”或“已受理”，但没有新 child、create command、浏览器接管和业务进度；
- `capture_task_debug_busy` 频繁出现，导致一个本可换设备执行的关键词停在原地；
- AI 列表预筛虽然运行，但大量 `need_detail`、低置信度或 fail-open 候选仍直接进入完整详情、评论和作者增强；
- 已判定无关或已跳过增强的基础列表记录仍可能进入正常业务内容视图、计数和后续 AI 队列；
- 小红书把带 `xsec_token/xsec_source` 的搜索结果导航地址当成短时上下文使用，后台却把它当作永久“原文”链接；裸 `/explore/:id` 与回填的历史 token 均可能在已登录账号中返回 `300031`；
- 弱网 Windows 节点在筛选和搜索刚出现结果时被过早判败。

本方案同时写清已经发布但仍需回归的内容，避免后续对话重复修复已完成的 canonical URL、终态防复活和内容分诊性能改动。

## 1. 当前事实基线

### 1.1 2026-08-31 线上故障快照

本次只读观察的父任务：

- 租户：`457e5851-93eb-4446-84e5-eb6ddb871e65`
- 父任务：`6249d04c-c296-49ec-96e0-e570f7fd9d04`
- 标题：`抖音-无人值守-弹性节点 · 08/31 10:23`

当时 6 台抖音 Agent 均为 `0.3.99`，在线、完整心跳新鲜、`taskStateKnown=true`。因此“没有设备接任务”不是设备整体离线。

关键现象：

1. 11:06 左右没有待领取或已确认的 create command；
2. 11:07 调度器曾把“别克壁纸”派给 Windows·地球，随后因 `SEARCH_FILTER_APPLICATION_FAILED` 又退回 `retryable`；
3. “凯迪拉克OTA”和“凯迪拉克车机升级”出现 `DOUYIN_SEARCH_SECURITY_CHALLENGE`；
4. “凯迪拉克车机升级”同时带有 `waitingForSourceClosure=true`，事件原因为 `source_local_closure_proof_unavailable`；
5. “凯迪拉克壁纸”“上汽通用客服”等还出现 `unattended_begin_fence_changed`；
6. 结果不是调度器完全停止，而是“偶发分配 → 快速技术失败 → 退回 → 安全门或候选池继续阻塞”的抖动。

用户后续反馈“当前大量无关内容穿透 AI，且大部分失败是 Debug 问题”。本交接已把 AI、Debug 与小红书原文链接列为三个并列 P0，但不能从截图直接宣称具体占比。实施对话必须重新只读查询该父任务及最近同版本批次：按标准化 error code/Debug 子原因/`businessStarted` 汇总 attempts，并把 `relevance_prefilter_decisions` 与实际详情、评论、作者增强及后置 `ai_result.relevance` 对账，形成修改前基线。

小红书原文问题已经有两条独立现场证据：

- `6a942033000000002102f2fa` 在 12:10 左右由 `Chrome · macOS~成都` 完成详情采集，登录后的网页随后返回 `300031`；
- `6a94c7c3000000002003b809` 在 10:25 左右由 `Chrome · macOS~重庆` 完成详情采集，同一“重庆”Chrome 登录后仍返回 `300031 / Page Isn't Available`；

## 2. 已确认的代码矛盾与根因

### 2.1 安全验证仍被 Extension 标成整批致命

文件：`utils/capture/douyin-search-guard.js`

`createDouyinSearchSecurityChallengeError()` 在 `ba4a4ba` 中仍设置：

```text
securityBlocked = true
requiresManualAction = true
stopBatch = true
fatal = true
retryable = false
keywordScoped = false
```

这与 update manifest 中随当前 0.3.99 版本链展示的 0.3.98 修复说明“验证只隔离当前关键词与当前账号”不一致。即使服务端后来尝试把 item 退回队列，本地 runner 仍按整批致命故障结束，容易留下 `needs_action` child、Debug Session、页面或本地锁。

### 2.2 安全接力策略把本地关闭证明作为无限硬门

文件：

- `server/services/capture-safety-handoff-policy.js`
- `server/services/capture-local-closure-proof.js`
- `server/services/capture-recovery-intents.js`
- `server/routes/capture-cloud.js`

`evaluateCaptureSafetyHandoff()` 在 `sourceLocalClosureProven !== true` 时直接返回 `source_local_closure_proof_unavailable`。严格防双跑的方向是对的，但当前实现把“证明没有到达”与“旧执行仍在活动”混为一谈。

`loadCaptureAgentLocalClosureReuseGate()` 又会以最近的终态 attempt 为 Agent 级复用门。若 `needs_action` 快照持续刷新 `updated_at`，但没有稳定的 `finished_at` 或合格 closure proof，所谓 20 秒静默时间会不断重新起算，导致该 Agent 长期无法领取任何新词。

### 2.3 冷却与关闭等待使用了可被心跳刷新的时间锚点

文件：`server/routes/capture-cloud.js`

以下路径都可能回退到 `updated_at`：

- `loadCaptureAgentLocalClosureReuseGate()` 的 `terminal_at`；
- `elasticRecoveryHoldRemainingMs()` 的恢复锚点；
- `waitingForSourceClosure/sourceClosureBlockedAt` 的重复写入。

终态或 `needs_action` 心跳继续到达时，`updated_at` 会更新。于是 UI 看见的 2 分钟或 20 秒不是单调递减的期限，而可能被每次心跳重置。这正是“冷却似乎无限循环”的主要代码原因。

### 2.4 弹性领取存在队首阻塞

文件：`server/routes/capture-cloud.js` 的 `dispatchNextElasticWorkItem()`。

当前 SQL 先 `LIMIT 1` 选一个 item；选中后才验证 source closure、资源准入和其他门。如果这个 item 暂不可派，函数多处直接 `return null`，而不是继续扫描同一 Agent 可领取的下一个 item。

因此一个 closure-blocked item 可以吞掉一次完整心跳领取机会；多个 item 分别带门禁时，后台看起来像“全部空闲但不分配”。

### 2.5 任何历史 attempt 都会永久排除同一 Agent

弹性领取 SQL 使用 `capture_task_item_attempts` 的存在性排除同一 Agent，不区分：

- 浏览器业务搜索已经真正开始；
- BEGIN 栅栏在启动前变化；
- Debug/DevTools 被占用；
- create command 在打开页面前过期；
- 筛选尚未完成。

于是 `unattended_begin_fence_changed` 等“业务尚未开始”的技术尝试也会缩小该关键词候选池，并增加 `attempt_count`。连续几次启动故障后，明明有可用账号，也可能被历史 attempt 规则全部排除。

### 2.6 筛选验证失败被本地定义为人工致命故障

文件：`utils/capture-sync.js`

`createSearchFilterApplicationError()` 当前设置：

```text
fatal = true
stopBatch = true
requiresManualAction = true
retryable = false
```

但 `SEARCH_FILTER_APPLICATION_FAILED` 实际上通常是页面控件、弱网或验证探针的技术故障，不应要求人工，也不应停止其他关键词。服务端虽有部分防御性归类，但本地 child 和 runner 已经被错误终止。

### 2.7 BEGIN 栅栏变化没有区分“安全拒绝”和“可重建启动”

文件：`background.js`

BEGIN 前后会多次检查本地 unattended lock、任务 owner、替换 Tab 和 Debug Session。任何中间清理或合法 Tab 替换引起的差异，都可能抛出 `unattended_begin_fence_changed`。该错误目前缺少统一的 `businessStarted=false` 证据和不计费语义，服务端容易把它当成一次真实业务 attempt。

### 2.8 `capture_task_debug_busy` 是技术容量信号，不应变成人工批次阻断

文件：

- `background.js`
- `utils/capture/debug-session.js`
- `sidebar/sidebar-logic.js`

“AI Debug”实际是浏览器调试/网络采集通道，不是 AI 模型本身。AI 列表预筛走服务端接口；Debug Session 负责浏览器接管、焦点保持、任务页所有权以及部分完整采集能力。当前命名把两个独立问题混在了一起。

`background.js` 的 BEGIN 目前把以下情况都压成 `capture_task_debug_busy`：

- StarVoice 自己仍有另一个 active session；
- StarVoice 终态任务留下了 stale session；
- 用户在同一 Tab 打开了 DevTools；
- 其他扩展或未知调试者占用了 Tab；
- cleanup 尚未完成但 owner 状态已经丢失。

这些情况需要完全不同的处理，但服务端目前只能把它们当成同一种 Agent 容量错误。并且 `capture-debug` manager 是 Profile 级单会话：同一 Extension 中一个未释放 session 足以让之后所有关键词的 BEGIN 失败。若错误在派发后才被发现，还会生成无业务进展的 attempt，再触发容量冷却和候选排除，所以用户看到的大量 Debug 失败会进一步演变成“不分配”。

正确行为应是：当前 Agent/Tab 技术不可用，当前 item 立即释放给其他合格 Agent；不得停止父任务，也不得自动 detach 用户手工打开的 DevTools。

### 2.9 AI 预筛只完成了第一道列表门，尚未形成业务闭环

主要文件：

- `utils/capture/relevance-prefilter.js`
- `utils/capture-sync.js`
- `server/services/relevance-prefilter.js`
- `server/routes/triage.js`

当前实现不是“AI 完全没挡住”，而是挡住条件过窄、后续闭环缺失：

1. 只有 `modelDecision=skip`、`tenantRelevance=irrelevant`、无保护信号、服务端明确返回 `skip_full_capture` 且置信度达到 0.97（极清晰双低匹配可用 0.95）时，Extension 才真正跳过详情、评论和作者采集；
2. `need_detail`、低置信度、标题不足、模型超时、模型异常及输出不完整全部 `collect_full`；
3. 设计文档中的“详情二筛”尚未落地，因此列表证据不足时不是先取最小正文再判断，而是直接支付完整增强成本；
4. 预筛发生在基础列表记录已经写入本地记录之后。`skip_expensive` 会阻止昂贵增强，但基础记录仍保留；如果业务查询只排除 `records.ai_result.relevance=irrelevant`，尚未完成后置标注或只在 `payload.aiRelevancePrefilter` 中留痕的记录仍可能暂时进入业务视图；
5. 当前每词上限容易按“已发现/已保存基础记录”计算。无关项占满上限后，即使后面还有相关结果，也可能提前停止滚动，造成“无关内容很多、真正相关数量又偏少”的双重问题。

因此不能靠单纯降低 0.97 阈值解决。那会提高误杀风险。需要同时修正：判定阶段、实际处置、业务可见性、目标计数和 fail-open 策略。

### 2.10 小红书 canonical 身份与可打开导航被错误合并

主要文件：

- `server/services/record-store.js`
- `server/routes/triage.js`
- `web/admin/src/pages/workbench/TriageQueue.tsx`
- `web/admin/src/components/shared/RecordDrawer.tsx`
- `utils/capture/keyword-search.js`
- `utils/capture-sync.js`
- `background.js`

`ba4a4ba` 中的 `resolveXhsCanonicalRecordUrl()` 明确把带 token 的 `/search_result/:id` 或 `/explore/:id` 归一化为裸 `https://www.xiaohongshu.com/explore/:id`，并同时写入 `url` 与 `canonical_url`。这适合去重身份，却不适合网页导航。小红书搜索卡片给出的 `xsec_token` 属于短时、会话/搜索上下文相关导航参数；裸 URL 可能立刻返回 `300031`，历史 token 回填后也会过期或失去上下文。

2026-08-31 已对 619 条历史记录做过一次受控 token 回填，备份为 `/opt/onstarvoice/backups/xhs-url-context-backfill-pre-20260831T122653+0800.csv.gz`。该动作证明数据库可以保留参数，但不能刷新参数，也不能把临时 token 变成永久链接。0.4 不得继续以数据回填作为修复策略。

正确模型必须拆成两层：

- `canonical_url`：稳定内容身份，只用于去重、关联、审计和显示；
- `navigation_context`：短时可用的采集端导航上下文，带来源 Agent、获取时间和有效性，不得作为永久公开 href。

管理端点击“原文”时不能再无条件打开存量 `records.url`。应优先向当前在线、与记录来源一致且小红书登录有效的采集 Agent 发出“刷新并打开原文”命令：由 Agent 回到原搜索上下文或按原关键词重新搜索，匹配 `external_id` 后使用当次新鲜卡片链接在该 Agent 浏览器内打开。若无合格 Agent，只提供“搜索定位”降级并明确提示，不能伪装成永久直链。

## 3. 已确定的产品与安全规则

这些规则不再留给后续实现者自行猜测：

1. 验证码最多隔离“平台账号 + 当前关键词 + 当前父任务 occurrence”这一组合；不能隔离整个关键词，更不能停止整个父任务。
2. 同一账号在本次父任务中不得再次执行触发验证的同一关键词；不同、已登录且未尝试过的账号可以接力一次。
3. 原 Agent 在本地自动化已停并释放锁后，可以立即领取其他关键词；安全验证不使用 30 分钟或 2 分钟的整机冷却。
4. 第二个不同账号执行同一关键词时再次触发安全验证，或账号登录失效，才把该关键词转为真正 `needs_action`。
5. 系统不解验证码、不绕过登录、不自动操作安全挑战控件。
6. 筛选未证实时禁止开始采集，但应作为可恢复技术故障，而不是人工故障。
7. pre-start 技术错误不消耗业务 attempt；已经开始搜索或保存结果的执行才进入业务/安全预算。
8. 已完成关键词不重跑；已有持久化结果但增强不完整时显示“部分完成”，不得隐藏保存数量。
9. 命令已受理、下拉已选择、HTTP 200 都不等于恢复成功。必须看到新 attempt、create command、Agent ACK、浏览器接管、`business_progress_at/progress_seq` 推进和最终结算。
10. 抖音“综合/图文”本 hotfix 仍可在同一关键词内串行，但 checkpoint 必须分别记录；接力只恢复未完成 pass，不重跑已完成 pass。
11. `modelDecision` 只是模型意见，只有 `executionDisposition` 才决定浏览器动作。UI 不得把“模型倾向无关但实际放行”显示成“已过滤”。
12. 高置信度无关项不得打开详情、评论或作者页，不进入正常内容分诊、告警、报表和业务保存数量；只保留可审计的候选/判断证据。
13. `need_detail` 只能先采最小详情判断包，二次判定前不得采评论、作者指标或主页；二筛确认相关、仍不确定或命中保护信号后才允许完整增强。
14. 普通候选在 AI 主模型与备用模型都失败时不得无限量 `collect_full`。保留基础证据并进入 `defer_enhancement`；风险/投诉/救援等保护信号仍可完整采集，避免漏报。
15. AI 过滤项不消耗“每词需保留作品数”。系统继续扫描，直到达到相关保留目标、平台明确无更多结果或命中独立的最大扫描/时间安全上限。
16. Debug 占用必须区分 StarVoice active、StarVoice stale、外部 DevTools 与未知 owner；只有可证明属于 StarVoice 已终态任务的 stale session 才能自动清理。
17. 小红书 `canonical_url` 只表示内容身份，绝不再承诺可长期直开；`xsec_token` 不写入 canonical，也不作为永久链接回填。
18. 管理端“小红书原文”必须执行实时解析：在采集端重新搜索并匹配 `external_id`，取得当前导航上下文后在该采集端打开。
19. 原文刷新只能调度到同租户、在线、声明 `xiaohongshuSourceOpenV1` 能力且小红书账号登录有效的 Agent；不得跨租户，也不得把 token 回传给另一浏览器/Profile 使用。
20. 无可用 Agent、重新搜索未命中、账号登录失效、安全挑战或 300031 复现时，返回结构化失败并提供搜索定位；不得自动解验证码、反复刷新、盲目重采或把旧链接标为成功。

## 4. 目标状态模型

### 4.1 失败策略必须结构化

新增一份服务端与 Extension 共用、由契约测试锁定的 failure policy。至少输出：

- `scope`: `attempt | agent | platform_account | account_keyword | item | parent`
- `faultClass`: `prestart_technical | page_technical | platform_safety | login | no_result | user_stop | data_integrity`
- `businessStarted`: boolean
- `attemptCost`: `none | technical | business | safety`
- `retryable`: boolean
- `retryMode`: `same_agent | distinct_account | any_compatible | none`
- `requiresManualAction`: boolean
- `stopParent`: boolean
- `retryAfterMs`: number

首版固定映射：

| 错误 | scope | attemptCost | 自动动作 |
|---|---|---|---|
| `DOUYIN_SEARCH_SECURITY_CHALLENGE` | `account_keyword` | `safety` | 源账号+词封存；不同账号最多接力一次；其他词继续 |
| `LOGIN_REQUIRED` / `AUTHENTICATION_REQUIRED` | `platform_account` | `safety` | 该账号暂停；其他账号继续；通知人工登录 |
| `SEARCH_FILTER_APPLICATION_FAILED` | `attempt` | `technical` | 原页幂等复核一次，仍失败则释放给其他 Agent；不人工、不停批 |
| `unattended_begin_fence_changed` | `attempt` | `none` | 本地清理后重新领取或换 Agent；不计业务次数 |
| `capture_task_debug_busy:self_active` | `agent` | `none` | Agent 保持 busy，item 立即允许其他 Agent 领取；原 session 正常结束后再恢复资格 |
| `capture_task_debug_busy:self_stale` | `agent` | `none` | 验证旧 owner 已终态且上传排空后，仅清理 StarVoice 自己的 session；同 Agent 最多重试 BEGIN 一次 |
| `capture_task_debug_busy:external_devtools` | `agent` | `none` | 不 detach；Agent 暂停领取，item 立即换 Agent，直到心跳明确报告 free |
| `capture_task_debug_busy:unknown_owner` | `agent` | `none` | 保守排除当前 Agent 并换机；不要求用户处理当前父任务 |
| `create_command_expired` 且页面未打开 | `attempt` | `none` | 重新派发，不排除原 Agent，不计业务次数 |
| 明确、稳定的无结果 | `item` | `business` | 0 条正常完成，继续下一词 |
| 用户停止 | `parent` 或明确 item | `none` | 不自动恢复 |

### 4.2 业务状态与本地运行状态分离

不要再用一个 `needs_action` 同时表示业务结论和浏览器是否仍占用资源。

每个 execution/attempt 至少要有：

- `business_status`：业务是否完成、部分完成、可重试或需人工；
- `local_runtime_status`：`active | quiescing | quiesced | unknown`；
- `first_terminal_at`：第一次进入终态/需处理的不可变时间；
- `local_quiesced_at`：runner、timer、Debug Session、任务锁已停止的时间；
- `last_reported_at`：后续重复心跳时间，仅用于观察，绝不能重置冷却或关闭期限。

### 4.3 AI 处置状态必须与模型判断、业务可见性分离

每个候选至少保留四层状态：

- `modelDecision`: `keep | skip | need_detail | null`；
- `executionDisposition`: `skip_expensive | collect_minimal_detail | collect_full | defer_enhancement`；
- `businessVisibility`: `eligible | filtered_out | deferred | audit_only`；
- `enhancementState`: `not_started | minimal_done | full_done | skipped | deferred | failed`。

固定映射：

| 条件 | 浏览器动作 | 业务动作 |
|---|---|---|
| 列表高置信度无关、无保护信号 | `skip_expensive`，不开详情 | `filtered_out`，只保留审计，不计业务保存数 |
| 列表 `need_detail` / 证据不足 | `collect_minimal_detail` | 暂为 `deferred`，二筛后再决定 |
| 详情二筛高置信度无关 | 停止，不采评论/作者 | `filtered_out` |
| 相关、不确定或保护信号 | `collect_full` | `eligible` |
| AI 主备都失败且无保护信号 | `defer_enhancement` | 保留基础证据，异步重判；父任务不因 AI 长时间占住浏览器 |

`filtered_out` 不是删除：`relevance_prefilter_decisions`、候选身份、来源关键词、模型与策略版本继续保留，用于抽检和误杀恢复，但不得混入正常内容分诊。

### 4.4 小红书原文打开状态必须单独建模

每次打开请求至少保留：

- `recordId/externalId/tenantId`；
- `requestedBy/requestedAt`；
- `sourceAgentId/targetAgentId`；
- `resolutionMode`: `fresh_search | fresh_card | search_fallback | none`；
- `status`: `queued | acknowledged | resolving | opened | not_found | login_required | security_blocked | stale_context | failed`；
- `resolvedAt/openedAt/errorCode`；
- 导航参数只存在于发送给目标 Agent 的受控命令和本地运行时，不写入普通审计、前端 JSON 或 canonical URL。

`opened` 只在目标 Agent 已匹配正确 `external_id` 且浏览器完成导航后成立；HTTP 200、command ACK、找到关键词页或生成一个带 token 的字符串都不算成功。

### 5.7 候选池和预算修正

1. 候选排除不再使用“该 Agent 曾有任何 attempt”这一粗条件。
2. `attemptCost=none`：不增加业务次数，不排除同账号；清理完成可重试。
3. `attemptCost=technical`：不增加业务次数；可短暂降低该 Agent 排名，但 item 立即可给其他 Agent。
4. `attemptCost=business`：计入正常业务尝试。
5. `attemptCost=safety`：写入账号+词隔离，并使用独立 `safety_handoff_count`。
6. 排名继续考虑近期技术失败、当日搜索量、物理 host 和共享网络组，但评分只能影响优先级，不能把所有候选过滤为空。
7. 弱网 Windows 可配置物理机/共享 5G 并发上限；这不是修复调度死锁的替代品。

建议冷却初值：

- 安全验证：整机冷却 0；本地 quiesce 目标不超过 15 秒；精确账号+词在本 occurrence 内不再尝试；
- pre-start 技术错误：5–15 秒本地清理；item 同时可被其他 Agent 领取；
- 页面/筛选技术错误：源 Agent 30 秒降权；item 立即可被其他 Agent 领取；
- 明确资源压力：最多 2 分钟且使用不可变期限；
- 离线：按双心跳租约撤销，不用反复滚动冷却。

这些值必须可配置、可观测，但任何心跳都不能重置同一轮期限。

### 5.9 AI P0：从“列表意见”改成“两阶段处置闭环”

主要文件：

#### A. 先把统计口径拆开

每个关键词上报并持久化：

- `discoveredCandidateCount`：列表发现数；
- `prefilterEvaluatedCount`：AI 真正返回有效判断数；
- `prefilterFailOpenCount`：超时、错误或无效输出数；
- `listFilteredCount`：列表阶段过滤数；
- `minimalDetailCount`：只采最小详情用于二筛的数量；
- `detailFilteredCount`：详情二筛过滤数；
- `fullEnhancedCount`：真正完成详情/评论/作者增强数；
- `businessSavedCount`：进入正常业务内容的数量；
- `deferredEnhancementCount`：等待 AI 恢复后再判定的数量。

管理端和 Extension 的“保存 N 条”默认显示 `businessSavedCount`，同时可展开候选、过滤、延后和增强数量。不能再把基础候选行、AI 审计行和业务保存混为一个数。

建议单独增加迁移 `078_relevance_disposition_v2.sql`，不要把它混进调度迁移 077：

- 对 `(tenant_id, business_visibility, created_at)` 和 deferred 待处理项建立部分索引；
- 迁移回填只把已有明确 `skip_expensive/detailCaptureStatus=filtered` 的记录标为 `filtered_out`，不根据标题或旧模型结果猜测性删除/隐藏数据。

#### B. 列表高置信度无关必须真正阻断昂贵路径

6. 保留 `relevance_prefilter_decisions` 与最小候选审计，支持抽检和误杀恢复。

服务端业务查询除了排除 `records.ai_result.relevance=irrelevant`，还必须排除 `payload.aiRelevancePrefilter.executionDisposition=skip_expensive`、`detailCaptureStatus=filtered` 或新的结构化 `businessVisibility=filtered_out`。优先新增结构化字段/列，不长期依赖脆弱 JSON 文本判断。

#### C. 落地详情二筛，不让 `need_detail` 直接完整增强

扩展 `POST /api/relevance/prefilter` 支持 `stage=detail` 与新提示词 `prefilter-detail-v1`。Extension 对 `need_detail` 只采最小判断包：稳定作品 ID、详情标题/正文、标签、作者名、发布时间，以及页面已经提供的 OCR/口播摘要；禁止先抓评论、作者指标和主页。

二筛返回：

- 高置信度无关且无保护信号：`skip_expensive + filtered_out`；
- 相关、不确定或保护信号：`collect_full + eligible`；
- 模型异常：进入 D 节的有界延后策略。

已在列表阶段 `keep` 且高置信度相关的内容不重复二筛，直接完整增强；这样减少 AI 调用，也避免相关内容被二次误杀。

#### D. 把无限 fail-open 改成“保护信号放行 + 普通候选有界延后”

继续使用 DeepSeek 主路由与当前备用模型，但主备都失败时：

- 命中救援、故障、投诉、账号安全等保护信号：继续完整增强；
- 普通候选：保留基础证据，标为 `defer_enhancement`，不在浏览器中无限量完整采集；
- 每关键词允许少量 fail-open 抽样完整采集，用于监测 AI 漏判，默认上限建议为 `min(3, 10% 候选)`，必须由服务端策略下发；
- 延后项进入可观测队列，AI 恢复后先重判；只有判为相关/不确定的项才生成 targeted enhancement command；
- 延后队列不能阻塞父关键词收口，父任务显示“列表完成，增强延后 N 条”，不能伪装成全部增强完成。

这不是简单 fail-close：数据身份和审计仍保留，高风险信号仍放行，普通内容则避免在 AI 故障时把无关数据和浏览器负载同时放大。

#### E. 目标上限按相关保留数计算

AI 过滤和延后项不消耗每词 `postLimit`。继续扫描直到：

1. `businessSavedCount >= postLimit`；或
2. 平台出现稳定无更多结果；或
3. 达到独立 `maxCandidatesScanned`（建议默认 `max(postLimit * 5, 100)`）；或
4. 达到每 pass 最大时长。

达到扫描/时间安全上限但业务保存不足时，结算为“完成但相关结果不足”，展示发现、过滤和保留数量，不能报搜索失败。

#### F. UI 只根据实际处置说话

- `modelDecision=skip + executionDisposition=collect_full`：显示“模型倾向无关，因证据不足/保护规则继续采集”；
- `skip_expensive`：显示“AI 已过滤，未采详情/评论/作者”；
- `collect_minimal_detail`：显示“读取最小详情，等待二次判断”；
- `defer_enhancement`：显示“AI 暂不可用，已保留候选并延后增强”；
- 禁止只读取 `modelDecision` 就显示“AI 已判无关”，也禁止只读取 Extension 100% 就显示完整增强成功。

#### G. 上线前先用真实数据校准，不直接降低阈值

按租户、平台、关键词统计最近真实批次中的 `model_decision`、`execution_disposition`、`server_model_status`、`metadata.failOpen`、后置 `ai_result.relevance` 和实际 enhancement。至少人工抽检：

- 100 条被列表过滤候选；
- 100 条列表放行但后置判无关候选；
- 所有保护信号放行候选；
- 抖音综合与图文分别计算误杀率和无关穿透率。

只有抽检证明误杀可接受后才调整阈值。P0 的首要目标是让已有处置真正生效、补详情二筛和修正 fail-open，而不是盲目从 0.97 降到更激进数值。

## 9. 生产验收标准

### 9.1 必须通过的场景

1. **验证码隔离**：账号 A 的关键词 K 遇验证后 15 秒内 quiesce；A 可领取 K2；K 在 30 秒内交给不同账号 B（存在空闲 B 时）。
2. **不双跑**：任意时刻同一 item 只有一个有效 lease；A 的迟到回报不能改变 B 的 item、结果或父任务。
3. **二次验证**：B 对 K 再次验证后，仅 K 转人工，其他关键词继续。
4. **筛选弱网**：页面结果先出现、筛选控件后稳定时不误判；筛选始终无法证实时只释放 K，不停批、不人工。
5. **BEGIN 竞态**：Tab 合法替换或 stale group 清理不会消耗业务 attempt；可自动再派。
6. **Debug 忙**：用户 DevTools 占用某 Tab 时不被强制 detach，item 自动交给其他 Agent。
7. **队首阻塞**：至少一个 item 等 closure 时，其他可派 item 仍在同一调度周期生成 child/create command。
8. **冷却单调**：同一轮 `deadlineAt` 永不向后移动；到期后状态必须变化，不能继续显示相同 2 分钟。
9. **停机事实**：停止后不再产生新搜索/详情动作；只允许有界接收停止前 outbox。
10. **父任务收口**：完成、部分完成、失败、需处理数量与 item/attempt/实际持久化一致。
11. **Debug 自动绕行**：StarVoice stale session 可安全自清；外部 DevTools 不被 detach；存在其他空闲 Agent 时，Debug busy item 在 10 秒目标内换机，父任务不转人工。
12. **AI 真过滤**：高置信度 `skip_expensive` 的候选没有详情、评论和作者请求，且不出现在正常内容分诊、告警与业务保存数中。
13. **详情二筛**：列表 `need_detail` 先走最小详情；二筛无关停止，相关/不确定/保护信号才完整增强。
14. **相关数量补足**：过滤项不消耗 `postLimit`；存在足够相关结果时，`businessSavedCount` 达到上限，综合/图文分别可解释。
15. **AI 降级不泛滥**：主备模型故障时普通候选进入有界延后，保护信号继续；页面显示延后数量，父任务不长期卡住。
16. **小红书实时打开**：对本次已复现的两条记录，管理端不再下发裸链接或历史 token；在线来源 Agent 能重新搜索并精确打开目标作品。
17. **小红书安全边界**：新 token 不离开目标 Agent；未登录、安全挑战、未命中和 300031 有明确结算，且不自动绕过。
18. **小红书降级**：无合格 Agent 时页面明确提示并打开原关键词搜索定位，不再把失败的永久“原文”链接显示为正常功能。

### 9.2 每次恢复必须同时具备的证据

- 新 item attempt ID；
