# 负面巡查 Hotfix 第二轮方案审查

日期：2026-09-07。审查对象：negative-patrol-hotfix-plan-20260907.md，审查时共 149 行。

结论：方向已覆盖三个目标，但仍有以下实施合同缺口，不能无条件通过。下面是对方案可执行性的发现，不表示本轮已复现所有生产现象。本轮只读检查代码，并生成本审查记录；未修改原方案或业务代码，未访问或操作生产。

## 生产保护

### R1 [P1] 限制新建任务不足以限制已有命令实际交付

- 方案位置：62—66 行。
- 代码：server/routes/capture-cloud.js:7097—7148，在弹性领取之后仍独立查询 pending/acknowledged 命令；约 13390 行的人工继续独立写 resume 命令。
- 后果：如果只在创建或弹性领取时检查额度，部署前已排队的命令、人工继续和重送命令仍能造成新增执行。已经交付到客户端的任务也不能被当作空闲额度。
- 必须补齐：把新执行命令首次交付纳入统一原子准入；同一命令重送不重复扣额；升级和重启时保守计入已交付、已确认但尚未报告开始的任务。明确旧设备已缓存任务的排空/收敛办法。
- 验收：存量 pending、acknowledged、人工继续、交付响应丢失与后台重启，均不能超发或重复执行。

### R2 [P1] 固定批次必须按帖计量，不能按整包命令计量

- 方案位置：61—62 行。
- 代码：negative-patrol.js:2400—2415 一个 create 命令携带整个 targets；sidebar/sidebar-logic.js:17411 起本地循环，约 17765 行上帖结束直接继续下一帖。
- 后果：100 帖整包若只消耗一个任务/命令额度，浏览器拿到包后，服务器过载也无法靠“暂停新命令”阻止包内剩余帖子继续采集和回传。
- 必须补齐：明确派发速率单位是帖子的执行尝试。优先使新巡查按帖从服务器领取，固定模式保留固定 Agent 分配语义；若采用逐帖许可接口，则明确设备能力与失败恢复。不能只写“不允许大包绕过”而没有实现路径。
- 验收：固定 100 帖批次执行中注入过载，检查实际帖子开始时间和回传速率；同时覆盖弹性队列。

### R3 [P1] 停止/取消需要受保护，不能排在可能阻塞的新领取之后

- 方案位置：53—55、65、140 行。
- 代码：capture-cloud.js:13475 起停止接口先做维护和锁定；约 7082—7107 心跳先合并快照和弹性领取，再查询命令。stop 在结果中排序靠前，但不能绕开此前的失败或阻塞。
- 后果：给心跳留连接仍不等于过载时能停止采集；新领取失败可能使同事务内的状态更新回滚，并阻断停止命令交付。
- 必须补齐：停止/取消的写入、交付、回执均纳入受保护容量；过载主动跳过新领取，新领取失败不得拖垮状态上报和停止交付。保留必要的一致性和任务锁顺序。
- 验收：规定并测量高压下停止响应时限；停止成功后不再交付 create/resume，已在途请求按明确边界收敛。

### R4 [P1] 回传后的内存积压不能只靠“观察后再决定是否修改”

- 方案位置：64—65、147 行。
- 代码：server/routes/sync.js:19、108—129 为无界 commentWorkflowQueue；约 353—388 行先写 queued receipt，再把携带记录的闭包放入内存。没有该队列长度、字节量或等待时长的对外快照。AI 准入有独立上限，不等于这条外围评论队列已有上限。
- 后果：停止新派发后，已有设备回传仍可继续堆积。HTTP 回传快不代表后处理队列已稳定，也不证明进程中断后 queued 工作能恢复。
- 必须补齐：把队列长度、估算字节、最老等待时间纳入低成本监测和准入；给未处理数据设有界承载与恢复合同。优先核实已持久化载荷和既有恢复能力，再以持久化引用替代无限保留完整载荷；无空间可靠承接时返回可重试状态，不能清除客户端未确认数据或把未完成后处理报成完成。
- 验收：慢 AI/评论处理下持续回传、达到积压边界、进程重启和重复回传；无无限内存增长、无已确认数据丢失，并可恢复收敛。此处是已确认的代码风险，尚未证明是下午整机失联的根因。

## 预览正确性

### R5 [P1] 人工优先需要明确决策表，现有附加过滤确实可能漏掉人工负面

- 方案位置：87—88 行。
- 代码：negative-patrol.js:397—400 同时检查 sentiment、business_visibility 和 ai_result.relevance。records.js:670—680 人工改情感不会同步改这两个附加状态；ai-labeler.js:1325—1336 保留人工 sentiment，却可更新 ai_result。relevance-prefilter.js:835—847、record-store.js:1122 也有业务可见性更新路径。
- 后果：当前 sentiment 正确为负面，也可能被历史 AI 无关判断或后续可见性更新挡掉。先前 128 条人工情感字段一致的聚合无法排除此路径。
- 必须补齐：形成查询可直接执行的决策表，明确人工中性/正面、人工负面、显式人工排除、待审误报、历史 AI 无关、业务过滤的优先级；预览和下发使用同一规则。冲突状态有可审查的排除原因。
- 验收：人工修正后重新 AI 分析、重新采集，名单仍遵守有效人工判断。
- 未关闭项：上述能解释漏选人工负面的路径，不能冒充“已改中性仍出现在预览”的已证实根因；后者仍需同一记录的修改历史和实际预览响应闭环。

### R6 [P1] 提交结果未知时丢弃请求键，可能重复建任务并再次放大负载

- 方案位置：91、131 行。
- 代码：NegativePatrolTaskCreator.tsx:127 的 pendingSubmission 只保存在组件；clearPreview:168、toggleCandidate:241、toggleAll:246 会清空。请求在 305 行设 30 秒超时，下一提交在 293—298 行可能生成新 requestKey。候选行与全选按钮约 441、458 行在提交时未禁用；日期等输入已有 submitting 禁用。
- 后果：服务器已创建但响应丢失，用户重选或重新预览后再提交会用新键；后端按键幂等不能识别它是同一未知提交，可能再建一批任务。
- 必须补齐：增加提交结果未知状态，保留不可变请求快照与原键；先查询/重试原请求确认结果，再允许明确的新提交。冻结全部选择入口，并覆盖弹窗关闭/重开、页面刷新后的恢复。不能只写“复用同一请求键”，却仍允许界面清掉它。
- 验收：数据库提交成功后丢响应，切选/重预览/关闭重开，最终只存在一次原提交；用户明确创建新任务仍可正常操作。

## 标签页与收尾

### R7 [P1] 验证码不一定进入 needs_action，保留现场的承诺尚无实际状态路径

- 方案位置：121 行。
- 代码：utils/cloud-targeted-post.js:687—748 识别 requiresManualAction，但 buildTargetResult:836—845 仍返回 failed；sidebar:17775—17782 的最终状态不生成 needs_action。needs_action 又被视为终态，sidebar:17245 附近遇它直接返回，现有恢复不能简单“继续原轮”。
- 后果：只按 needs_action 保留页面，真实验证码可能作为普通失败被关闭；或人工处理完后无法复用原页继续。
- 必须补齐：安全错误到保留现场状态/原因的映射、停止后续帖子、人工处理后的恢复转换和页面归属。可以单独建清理保留原因，避免未经兼容设计改服务端终态枚举。
- 验收：从真实采集安全错误触发暂停、原页保留、人工恢复；不能只在测试里直接注入 needs_action。

### R8 [P1] 最近命令缓存不等于可靠待回执队列

- 方案位置：118—120 行。
- 代码：background.js:2456—2472 的最近命令结果只留 50 条；约 4515 行按时间清理；reportTargetedPostTerminalToCloud:3456—3463 只接受当前单槽 request。任务账本不保存完整 targetResults。
- 后果：回传失败后关闭页面、换轮或缓存淘汰，旧轮结果可能不能独立补报；“先可靠保存待回执”目前缺少落实位置。
- 必须补齐：将未确认回执与可淘汰历史分开保存，按 command/request/attempt 保存完整结果和确认状态；允许旧轮独立补报，确认后才清理，恢复后有主动重试入口。未确认数据也需有容量预算；预算不足时暂停新执行，不能无限存储或淘汰未确认结果。
- 验收：断网换轮、超过 50 条其他命令、后台重启、服务端已收但确认响应丢失；结果可幂等补报且不会重复采集。

### R9 [P1] 回收登记必须从获取执行锁开始绑定轮次

- 方案位置：117—120 行。
- 代码：sidebar:17326 获取锁只传通用 owner/label，17366 才开帖子；background:7989 起该锁缺 request/attempt 绑定；释放仍依赖 sidebar:17898 的 finally。
- 后果：执行页在取锁后、建页前崩溃时，仅登记 tabId 无法选定应释放的锁；按通用 owner 补偿又可能误释放新轮锁。
- 必须补齐：取锁时绑定 requestId、attemptId、lockId、holder 身份；先确认该轮内容执行停止、持久化收尾，再精确释放本轮锁与关闭执行页。每步可幂等恢复，不依赖即将销毁页面的 finally。
- 验收：取锁后崩溃、建页失败、释放失败重试、新旧轮交错；旧轮既不能留下永久占用，也不能解除新轮锁。
