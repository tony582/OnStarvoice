## 4. Extension 提前的实施顺序

原计划把正式 P7 放在 G3 后。本计划先提前 R0/E0 的证据、规格和设计准备；将来 E1 如在 G3 关闭前实施，只能是已冻结协议内的 Extension 内部调整，需在功能批次中明确记载这项有限顺序调整，不能追认 G3 已通过。跨服务端协议、任务语义或数据库的变更留在独立批次。

| 批次 | 具体交付 | 进入与退出条件 | 当前状态 |
|---|---|---|---|
| R0/E0 | 文件证据、权属待核清单、源码/快照映射、行为验收目录、本计划 | 原始文件前后不变；所有未知事实明确标出 | 本 Draft 批次；不是权属和实机验收通过 |
| E-base | 架构基点与稳定 hotfix 的逐项归并候选 | 当前客户版本重新确认；9 文件及配套修复全覆盖；隔离回归通过 | 待功能准备批次 |
| E1a | 显式执行上下文、兼容 facade、五类调用方逐步迁移 | 不改消息/身份/存储；同类型任务、迟到事件、realm 隔离行为通过 | 待实施 |
| E1b | background 执行状态、owner、worker、停止和恢复职责拆分 | 稳定 UUID/requestId/Attempt 关系、资源回收次序、有限恢复预算保持 | 待 E1a |
| E2 | 结果标准化、本地确认、提交队列分离 | 丢响应后重放幂等；取消与在途结果明确；未同步数据不丢失 | 待 E1 |
| D1 | 任务型 Sidebar controller/presenter 和新 UI | UI 只读状态/发命令；不直接改账本或调度；用户已选设计约束保留 | 规格可并行；代码在 E1/E2 边界稳定后 |
| E3a/E3b | 小红书、抖音各自的页面识别、列表、详情、评论模块 | 依据有权使用的中立规格；逐平台真实验证；旧实现退出包需完整调用覆盖 | 待权属处置及执行接口稳定 |
| E4 | 关键词扩展、其余高相似模块及品牌/包元数据 | 完整来源清单；逐项许可/替换结论；资产和文案检查 | 不以“改名”认定完成 |
| E5 | 独立发布候选与客户验收 | 行为/性能/长期测试、版本来源、回滚兼容、权属处理记录完成 | 单独发布授权后小范围投放 |
| P4+ | 恢复服务端后续架构路线 | G3 正式关闭，Extension 已稳定，另选发布窗口 | 暂缓 |

实现边界示意（内部目标，不是新增服务器协议）：

```text
Sidebar 视图 → controller → 显式执行上下文 / 状态机
                                      ↓
                             平台采集器（每次仅一平台改造）
                                      ↓
                       标准化 → 本地确认 → 提交队列 → 现有服务端 API
```

E1 的 facade 可以在过渡期保留旧入口，但要登记调用清单和退出条件。最终“独立实现完成”不能凭移动文件或新增 wrapper 认定；新旧实现不能同时对真实平台采集或双重提交。

## 5. UI/UX 与代码独立的共同要求

依据已读取的“重新设计 Extension UIUX”任务，沿用 [现有 Figma](https://www.figma.com/design/jk1NmFyzAWdBQROUU9nSYI/StarVoice-Extension-UIUX-Redesign-%E2%80%94-3-Directions?node-id=15-39&p=f) 已确认的 Logo 蓝、轻量状态导航（全部/进行中/需处理/历史）、去掉三张重复 KPI 卡、设置页仅“授权与设备”。本批未改 Figma。

产品目标是企业舆情采集端：展示任务、运行进度、需要处理的异常和结果提交状态。手工笔记/博主/搜索入口仍可用，作为“临时采集”次级入口设计；保留已选的笔记/博主页面区分。组织、设备、任务来源等仅展示服务端已提供且适合用户判断的信息，不虚构风控结论或暴露内部锁/栅栏编号。

设计规格需要覆盖未授权、运行、暂停验证、停止中、部分结果、提交失败、完成等状态。设置只显示授权与设备的五类已选状态；移除普通业务设置前必须核查旧缓存的实际作用，安排兼容行为，不能在换 UI 时悄悄改变安全默认值或后台规则。

独立性验收同时覆盖代码来源、产品工作流、视觉资产、导出/帮助文案、manifest 和发布包。对依赖/字体/图标/第三方通用实现保留来源和许可；没有“低于某个文本百分比即可合法”的门槛。本次相似度只是排查目录，不是法律结论。

本团队已接触 MediaClaw 源码，不能把后续实现自行称为严格洁净室开发。如果权属审查确定需要此类安排，应由律师定义隔离规格和未接触争议源码的独立实现流程。不能靠删除历史、移除权利信息或混淆压缩消除历史权属问题。

## 6. 每批客户稳定性与发布条件

1. 同时记录架构 base、候选 head、实际交付来源及其差异；新 hotfix 出现时重新核对，禁止覆盖客户修复。
2. 先用固定输入和模拟故障验证，再在专用测试 Profile、测试租户和测试账号验收；测试调度必须关闭，避免接入客户任务。真实平台采集另获明确范围，不能将两套执行器同时接在同一任务上。
3. 第一批冻结协议、持久化格式、权限、平台等待、并发、重试预算及版本号。现有 `unlimitedStorage` 已在 0.4.3/0.4.5 manifest 中，本批既不新增也不移除；6MB/8.5MB 是此前建议的运行阈值，不能当成当前浏览器硬配额。
4. 用户停止后立即阻止新的采集和业务轮次；已本地确认的记录保留；在途提交按幂等确认结算，迟到成功不能覆盖取消/新 Attempt。UI 释放和后台资源回收分别显示，停止时限不改变 owner 断连宽限。详见 [E0](E0-contracts-and-acceptance.md)。
5. 待同步、同步失败、活动任务和归属不明确的数据不自动删除。存储迁移/IndexedDB、自动清理属于后续独立方案，不能在 E1/E2 顺带实施。
6. 先验证旧稳定包可读取候选产生的持久状态，保留原包、哈希和版本记录，再考虑灰度。回滚只回滚候选文件/包，不清空用户数据；一旦涉及不兼容数据格式，停止此批并重新设计回滚。
7. 客户更新需单独授权，先内部验收、再明确同意的小范围客户，验证完成后才扩大。服务端架构发布与 Extension 更新分别安排；CI 绿色不自动触发发布。

停止条件：证据源变化、版本归并遗漏、串任务/跨租户、重复业务记录、未同步结果丢失、停任务复活、旧包不能恢复数据、行为回归或 CI 失败。停止的是候选推进，不操作客户状态补偿测试差异。
