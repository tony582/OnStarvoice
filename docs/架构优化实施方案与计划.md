## 1. 决策摘要

StarVoice 需要进行架构优化，但不推倒重写，也不直接微服务化。

目标形态固定为：

> **模块化单体 + 独立后台 Worker + PostgreSQL 持久化任务/Outbox + 显式维护命令。**

继续保留同一仓库、同一数据库和现有外部协议。优先解决进程职责、依赖方向、持久化后台任务、测试门禁和发布可靠性，再拆分前端与 Extension 大文件。

本次任务只授权在当前工作区完成方案和 P1-A/P1-B 本地改动。Gate 通过只表示技术条件满足，不会自动授权下一阶段。提交、推送、合并、测试环境发布、生产只读核验、生产部署、生产数据操作和客户 Extension 升级均是相互独立的授权阶段。

### 2.4 当前主要矛盾

业务能力持续增长，但新的领取、接力、恢复、排期和统计逻辑仍大量进入 HTTP 路由和单一服务进程。系统现在能够承载更多业务，却更难安全修改、独立扩容和准确判断健康状态。

## 3. 优化原则

### 3.1 必须保持的不变量

1. 同一租户、Agent 和稳定任务 ID 的重试不能产生重复业务任务。
2. Work Item 同一时刻只能有一个有效执行者；重新分配必须保留历史。
3. `execution_task_id`、`assignment_revision`、请求哈希和任务检查点的栅栏语义不得弱化。
4. Extension 与服务端现有命令、心跳、快照和同步协议保持向后兼容。
5. 租户 ID 必须贯穿查询、锁、事件、Job 和日志上下文。
6. 原始采集成功不得因 AI、通知、报表或媒体处理失败而回滚。
7. 删除、无结果、范围外与平台安全验证必须继续使用不同状态语义。
8. 快照和任务事件继续只追加；业务历史不能被技术压缩误删。
9. 数据库迁移优先采用向前兼容的加法迁移，应用回滚不得依赖破坏性 down migration。
10. 每一个实施阶段必须可独立验收、暂停和回滚。

### 3.2 实施纪律

- 机械移动与行为改变分开提交，避免无法判断回归来源。
- 路由兼容层保留到新模块经过测试和灰度后再删除。
- 一个阶段允许包含多个小 PR，不允许把跨阶段改动合成一个大 PR。
- 每次只改变一个主要风险面：门禁、启动边界、任务持久化、前端注册或 Extension 模块化。
- 新增数据库字段、表和索引必须有真实 PostgreSQL 测试及查询计划检查。
- 发布使用明确文件清单；不使用 `git add -A` 混入构建物、ZIP、`.env*` 或无关改动。

### 3.3 明确非目标

本轮架构优化不包括：

- 拆分微服务、引入 Kubernetes、Kafka 或新的基础设施集群；
- 增加生产机器或 PM2 实例数；
- 调整无人值守时间、任务频率、Agent 分配策略或平台访问节奏；
- 增加自动重试次数；
- 更换 AI 提供商、模型、路由、提示词或增加 AI 消耗；
- 改变客户可见工作流或进行视觉改版；
- 清理生产任务、修改生产数据或自动部署；
- 为了“代码更漂亮”而重写已验证的采集业务规则。

## 4. 目标架构

```text
Extension / Admin / Dashboard
              │
              ▼
      API 进程（HTTP 边界）
      ├─ 认证、租户和参数校验
      ├─ 调用应用用例
      └─ 返回稳定 API 契约
              │
              ▼
          PostgreSQL
      ├─ 业务事实与历史
      ├─ Task / Attempt / Work Item / Event
      ├─ Job / Outbox / Lease
      └─ 迁移与维护审计
          ▲             ▲
          │             │
 Scheduler Worker    AI / Media / Report Worker
 排期、租约回收、     持久化领取、重启续跑、
 命令结算、通知领取   有界重试、幂等完成

 Maintenance CLI
 ├─ migrate
 ├─ repair / backfill
 └─ preview / verify
```

### 4.1 模块依赖方向

```text
routes / worker entrypoints
        ↓
application use cases
        ↓
domain policies and state transitions
        ↓
repositories / external adapters
        ↓
PostgreSQL / AI / SMTP / filesystem
```

Cron、Worker 和路由可以调用同一个应用用例；Cron 不再从路由文件导入业务函数。领域层不得依赖 Express 的 `req/res`。

### 4.2 进程角色

| 角色 | 负责 | 不负责 |
|---|---|---|
| API | HTTP、鉴权、租户、参数、同步调用 | Cron、历史回填、无限循环、一次性 repair |
| Scheduler Worker | 排期、命令对账、租约回收、通知领取 | 对外 HTTP、页面静态资源 |
| AI/Media Worker | AI、媒体、报告等持久化 Job | 修改采集协议、直接决定 Agent 分配 |
| Maintenance CLI | 迁移、repair、backfill、preview、verify | 随服务启动自动长期运行 |

P2 第一版仍保留 `PROCESS_ROLE=all` 兼容模式，直到独立角色通过测试和灰度；不能一次性切断现有启动方式。但旧拓扑和拆分拓扑必须二选一，严禁同时运行 `all` 与任一独立 Worker。

| 启动拓扑 | 允许组合 | 禁止组合 |
|---|---|---|
| 兼容拓扑 | 仅 `all` | `all` + Scheduler/AI/Media Worker |
| 拆分拓扑 | API + 所需独立 Worker | 任意 `all` 进程 |

本地开发可显式选择兼容拓扑；生产缺少明确角色配置时必须拒绝启动，不能静默回落到 `all`。

跨进程互斥采用两层防线：发布清单预检拒绝混合拓扑；每个拥有 Scheduler 或 AI 执行权的进程还必须持有对应 PostgreSQL advisory lock/角色租约。仅检查本进程的环境变量不足以证明互斥；锁丢失时必须停止领取并退出或降为不可就绪。

- 不包含数据库迁移，不改变运行时协议。
- 如果 lockfile 变化超出最小依赖范围，停止并单独审查，不强制升级。

## P2：应用启动、进程、配置、健康和迁移边界

### 目标

让 HTTP 服务可以被测试和独立启动；让迁移、repair 和后台循环不再隐式绑定到 API 进程。

### 工作包

1. **P2-1 `createApp()`**
   - 将 Express 构建提取为无监听、无 Cron、无迁移、无回填副作用的工厂；
   - `server/index.js` 暂时作为兼容入口；
   - API 路径、静态资源和错误响应保持兼容。
2. **P2-2 进程入口**
   - 建立 API、Scheduler Worker、AI/Media Worker、Maintenance CLI 入口；
   - 开发环境可显式选择 `PROCESS_ROLE=all`，生产必须显式选择兼容或拆分拓扑；
   - 启动时检测角色互斥，`all` 与任何独立 Worker 并存时拒绝启动；
   - 每种角色支持独立优雅退出。
3. **P2-3 配置校验**
   - 区分开发默认值与生产必填配置；
   - 生产环境缺少 `DATABASE_URL`、关键目录或认证配置时明确失败；
   - 日志不得输出密钥和完整连接串。
4. **P2-4 健康端点**
   - `live`：进程能响应；
   - `ready`：数据库可用、迁移状态可读、角色初始化完成；
   - Worker 单独记录最后成功循环、最近错误和积压年龄；
   - 不再用单一 `/api/health` 推断 AI 或队列吞吐健康。
5. **P2-5 迁移治理**
   - 增加数据库级迁移锁；
   - 保存迁移 checksum，拒绝已执行文件被静默修改；
   - reset/repair/backfill 转入显式维护流程；
   - 新维护任务不再复用 `schema_migrations` 冒充结构迁移。

### P2 子阶段顺序

1. **P2-A：可测试 App 工厂**：只提取 `createApp()` 与 HTTP 测试，不改变生产入口和后台循环。
2. **P2-B：角色配置与互斥**：加入显式角色校验、发布清单预检和数据库角色锁；继续使用兼容 `all` 拓扑。
3. **P2-C：独立入口与健康**：建立 API/Worker 入口、liveness/readiness 和优雅退出，先在本地多进程测试。
4. **P2-D：迁移治理**：迁移锁、checksum 和维护命令单独实施，不与拓扑切换同一批。
5. **P2-E：测试环境拓扑切换演练**：获得测试环境授权后才执行 `all → split → all` 演练。

每个子阶段独立提交候选、独立验证和独立回滚；前一子阶段通过不自动授权下一子阶段。

### Gate G2

- [ ] `createApp()` 的真实 HTTP 测试覆盖认证、租户、404、500 和健康端点。
- [ ] API-only 模式不会启动 Cron、AI 循环、repair 或历史回填。
- [ ] Worker-only 模式不监听公网 HTTP。
- [ ] API 与 Worker 同时启动时，不重复注册同一调度循环。
- [ ] `all` 与独立 Worker 的混合拓扑会被配置校验拒绝。
- [ ] 真实并发进程证明 Scheduler/AI 数据库角色锁只有一个持有者，锁丢失者停止领取。
- [ ] 生产缺少显式角色配置时失败，不静默回落到 `all`。
- [ ] 两个并发迁移进程只有一个执行迁移，另一个安全等待或退出。
- [ ] 修改已执行迁移文件可被 checksum 门禁发现。
- [ ] 兼容 `all` 模式通过现有 1133 项回归测试。

### 灰度与回滚

- 第一轮生产仍可显式使用兼容 `all` 模式；独立角色先在本地和测试环境验证，两种拓扑不得并存。
- 保留旧入口一个完整发布周期。
- 数据库变化只允许加法迁移；旧应用必须仍能读取新结构。
- `all → split` 顺序：阻止新工作进入旧循环，等待/结算在途工作，停止 `all` 并确认进程退出和角色锁释放，启动独立角色并确认唯一锁持有者与 readiness，最后恢复新工作入口。
- `split → all` 回滚顺序：阻止新工作，停止全部独立 Worker 并确认锁释放，停止 API，启动兼容 `all` 并确认唯一角色锁与 readiness，再恢复新工作；任何时刻不得重叠执行权。

## P3：采集任务领域边界

### 目标

把任务领取、命令、租约、状态迁移和事件投影从 HTTP 路由中移到可复用、可测试的模块，同时保持现有协议和数据库语义。

### 建议目录

```text
server/modules/capture/
  domain/
    task-status.js
    recovery-policy.js
    assignment-fence.js
  application/
    heartbeat.js
    command-lifecycle.js
    elastic-work.js
    lease-reconciliation.js
    snapshot-projection.js
  infrastructure/
    capture-repository.js
    event-repository.js
  http/
    capture-router.js
```

目录名可在实施时微调，依赖方向不能反转。

### 工作包

1. **P3-1 后台函数先出路由**
   - 迁移 `reconcilePendingCaptureCommands`、`reconcileElasticCaptureLeases`、自动恢复等函数；
   - Cron 改为依赖应用服务；
   - 原路由保留临时 re-export，避免一次性断开测试和旧导入。
2. **P3-2 Heartbeat 用例**
   - 输入为已鉴权 Agent 与规范化心跳 DTO；
   - 统一完成 Agent 更新、快照投影、弹性领取和命令返回；
   - 不接收 Express `req/res`。
3. **P3-3 弹性领取用例**
   - 保留现有行锁、`SKIP LOCKED`、能力、平台、空闲和安全阻断判断；
   - 领取、子任务、Command、Attempt、Item revision 和 Event 在同一事务内完成。
4. **P3-4 Repository 边界**
   - 收敛 SQL 和事务接口；
   - 不建立无业务意义的“一表一个 Repository”；
   - 以用例和事务边界组织查询。
5. **P3-5 状态转换策略**
   - 把状态合法性、聚合和恢复处置提取为纯函数；
   - 数据库仍保留约束作为最后防线。

### Gate G3

- [ ] 旧 API 请求与响应契约快照不变。
- [ ] 两个并发 Agent 领取同一池时，每个 Work Item 只有一个有效领取者。
- [ ] 旧 `assignment_revision`、旧 `execution_task_id` 和旧 Attempt 的写回全部被拒绝。
- [ ] Command 过期、Agent 离线和父任务取消竞态有真实 PostgreSQL 测试。
- [ ] Cron 不再从路由目录导入业务函数。
- [ ] 路由只保留鉴权、参数、状态码和应用用例调用。
- [ ] 在隔离测试库装载脱敏代表数据后，关键查询执行计划满足切换前记录的量化阈值；任何生产只读对比另行授权。

### 灰度与回滚

- 先做纯移动和兼容导出，再切换调用者，最后删除旧实现。
- 每个子用例单独 PR；不得一次移动完整 9,000 行文件。
- 任一行为对比不一致时恢复旧调用路径，不修改生产任务状态补偿差异。

## P4：持久化后台 Job 与独立 Worker

### 目标

消除 `setImmediate`、内存 `Set/Map` 和启动后定时回填导致的重启丢任务问题；后台工作可以领取、续租、失败重试和幂等完成。

### 最小 Job 模型

| 字段 | 用途 |
|---|---|
| `tenant_id` | 租户隔离；系统任务必须使用明确系统作用域 |
| `kind` | Job 类型 |
| `payload` | 最小引用，不保存密钥和大段客户内容 |
| `idempotency_key` | 业务幂等键 |
| `status` | queued / leased / succeeded / retry_wait / dead |
| `attempt_count` | 有界尝试次数 |
| `run_after` | 延迟与退避 |
| `lease_owner/lease_expires_at` | 崩溃回收 |
| `lease_revision` | fencing token；拒绝旧租约持有者续租或完成 |
| `last_error` | 截断、脱敏的诊断信息 |

### 工作包

1. **P4-1 Job/Outbox 基础设施**：加法迁移、claim/lease、fencing token、续租、完成、失败和回收；续租、完成和失败都必须按 `job_id + lease_owner + lease_revision` 条件更新。
2. **P4-2 Worker Runtime**：Job registry、并发上限、优雅退出和结构化日志。
3. **P4-3 舆情剖析试点**：第一个迁移 Job，先 shadow enqueue，再切换执行权。
4. **P4-4 评论 AI**：用持久化领取替代进程内无限循环；不改变模型、提示词和调用优先级。
5. **P4-5 媒体与报告**：媒体落地、报表、历史修复按风险逐项迁移。
6. **P4-6 Admission 边界**：第一阶段只运行一个 AI Worker；扩为多个 Worker 前必须实现跨进程总并发控制。
7. **P4-7 切换协议**：每类 Job 明确唯一执行权、提供商幂等键/结果查询/人工处置策略，以及“停止旧领取 → 等待或隔离在途租约 → 切换执行权 → 开启新领取”的顺序。
8. **P4-8 最小观测前置**：在任何 shadow/cutover 前提供队列长度、最老 Job 年龄、租约回收、Worker 最后成功循环和重复副作用防护指标；P5 再做全链路完善。

### Gate G4

- [ ] Worker 在领取后被强制终止，租约到期后 Job 可按既有重试预算恢复，任一时刻只有一个有效租约持有者。
- [ ] Job 被新 Worker 重领后，旧 `lease_revision` 的续租、完成和失败回写全部被拒绝。
- [ ] 幂等键防止同一业务事件重复创建有效 Job。
- [ ] 外部调用成功但落库响应丢失时，重试不会重复产生客户可见副作用。
- [ ] AI Job 迁移前后模型、路由、提示词、超时和调用条件一致。
- [ ] 原始采集写入不等待后台 Job 完成。
- [ ] dead Job 可诊断、可人工重放，但不会无限自动重试。
- [ ] shadow 阶段证明新旧候选集合一致后才切换执行权。
- [ ] 每类外部副作用都有可验证的幂等机制或明确的人工不自动重试处置。
- [ ] 切换前已能观察队列、积压年龄、Worker 循环、租约回收和重复防护。

### 灰度与回滚

- 每种 Job 有独立开关；只切换未来任务，不删除历史。
- 先 shadow enqueue，不执行外部调用；比对一致后，按唯一执行权协议切换。
- 回滚顺序固定为：停止新 Worker 领取，等待可安全完成的在途任务或使其租约失效并隔离，确认无新路径有效持有者，再恢复旧调度；全程保留 Job 台账。

## P5：可观测性与发布可靠性

### 目标

能够区分“进程在线、队列在跑、业务在推进”，并使发布具备明确构建清单、健康门禁和可恢复回滚点。

### 工作包

- 统一请求、任务、Agent、Job 的上下文字段：`requestId`、`tenantId`、`taskId`、`itemId`、`agentId`、`jobId`。
- 结构化日志替代关键链路的自由文本 `console.*`；所有错误脱敏和截断。
- 暴露或汇总以下运行指标：
  - API 5xx、延迟和数据库池等待；
  - Scheduler 最后成功时间与调度延迟；
  - 队列长度、最老 Job/Work Item 年龄、租约回收数量；
  - Agent 心跳、任务心跳和业务进展分别统计；
  - AI admission active/queued/oldest wait 和成功吞吐；
  - stale revision 拒绝数、领取冲突数和重复副作用防护数。
- 发布同时构建 Admin 与 Dashboard，生成版本/提交/迁移/静态资源清单。
- 发布目录版本化；备份、迁移、切换、PM2、readiness、业务冒烟和回滚材料分别验证。
- 不把现有 `deploy/deploy.sh` 描述为原子发布，直到实现与验证完成。

### Gate G5

- [ ] 关闭数据库时 readiness 失败而 liveness 仍能正确表达进程状态。
- [ ] Scheduler 或 AI Worker 停止时，API 健康不再被误报为整套系统健康。
- [ ] 可从一个 task ID 追踪 Agent、Command、Attempt、Item、Job 和最终结果。
- [ ] 发布包能证明构建来源、迁移集合和静态资源版本。
- [ ] 测试环境完成上一版本回滚演练；数据库向后兼容边界有记录。
- [ ] 未得到部署授权前，不触碰生产 PM2、Nginx、数据库或客户 Extension。

### 灰度与回滚

- 日志与指标先在本地/测试环境启用，确认脱敏、容量和告警阈值后再单独申请环境发布。
- 发布继续使用版本化目录和加法迁移；应用回退只切回上一已验证版本，不删除新表、新列或审计数据。
- 若新健康门禁误报，先恢复上一版探针配置；不得为了显示“健康”而关闭 Worker 积压或业务推进检查。

## P6：Admin 页面注册与 API 边界

### 目标

消除桌面、移动和 Sidebar 多处维护页面、权限和标题导致的漂移，并阻止旧请求覆盖新筛选结果。

### 工作包

1. 建立单一 Page Registry，包含页面 ID、标题、工作区、权限、桌面/移动可见性、懒加载组件和 Badge 配置。
2. Desktop、Mobile 和 Sidebar 只消费 Registry；允许各端保持不同布局，不强迫视觉统一。
3. API 客户端增加运行时响应校验、稳定错误码和统一 401/session-expired 处理。
4. 建立统一查询 hook：AbortController、generation fence、loading/error/empty 状态和租户切换取消。
5. 先拆数据请求与状态，再拆 2,000 行级页面组件；不顺带重做视觉。

### Gate G6

- [ ] 同一页面只在 Registry 定义一次身份、权限和加载器。
- [ ] 桌面、移动和 Sidebar 的可见页面、平台管理员权限测试一致。
- [ ] 租户或筛选快速切换时，旧响应不能覆盖新结果。
- [ ] API 返回结构漂移在边界被检测，而不是在组件深处报错。
- [ ] 关键运营列表保持空结果时表头和筛选可用，滚动结构不回退。
- [ ] 本阶段修改文件 lint 通过，Admin 全局 lint 债继续下降。

### 灰度与回滚

- Page Registry 和查询层先通过兼容适配器供一个低风险页面使用，再逐页迁移；不一次删除旧映射。
- 出现权限、路由、移动端可见性或请求时序差异时，恢复该页面旧注册/请求路径；其他已验证页面不连带回滚。
- 本阶段默认无数据库迁移；如后续确需加法字段，必须拆成独立工作包和 Gate 证据。

## P7：Extension 渐进模块化

### 目标

降低超大文件修改风险，同时保持 Manifest、消息协议、本地账本、Debug 所有权和平台采集行为兼容。

### 拆分顺序

1. **消息协议与 DTO**：集中消息名、请求/响应和版本兼容。
2. **任务状态机**：锁、Attempt 栅栏、检查点、恢复和终止吸收。
3. **平台适配器**：小红书、抖音、微博分别收敛页面识别、列表、详情、评论和作者能力。
4. **同步与离线队列**：记录 envelope、批量同步、取消和幂等。
5. **Sidebar 控制器与视图**：状态派生与 DOM 渲染分离。

### 实施方式

- 原入口保留 facade，逐函数迁移并保持导出兼容。
- 每次只拆一个稳定协议或一个状态机，不同时改变页面选择器。
- `extension-build/` 始终由同步脚本生成，不直接编辑。
- 每个平台拆分都需要目标真实页面测试；DOM 契约断言不能作为唯一证据。

### Gate G7

- [ ] 现有 Extension 回归测试全部通过。
- [ ] 源码与本地 `extension-build/` 交付快照一致；客户已安装版本另行授权核验。
- [ ] 手工、云端一次性、无人值守、停止和恢复链路均通过真实浏览器验收。
- [ ] Agent、租户、任务和 Attempt 切换不会复活旧状态。
- [ ] 抖音/小红书平台安全验证仍是人工介入，不因拆分增加重试或并发。
- [ ] 客户浏览器仍需明确升级和 Reload；服务端发布不会被描述为浏览器已升级。

### 灰度与回滚

- 每次仅切换一个协议、状态机或平台适配器，并保留原 facade 一个预先定义的完整观察周期。
- 出现消息协议、锁、Attempt、检查点或真实页面行为差异时，恢复对应 facade 调用，不同时回滚其他已验证模块。
- 发布前保存最后兼容 Extension 包、版本号和受影响浏览器/Profile 清单；回滚仍需人工安装并 Reload，不能假设服务端回退会自动回退浏览器。

## P8：兼容层和遗留入口收尾

### 目标

在新边界稳定后删除临时 re-export、`PROCESS_ROLE=all` 兼容依赖和确认无调用的 Legacy 页面，降低永久双轨成本。

### 删除门槛

- 至少一个预先定义的完整观察周期没有旧路径调用；该周期需覆盖所有受影响调度至少一次，且不短于 7 个自然日；
- 仓库搜索、运行日志、API 清单和真实浏览器均无使用证据；
- 回滚版本不再依赖被删除接口；
- 用户文档、API 文档、部署手册和故障手册已经同步；
- 删除作为独立 PR，不与新功能混合。

### Gate G8

- [ ] 最后一个兼容版本、构建来源和恢复包已归档并验证。
- [ ] 旧入口在一个完整、预先定义的观察周期内调用次数为 0。
- [ ] 删除后的 API、进程角色、Admin 与 Extension 冒烟通过。
- [ ] 已在测试环境演练恢复被删除入口或回退到最后兼容版本。
- [ ] 回滚窗口、负责人、证据日期和关闭条件已记录。

### 回滚

- 删除仅以独立提交/PR 进行；回滚优先恢复该提交和最后兼容配置，不执行数据反向迁移。
- 若新代码已写入旧版本未知但可忽略的加法字段，旧版本必须已被兼容性测试证明可运行；否则禁止删除。

## 7. 验证矩阵

| 层级 | 最低要求 |
|---|---|
| 纯函数 | 状态转换、恢复处置、聚合、输入规范化 |
| Repository | 真实 PostgreSQL、约束、事务、行锁、迁移 |
| 应用用例 | 并发领取、命令过期、离线回收、幂等和旧写入栅栏 |
| HTTP | 真实 Express app、认证、租户、状态码、错误契约、健康端点 |
| 多进程 | 两个 Worker/Agent 并发领取、崩溃、租约过期、重新领取 |
| Admin | 构建、lint、权限、请求取消、关键桌面与移动路径 |
| Extension | Node 回归、源码/交付一致性、Chrome/Edge 真实页面 |
| 发布 | 干净构建、备份、迁移、readiness、业务冒烟、回滚演练 |

不能以单一测试层通过代替其他层。例如，1133 项 Node 测试通过不能替代 PostgreSQL 竞态测试；PM2 online 不能替代 AI 队列吞吐检查。

## 8. 指标与推进门槛

### 8.1 正确性硬指标

| 指标 | 要求 |
|---|---|
| 同一 Work Item 同时存在两个有效执行者 | 0 |
| 旧 revision / 旧 execution task 写回被接受 | 0 |
| 因 Worker 重启永久丢失持久化 Job | 0 |
| 跨租户读取、领取或回写 | 0 |
| AI 失败导致原始采集回滚 | 0 |
| 未授权的生产变更 | 0 |

### 8.2 工程指标

- CI 必需检查通过率和平均耗时；
- Admin lint 存量从 288 单调下降，不允许增加；
- Dashboard build/lint 恢复并保持通过；
- 真实数据库/API/多进程测试占比逐阶段增加；
- 超大核心文件行数下降只能作为结果指标，不能以移动行数代替职责解耦。

### 8.3 运行指标

正式设定绝对 SLO 前，先采集至少一个完整业务周期的当前基线。灰度阶段要求：

- 每个 Gate 在开始前补齐责任人、日期、验证环境、复现命令/证据链接和量化阈值；默认只使用本地或隔离测试环境；
- 生产查询、生产快照或生产只读核验均不属于默认验证手段，必须单独授权；
- API 5xx 和 p95 延迟的容许变化在灰度前由基线数据确定，不使用“明显回退”作为验收文字；
- heartbeat 事务 p95 的容许变化在灰度前量化并记录；
- 最老排队 Job/Work Item 年龄不持续增长；
- Scheduler 实际执行时间与计划时间偏差可解释；
- 租约回收、领取冲突和 stale-write 拒绝均可观察；
- AI 模型、调用条件和费用不因架构迁移增加。

## 9. 分支、提交与发布策略

### 9.1 分支

- 实施分支使用 `codex/` 前缀。
- G0 前不开始跨文件结构改造。
- 当前功能分支若先合并，则从合并后的 `main` 创建架构分支；若不合并，必须在架构分支说明对 `1332176` 的依赖。

### 9.2 提交

- 一个提交只做机械移动、测试、行为改变或文档中的一种主要事项。
- 每阶段完成后先本地验证；“提交”不自动授权推送。
- 推送不自动授权合并；合并不自动授权生产部署。

### 9.3 发布

- 数据库、Server、Admin、Dashboard、Extension 分别列出发布范围。
- 数据库备份、应用备份、构建、迁移、进程重启、健康、业务验证和回滚材料分别报告。
- Extension 发布必须说明哪些浏览器/Profile 尚需升级和 Reload。
