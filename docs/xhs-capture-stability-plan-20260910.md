# 小红书采集与任务恢复微调方案

日期：2026-09-10。状态：待实施方案。

目标：自动搜索能进入可用的搜索和筛选流程；搜索结果里残留的删帖不再拖着整个关键词反复执行；临时故障有界恢复；任务页面能直接说明原因和下一步。

- 源码确认：自动构造小红书搜索 URL 时会沿用匹配 `/search_result` 的现有路径，范围包含 `/search_result_ai`；模拟搜索提交函数目前只支持抖音。

## 2. 搜索与筛选适配（P0）

### 调整

1. 小红书自动搜索优先通过当前页面搜索框提交关键词，触发平台自己的搜索流程。核验输入关键词、结果页就绪和页面类型，避免把旧页面当成新搜索结果。
2. 兼容现场能复现的普通搜索和 AI 搜索布局；选择器按页面能力分支处理。保留直接导航作为有条件的回退，但只使用现场验证可用的路径及必要参数，不再无条件继承旧搜索路径和查询上下文。
3. 筛选前确认控件已加载。面板未打开时允许一次受控恢复：重新提交同一关键词，等待结果就绪，再应用筛选。每个关键词尝试共用恢复预算，避免导航、筛选和外层恢复各自循环。
4. 保留“时间项已选中 + 结果刷新证据”和后台入库时间窗校验。筛选仍无法验证时停止本词采集，说明是页面适配/筛选失败；不得改成不限时间或伪报没有结果。
5. 初始停止规则：同一任务项在相同扩展构建、页面类型、筛选条件和子错误码下连续 2 次执行失败，且各自已耗尽一次本地恢复后，转为“需要处理：筛选适配失败”，停止该任务项在相同条件下的自动接力。既有预算更小时先按预算停止；不因这两次失败全局停用其他关键词或账号。修复构建、可靠的环境恢复证据或人工复查可解除，不能仅靠轮询重新入队。

### 验收

- 在 Mac 上的成都 Chrome 配置内，用同一账号、同一关键词和相同筛选，对比手动搜索与自动搜索。
- 覆盖从首页、普通搜索页、AI 搜索页进入；确认走通有效流程、筛选一致、结果属于当前关键词。不要求个性化排序或实时结果逐条相同。
- 面板延迟加载能够恢复；持续打不开只执行一次本地恢复，随后记录明确原因；新旧结果未刷新、时间条件未生效时不能误采。

主要位置：`utils/capture-sync.js`、`content-v2.js`、`utils/capture/xhs-search-filter-evidence.js`。

## 3. 删帖与不可用帖按单帖结算（P0）

### 调整

1. 将现有页面可用性识别接入记录批量增强：详情就绪检查与详情采集失败处均检查，且核对目标帖子身份，防止详情跳转后误采别的帖子。
2. 明确区分“平台明确删除/不存在”“当前网页或账号不可查看”“网络或页面加载失败”。登录、验证页面和普通超时不能归为删帖；扫码查看等页面只证明网页访问受限时，文案不能断言作者已删除。
3. 明确删除的帖子按“已删除，跳过增强”结算；当前不可查看的帖子按“当前不可用，本轮跳过”结算。它们不计为增强成功，也不进入技术失败重试集合。
4. 保留列表采到的已有字段、历史详情和人工处置；不以空正文、空评论、数值 0 覆盖已有数据。结果分别统计采集数、增强成功数、删除跳过数、不可用跳过数、真正失败数。
5. 用“租户 + 平台 + 帖子 ID”保存服务器可查询的可用性状态、原因、证据、观察时间与复查条件；优先复用现有记录元数据。不能只记本机 `recordId`，否则换节点或产生新记录后又会重试。
6. 明确删除状态在后续分配与增强前跳过，允许人工复查或可靠的重新可访问证据解除。账号访问限制按账号/节点限定范围；不确定的网页不可用状态建议 24 小时后允许一次复查，期限为待验证的初始值，不永久屏蔽。
7. 状态写回必须可重复提交且不重复计数。写回暂时失败进入待同步恢复；不能因标记未送达就直接确认跨节点闭环，也不能重跑已完成的整词搜索。

### 验收

同一个关键词含 1 条删帖和多条正常帖时，跳过删帖并完成正常帖；下一轮及同租户其他节点再次搜到该删帖时不会重复增强。仅账号不可查看不能阻止其他有访问权限的账号。全部帖子都已删除时，显示“搜索完成，全部为已删除/不可用帖”，不显示为采集成功若干条或技术失败。

主要位置：`utils/capture/target-page-availability.js`、`utils/capture-sync.js`、`utils/capture/enhancement-retry.js`、服务端记录状态读写及增强候选查询。

## 4. 失败、重试和重新分配统一口径（P0）

| 实际结果 | 本机处理 | 后续分配 |
| --- | --- | --- |
| 已删除/当前不可用的单帖 | 保存跳过状态，继续其他帖子 | 按上述状态范围与有效期跳过该帖，不因此重跑关键词 |
| 搜索正常且确实没有结果 | 以 0 条正常完成 | 不重分配本次关键词 |
| 网络、数据库暂忙、消息短暂超时 | 延迟后有限重试，保留进度 | 仅在确认原尝试已结束或失去归属后接力未完成内容 |
| 同版本反复出现筛选或布局不支持 | 受控恢复后报告适配失败 | 停止相同条件下无效接力，修复后恢复 |
| 登录失效、需要验证 | 进入需要处理状态，保留具体原因 | 不当作删帖或一般网络故障；保留既有明确安全处理规则 |
| 用户取消、任务已被替代或终结 | 结束当前旧尝试 | 不因迟到消息重新唤起任务 |

区分“本次尝试已结算”和“关键词成功完成”：尝试结束时必须逐条归类成功、业务跳过和真正未完成；关键词只有搜索步骤完成、全部增强目标均已成功或按业务规则跳过，才算完成。仍有真正未完成则进入部分完成/失败及相应恢复流程，不把整个词伪装成成功。

采集结果、增强重试集合、检查点、服务端分配使用同一组结果语义。跨节点接力读取已保存进度和可用性状态；优先只补真正未完成的帖子。沿用现有尝试预算和冷却机制，不增加嵌套重试次数。

预算来源为 `server/routes/capture-cloud.js` 的分配策略和任务保存的资源范围。当前基线的普通技术失败上限按有效节点额度乘 2 轮计算；未配置节点范围时额度默认 2，同任务项冷却默认 5 分钟，部分不计业务次数的基础故障另有技术计数上限 2。实施必须记录每个任务实际解析出的节点额度、业务/技术已用与总次数、冷却截止时间，不把默认值当成所有任务固定上限。普通次数耗尽进入失败，技术恢复次数耗尽或适配停止规则触发进入需要处理；两者均停止自动入队。验收覆盖达到边界前后及服务重启后预算不重置。

任务页同步显示“会不会再分配、何时重试、原因、已尝试/最多次数”。例如：“已跳过 1 条删除帖，本词完成，不再分配”；“网络中断，等待恢复”；“筛选不兼容，自动接力已停止”。

验收增加一组跨层场景：客户端将删帖结算为跳过后，检查点、任务终态和服务端分配必须得出相同结果；旧尝试迟到回报不能覆盖新尝试或触发重跑。

主要位置：`utils/unattended-keyword-run.js`、`utils/capture/enhancement-retry.js`、`server/routes/capture-cloud.js`、后台任务结果展示。

## 5. 状态上报与错误展示（P0/P1）

- 区分“侧栏到扩展后台消息超时”和“扩展后台到服务器请求失败”，保留实际出错环节，避免统一归为数据库问题。
- 复用现有检查点上报 outbox 与确认机制，补查启动和终态上报的恢复链路。消息超时先核对同一任务、同一尝试是否已接受；未确认执行归属前不开始平台搜索，也不立即创建第二份任务。
- 延迟回报继续执行既有任务/尝试身份和终态校验；`terminal` 本身只是旧执行应停止的信号，只有结合该任务真正的结束原因才能判断成功还是失败。
- 将关键词内捕获的失败透传到任务、诊断导出和错误页。至少包含任务 ID、尝试 ID、节点、关键词、阶段、错误码、原始子原因、时间和下一步；筛选案例需保留 `panel_not_opened`，不能只留下通用错误或 `error: null`。
- 页面默认突出当前任务的失败；读取收藏数、评论数和可回退的视频提示降为警告，显示所属任务与时间，同类信息聚合计数。失败详情展开后能看见恢复记录。
- 评论/收藏数读取失败单独标“未读取到”，逐步补齐空值/可信度表达，避免缺失值被当成真实 0；已有数据不得被失败读取覆盖。

验收：启动回报已接受但响应丢失时不重复开工；终态回报延迟能恢复且不重复分配；任务记录和诊断导出能定位同一条最新失败；成功任务的旧执行终止消息不被显示成当前任务故障。

主要位置：`sidebar/sidebar-logic.js`、`background.js`、`utils/unattended-report-outbox.js`、`utils/diagnostics.js`、`utils/task-center.js`、任务结果展示组件。

## 6. 数据库限流微调（P1）

源码默认总预算为 10，默认单实例下 critical/general/reporting 为 4/4/2，等待分别为 500/500/250 毫秒。实际额度还受实例数和环境变量影响；执行门限位于每个 Node 进程中，不是所有服务器共用一个内存计数器。此次没有复查线上当前参数。

1. 先采集实际实例数、池配置、三类 active/queued、排队耗时、查询/事务耗时、`queue_full` 与 `queue_timeout` 数量，检查限额触发时数据库是否还有余力。
2. 优先减少重复配置读取和过密轮询，处理明确的慢查询或长事务占位。已有运行中/排队快照可复用，补齐时间与拒绝原因指标。
3. 将“数据库容量暂时不可用”改成“后台数据库请求暂忙，请稍后重试”，详情显示通道与等待超时/队列满。统一受影响接口的可重试错误响应；读取类请求遵循 Retry-After 并加入抖动退避，写请求只在有去重/幂等保证时自动重试。
4. 若证据表明只是短暂排队且接口时限允许，测试将普通通道等待从 500 毫秒调整到 1500 毫秒；这是候选值，须验证上游超时和队列积压。并发额按数据库余量及全部实例连接预算再定，保留关键操作保障。
5. 单独灰度数据库参数，对比限流率、尾部延迟、队列长度和数据库负载。限流减少但延迟/积压显著上升不算通过；恢复原参数后继续定位耗时来源。

主要位置：`server/db/query.js`、`server/db/pool.js`、受影响接口和客户端请求恢复。

## 7. 实施与验收顺序

1. 整理发布基线与已有恢复修改，在独立修复分支衔接；保存成都现场两类案例：筛选失败页面、搜索残留删帖。核对实际加载的扩展版本/构建，避免测到旧包。
2. 第一批完成搜索适配、单帖可用性结算、关键词/服务端重试规则与错误原因透传。围绕正常/删帖混合、全部删除、暂时不可用、筛选未生效、切节点继续、迟到回报补充行为测试，并验证已有日期校验和正常采集不回退。
3. 在成都同一浏览器配置先验一个正常词，再验“安吉星”及残留删帖案例；检查搜索、增强、结果计数和后续分配。用第二个测试节点确认明确删帖状态能共享、账号限制不会误伤其他账号。
4. 再处理上报恢复余项、缺失数值展示和数据库观测/调参；运行仓库要求的回归与受影响的服务端集成检查。真实页面验收与自动化测试分别记录，不以模拟页面测试代替成都实测。
5. 小范围发布配套扩展与服务端，按实际调度间隔覆盖至少两次正常巡检，并观察一次失败恢复链路。保存改动前版本与参数；回退时保留已采数据和业务跳过记录，检查旧版本兼容性。

交付通过的标准：同类搜索能稳定进入有效筛选流程；1 条坏帖不再导致整词重复接力；真实未完成不会被写成成功；当前失败原因和下一步在任务页可见。数据库限流的具体根因、成都删帖跨次任务链及真实页面适配结果，须在实施阶段用现场证据补齐。
