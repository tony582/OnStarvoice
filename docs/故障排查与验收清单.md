## 1. 排查顺序

任何采集问题都按以下顺序判断：

1. **版本**：客户加载的是不是当前生产 Extension；
2. **租户**：激活码、Agent 和后台当前租户是否一致；
3. **Agent**：是否有新鲜设备心跳，是否停用/退役；
4. **命令**：任务是否已创建、分配、领取和回执；
5. **本地账本**：Extension 是否生成同一任务；
6. **页面状态**：平台页面、登录态、弹窗、风控或删除状态；
7. **业务进展**：关键词、作品、评论和增强是否真实推进；
8. **云端写回**：目标 ID、尝试编号和进度序号是否通过所有权校验；
9. **聚合状态**：父任务是否按工作项终态正确结算。

排查证据至少保留：

- 发生时间和时区；
- 租户、Agent 显示名称和短 ID；
- Extension 版本；
- 云端任务 ID、命令 ID、工作项 ID；
- 当前页面 URL；
- Extension 诊断日志；
- 后台任务详情、事件和最近心跳；
- 可复现步骤和截图。

## 2. 常见症状

### 2.1 Extension 显示的版本或行为仍是旧版

可能原因：

- 修改了源文件但没有同步到 `extension-build/`；
- 浏览器仍加载旧目录或未点“重新加载”；
- 客户收到的是历史 ZIP；
- 本地联调包与生产包混用。

处理：

```bash
# 本地联调
scripts/sync-extension-build.zsh local

# 生产快照
scripts/sync-extension-build.zsh production

# 客户交付 ZIP；脚本会重建生产快照并拒绝 localhost
scripts/package-extension.zsh
```

浏览器应加载 `extension-build/`，不要直接交付仓库根目录，也不要手改 `extension-build/`。

### 2.2 Agent 显示在线，但任务没有下发

“在线”只代表心跳新鲜。继续检查：

- Agent 是否属于当前租户；
- 是否支持目标平台和远程任务能力；
- 是否被停用或退役；
- 是否已有执行中任务或排队任务；
- 云端命令是 `pending`、`claimed`、`running`、`failed` 还是 `expired`；
- Extension 本地任务中心是否出现相同任务 ID；
- 浏览器 Profile 是否换过激活码或租户。

永久不会再上线的旧节点应退役或删除；否则分配给它的任务会一直等待。

### 2.3 点击继续后又从第一个关键词开始

检查：

- 旧任务是否真的上报了检查点；
- `currentKeyword`、完成/失败/跳过集合和关键词结果是否存在；
- 恢复任务是否引用正确的父任务和控制任务 ID；
- 新尝试编号是否递增；
- 旧心跳是否覆盖了新尝试。

正确行为是从最近有效检查点继续，仅执行剩余项。没有检查点时只能从可证明的最后业务事件恢复，不能假装精确续跑。

### 2.4 任务一直执行中，但业务没有进展

比较三种时间：

- 设备心跳新、任务心跳旧：任务循环没有运行；
- 任务心跳新、业务进展旧：循环存活但页面或步骤卡住；
- 三者都旧：浏览器或设备离线。

还要查看本地采集锁、平台弹窗、调试会话、页面 URL 和当前工作项。不要只看进度条。

### 2.5 “采集结果与目标作品标识不一致”

这是保护性拦截，不应关闭。常见原因：

- 抖音删除页自动播放了下一条；
- 页面跳转到推荐作品；
- 点击评论时误进入 AI 抖音页；
- 详情页仍在过渡状态；
- 任务结束后页面循环播放；
- URL、页面状态中的作品 ID 与目标 ID 取值来源不一致。

处理：

1. 先停止自动播放或跳转；
2. 重新定位目标 URL；
3. 同时校验 URL ID、页面作品 ID 和工作项目标 ID；
4. 确认一致后才允许写回；
5. 已删除目标标记为不可用，不采集下一条替代内容。

### 2.6 抖音“服务出现异常”

这是搜索服务临时异常，不等同账号风控。当前关键词可记录为搜索异常并继续下一个词，不应导致整项任务永久停止。

如果页面明确出现验证码、安全验证、访问频繁或风险码，则进入人工处理，不能继续自动搜索，也不能静默换 Agent 反复试探。

### 2.7 抖音作品不存在并开始倒计时播放下一条

必须在倒计时结束前识别“图文/作品不存在”页面：

- 标记目标为 `deleted` 或 `page_unavailable`；
- 保存不可用时间和原目标 ID；
- 取消自动播放/导航；
- 禁止把下一条作品写回当前工作项；
- 继续任务时跳过这个已结算工作项。

### 2.8 抖音评论按钮进入“AI 抖音”

抖音详情页结构会变化。评论入口必须同时满足：

- 位于作品交互区；
- 图标、可访问名称或邻近计数符合评论语义；
- 不位于顶部“AI 抖音”导航；
- 点击后评论面板或评论列表确实出现。

未验证面板出现时不能开始评论读取，也不能把推荐内容当评论。

### 2.9 小红书二维码或 “Sorry, This Page Isn't Available”

先区分：

- 笔记删除/不可用：记录业务终态，保留历史；
- 需要 App 扫码：当前 Web 页面不可访问，记录不可用；
- 登录或安全拦截：进入人工处理；
- 页面暂未完成加载：短暂等待后再判断。

不能在删除页和任务完成页之间反复切换。关闭运行面板时应回到原搜索页或安全落地页。

### 2.10 搜索无结果或筛选后无结果

“指定筛选范围内没有内容”是有效业务结果：

- 当前关键词标记完成或跳过；
- 不计入未完成；
- 继续下一个关键词；
- 结果说明应使用“范围内未发现”，不要显示系统错误。

### 2.11 官方账号评论巡查失败

重点检查：

- 官方账号资料是否配置真实主页 URL；
- URL 是否属于登记的平台和目标账号；
- 任务日期范围是否在详情页校验，而不是仅依赖列表页；
- 列表无法确认发布日期时是否进入详情核验；
- 发布日期未知的作品是否被排除；
- 评论读取数量是否为“本次已读样本”，而不是平台显示的评论总数；
- 账号主页是否被错误替换为搜索结果、客服电话或其他账号作品。

默认日期范围为近 7 天，单次连续范围最多 30 天；作品上限 `1–20`，每篇评论读取上限 `1–100`。

### 2.12 负面巡查显示“暂时无法读取”

检查：

- 是否至少有一条互动快照；
- 负面判断是否已完成；
- 自动深度分析任务是否成功；
- 当前租户是否能读取该内容的分析和快照；
- 迁移数据是否把内容复制到新租户但漏了分析、快照或评论关联。

第一条快照只能建立基线；至少两条快照才能计算评论、点赞、收藏和转发增量。已删除内容仍应显示历史快照和删除状态。

### 2.13 负面内容被自动转成工单

当前规则是不自动转工单。只有用户明确点击“转工单”并成功提交，才创建工单。

如果出现自动转单，检查：

- 是否复用了历史测试数据；
- 迁移时是否复制了 `ticket_id` 或处理状态；
- 后端采集/分析流程是否误调用工单接口；
- 前端是否仅因存在风险就把状态映射成“已转工单”。

转工单后必须继续展示源内容、评论、官方回复、快照历史、巡查/分析记录和处理时间线。

### 2.14 AI 开关打开，但看不到 AI 介入

Extension 的前置筛选是“规则优先、AI 批处理、失败放行”：

1. 确定性规则先筛选；
2. 保存候选列表；
3. DeepSeek 批量判断；
4. 只跳过高置信无关项；
5. 超时、服务异常或判断不清全部继续采集。

确认服务端：

- `LLM_PROVIDER=deepseek`；
- `LLM_API_KEY` 有效；
- `LLM_API_ENDPOINT` 和 `LLM_MODEL` 正确；
- 租户没有关闭前置筛选；
- 请求没有因并发、日限额或超时被降级；
- 任务事件中存在 AI 批处理或 fail-open 记录。

AI 无事件时不能在 UI 中假装“AI 已筛选”。安全、品牌等单字命中不能直接判断内容有风险。

### 2.15 社交账号识别错误或一个账号绑定多个 Agent

自动识别是尽力而为，不能代替人工确认。检查：

- Extension 读取的是当前登录账号而非帖子作者；
- 平台账号 ID、昵称和主页 URL 是否完整；
- 手动绑定模式是否仍允许心跳自动增删；
- 同一账号是否因 ID 格式不同生成重复记录；
- 一个 Agent 是否同时被多个账号记录占用。

人工绑定后，未勾选的 Agent 不应被心跳自动加回；需要更换时显式编辑绑定。

### 2.16 后台显示旧状态或旧统计

后台部分页面按约 15 秒轮询。先手动刷新并核对接口响应，再判断是否是 UI 缓存。

如果 Extension 已完成而后台仍显示失败，核对：

- 最新尝试是否覆盖旧尝试；
- 任务详情是否仍展示上一次尝试；
- 成功回执是否因命令过期被丢弃；
- 工作项已成功但父任务聚合未重新计算。

### 2.17 生产页面仍是旧版

`deploy/deploy.sh` 已退役并会在任何构建、网络或写入动作前退出 64；它不发布 Admin、Dashboard 或 Extension。退役前的历史实现也未覆盖 Dashboard/Extension。

检查：

- `web/admin/dist` 是否来自当前提交；
- Nginx/服务端实际静态目录；
- 浏览器缓存；
- PM2 运行路径和提交；
- dashboard 是否需要单独构建；
- Extension 是否单独打包并由客户 Reload。

### 2.18 数据库迁移异常

P2-D 主线代码会在 PostgreSQL session advisory lock 下升级 tracker、校验 checksum，并按文件事务执行非 reset 迁移。生产尚未部署该代码，仍为迁移 066 和单一 `all`；不能把下面的 CLI 当成当前线上已有能力。

先保存错误码和完整日志，重点区分：

- `DATABASE_MIGRATION_LOCK_TIMEOUT`：另一个新迁移进程仍持锁或没有正常释放；
- `DATABASE_MIGRATION_CHECKSUMS_NOT_READY`：旧库尚未显式完成 v066 adoption；
- `DATABASE_MIGRATION_CHECKSUM_MISMATCH`：数据库登记值与当前文件不一致；
- `DATABASE_MIGRATION_BASELINE_*`：冻结清单本身缺失、损坏或历史文件被改写；
- `DATABASE_RESET_MIGRATIONS_DISABLED`：环境误设 `ALLOW_RESET_MIGRATIONS=1`；
- `MAINTENANCE_DATABASE_URL_REQUIRED`：生产 Maintenance 没有显式非空 `DATABASE_URL`；该错误发生在任何锁或数据库访问前，禁止用本地默认连接串临时绕过。

只读核验使用：

```bash
PROCESS_ROLE=maintenance npm --prefix server run maintenance -- verify
```

`node server/db/migrate.js` 直接入口已禁用；`migrate` 是写入命令，不是排障探针。生产禁止为了“让迁移通过”补写 `schema_migrations`/checksum、修改 baseline、删除 legacy marker 或设置 `ALLOW_RESET_MIGRATIONS=1`。首次 v066 adoption 只能在完整备份、冻结版本核对、停止旧 migrator/长期进程并取得明确生产授权后执行；不能滚动混跑。迁移与三个 legacy once marker 的桥接说明见 [数据库与迁移说明](./数据库与迁移说明.md)。

如果 SAIC-GM relabel 出现 `MAINTENANCE_TASK_PARTIAL_FAILURE`，应确认 `maintenance_runs` 保持 `failed` 且没有 success/rollback marker，并保存逐条 `[Relabel]` 错误。该任务会 fail-closed，但先前成功的单项不会自动回滚；任何 prior failed 或遗留 running 都会在后续调用触发 `MAINTENANCE_TASK_RESTORE_REQUIRED`。此时必须保持旧/新长期进程和所有写入入口停止，恢复该任务执行前的整库备份，并确认 ledger 与业务数据一起回到执行前状态后再重新授权。禁止自动重跑、手工标记成功，或回滚代码后直接启动旧 `all`；旧版本可能因没有成功 marker 而再次执行部分任务。

legacy import 留下遗留 `running` 或除 `LEGACY_SQLJS_DATABASE_NOT_FOUND` 外的 `failed` 后，下一次调用应以 `MAINTENANCE_TASK_RESTORE_REQUIRED` 拒绝。必须恢复该任务开始前的整库备份，并确认失败 ledger 和业务数据均随恢复回到执行前状态后再重新授权；禁止删除失败记录、补 success/marker 或以“写入幂等”为由直接重跑。固定文件缺失是唯一允许直接修复来源后重试的错误：先补齐并复核代码固定路径的文件，再重新取得执行授权，仍不得伪造 success。

旧 sql.js import 或 comments backfill 的 JS 文件直接执行会以退出码 2 拒绝；只能使用 Maintenance allowlist/package alias，并满足 offline 确认和锁。确定性 alert UUID 与幂等 upsert 只减少重复写入，不扩大上述重试例外。legacy/CSV record upsert 均设置 `localizeMedia: false`；需要媒体落地时另行授权受审计的 `recent-media-backfill`，不要在锁外手工触发下载。`user:create-admin` 必须显式 `PROCESS_ROLE=maintenance`，生产还必须有非空 `DATABASE_URL` 和 checksum-ready schema。历史 `repair-*.sql`/tenant-specific SQL 只作证据，禁止直接在生产重放。

Extension CSV importer 的帮助/dry-run 不连接数据库，因此预览成功不代表 commit 可执行。`--commit` 若缺少显式 maintenance role、生产非空 `DATABASE_URL` 或 `MAINTENANCE_OFFLINE_CONFIRMED=1`，应保持拒绝；禁止为了绕过错误改成本地默认库或只设置确认变量。写入路径会取得 `all` 执行权锁并做 checksum readiness，但仍须人工确认旧 API/Worker/其他写入入口停止。该 importer 不写 `maintenance_runs` 且不是全量单事务；出现部分失败时先保存输出、按目标租户核对已写入行，再决定是否经重新授权重试，不能假定非零退出已自动回滚。

## 4. 发布门禁

### Gate A：范围与工作区

- [ ] 当前分支、提交和工作树已记录；
- [ ] 用户未提交修改已明确保护；
- [ ] 变更文件与需求一一对应；
- [ ] 没有凭证、Cookie、激活码或生产数据进入 Git；
- [ ] 迁移是否破坏性已确认。

### Gate B：代码与构建

- [ ] Extension 全量逻辑测试通过；
- [ ] Chromium 快照冒烟通过；
- [ ] 管理后台构建通过；
- [ ] 服务端目标测试通过；
- [ ] 新迁移在空库和升级库验证；
- [ ] 真实双进程迁移锁、checksum 篡改与锁释放已在隔离 PostgreSQL 验证；
- [ ] API、任务状态与 UI 文案一致。

### Gate C：Extension 交付

- [ ] 根目录源代码先同步到 `extension-build/`；
- [ ] `manifest.json` 与 `extension-build/manifest.json` 版本一致；
- [ ] 生产包内没有 localhost；
- [ ] 客户 ZIP 只由 `scripts/package-extension.zsh` 生成；
- [ ] Chrome/Edge 均完成 Reload 与关键流程冒烟；
- [ ] 激活、心跳、远程任务、停止和恢复已验证。

### Gate D：生产发布

- [ ] 已取得本次发布授权；
- [ ] 数据库、上传目录和当前发布包已备份；
- [ ] 备份可读取，回滚命令已准备；
- [ ] 迁移完成且无意外 reset；
- [ ] 若包含 P2-D，旧 migrator/长期进程已停止，显式 adoption 与 verify 分步完成，未滚动混跑；

## 5. 生产冒烟

发布后至少验证：

1. `GET /api/health` 正常；

3. Agent 心跳、在线/离线判断正常；
4. 创建一次性任务并在 Extension 出现；
5. 中止和继续状态双向一致；
6. 多 Agent 工作项不重叠；
7. 小红书/抖音各完成一条只读采集；
8. 删除内容、无结果和风控三种状态可区分；

10. 官方评论巡查只读取目标官方账号和指定日期范围；

## 6. 回滚原则

- 先停止继续扩大影响的调度入口，不先删除数据；
- 静态前端可回滚到上一构建；
- 服务端回滚必须确认新迁移是否向后兼容；
- 数据库恢复前先保存故障现场和当前库备份；
- Extension 回滚需同时考虑本地账本格式和服务端协议兼容；
- 不使用 `git reset --hard`、强制清库或删除客户任务作为故障修复手段。
