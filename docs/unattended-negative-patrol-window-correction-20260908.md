# 无人巡检负面巡查 7 天范围修正

分支：`codex/hotfix-negative-patrol-every-run-20260908`。

## 问题与最终确认

初版以帖子发布时间选取近 7 天内容，并额外按处理状态设置 1/3/7 天间隔、共享当天成功记录跳过后续轮次。用户最终明确：**没有复查间隔，7 天只表示内容范围**。

每轮以启动时刻 T 选取首次采集入库时间位于 `[T−168小时, T)` 的负面内容。使用 `records.created_at`：首次入库由数据库写入，后续采集、巡查只更新其他采集/更新时间，不延长这 7 天范围。上月发布但最近首次入库的帖子可以参与；早于窗口首次入库、最近复查的帖子不会因此重新进入。缺少发布时间不影响范围判断。本轮启动后新入库的内容下轮参与。

## 修改后的执行规则

- 继续按当前客户、平台、计划关键词以及当前负面判定筛选，人工修改优先。明确非监控、已归档、已失效等原有资格排除保持有效。
- 所有合格的负面内容每轮参与，不因今天已经巡查或冷处理、飞书表、已回复等处理状态而等待 1/3/7 天。保留人工处理状态，不读写飞书。
- 前次正式成功记录仅用于轮转排序、结果基线及审计，不再作为时间门槛。预估、建队列、节点领取使用一致规则。
- 同一轮同帖只生成一项；同一帖子同时只交给一个节点。关键词优先，空闲节点接续负面巡查。
- 失败冷却、需要人工处理、活动租约及结果落库证据保护保持有效。这些异常或并发条件与业务复查间隔无关。
- `next_due_date` 不再用于资格判断；新的成功记录写入空值。旧表的 `cadence_days=1` 仅用于兼容既有约束，无需新增迁移或批量改写历史数据。
- 新轮次保存 `windowBasis=first_collected_at`；历史轮次保留原有发布时间范围及跳过事实。修复不重写、重跑已经结束的轮次。
