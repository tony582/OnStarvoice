## 3. P3-1H 发现的锁顺序缺口

Profile 任务存在多条会相遇的写路径：定时调度、人工关注账号、人工官方账号、canonical retry、任务中心终态投影和旧 Monitor finish。基点中这些路径的业务锁顺序不一致：

| 路径 | 修复前的关键顺序 | 风险 |
|---|---|---|
| 定时 Profile 调度 | subscription → Agent → execution | 与先占 Agent 的 retry 形成 Agent/subscription 反序等待。 |
| 人工关注账号调度 | subscriptions → active executions → Agent | 与 retry 和其他 Profile 生产者顺序相反。 |
| 人工官方账号调度 | subscription/account → Agent → execution | 与先占 Agent 的路径顺序相反。 |
| canonical retry 的 Profile execution 续建 | Agent 之后 execution → subscription | 与调度路径存在 execution/subscription 反序；多记录输入也没有统一的稳定排序。 |
| 任务中心失败、停止与结果投影 | items/attempts → executions → subscriptions | 与已统一为 subscription → execution 的生产者形成直接反序；多条结果逐条投影还可能持有前一条 subscription 后再等待下一条 item。 |
| 旧 `/api/monitor/executions/:id/finish` | execution → subscription | 与任一 subscription → execution 入口形成直接死锁边；同时旧入口不应完成任务中心已经接管的 execution。 |

只改定时调度不能消除同一类死锁，因为人工入口、retry 和终态入口仍会访问同一组 Agent、subscription 与 execution 资源。因此 P3-1H 将所有本轮识别到的 Profile 路径统一到两个兼容前缀，并共同收敛到 `subscription → execution`：

```text
生产/重试：Agent execution-slot/advisory + Agent row
  → source/parent/item/attempt lineage fences（适用时）
    → subscription（多条时按 id 稳定排序）
      → existing execution（多条时稳定排序）
        → 新任务 / Command / execution 物化

任务中心终态：task/item/attempt（多条时稳定排序）
  → subscription（多条时按 id 稳定排序）
    → execution（多条时按 id 稳定排序）

旧 Monitor finish：subscription → execution
  且拒绝任何已由 capture_task_items 关联的 execution
```

## 4. 实施内容

### 4.1 定时 Profile 调度

- due subscription 候选发现改为只读阶段；每个 subscription 使用独立事务处理；
- 先取得兼容 Agent 的 execution-slot/advisory 与 Agent row，再锁定并重新验证 subscription，最后锁定可复用 execution；
- 每个 Agent 候选使用 savepoint；候选不合格时回滚并释放该候选在当前事务取得的锁，避免一次选择过程积累多个 Agent 锁；
- stale execution reconciliation 保持独立事务，避免先锁 execution 后再进入 Agent 选择。

### 4.2 人工 Profile 入口

- 关注账号入口先以无锁快照确定平台需求，锁定 Agent 后再按 subscription id 稳定锁定并复核 subscription，最后按 subscription/execution id 稳定锁定 active execution；
- 官方账号入口先以无锁快照确定候选和平台，锁定 Agent 后重新选择并锁定准确的 subscription/account，再进行任务和 execution 物化；
- 任何快照与加锁后选择不一致、状态变化或平台不兼容均 fail closed，不使用旧快照继续派发。

### 4.3 canonical retry

- Profile retry 先收集并验证续建条目；
- 在既有 Agent/source/parent/item/attempt 前置锁之后，按 id 稳定锁定全部 subscriptions，再按 id 稳定锁定全部 previous monitor executions；
- 去除旧的 execution `SKIP LOCKED` → subscription `FOR SHARE SKIP LOCKED` 旁路，避免因静默跳过而生成不完整的 Profile execution 投影；
- 更新旧 execution、插入新 execution、更新目标绑定仍位于同一事务中，不改变 API 或数据库 schema。

### 4.4 终态投影与旧 Monitor finish

- 新增共享的 Profile work 锁入口：先按 `ordinal, id` 锁定当前 execution task 的 items，再按 `item_id, attempt_number, id` 锁定 attempts，之后按稳定顺序锁定 subscriptions 与 executions；
- dispatch failure、停止投影、设备结果投影与缺失结果 fallback 都在任何 monitor execution 更新前取得完整 work 锁，避免多账号逐条处理跨回 item 锁；
- 旧 `/api/monitor/executions/:id/finish` 先锁 subscription，再更新单条 execution；更新条件增加与旧 start/list 一致的任务中心关联栅栏，不能绕过任务中心终态协议；
- 订阅同步、指标、cursor 与成功后的官方评论快照行为保持原有事务语义；没有修改端点、请求体、响应形状或 schema。

## 5. 隔离验证

验证环境：Node 24.19.0（本机 PostgreSQL）、Node 24.12.0（CI 同版非 PG 门禁）、Node 18.20.8、本机 PostgreSQL 17.9，均使用一次性独立测试库并在结束后删除。

| 验证 | Node 24 | Node 18.20.8 |
|---|---:|---:|
| Profile/route/capture focused 非 PG | 179/179 | 179/179 |
| 完整非 PG 回归 | 1769/1769 | 1769/1769 |
| Profile scheduler、canonical retry 与 legacy finish 定向真实 PG 竞态（含既有 HTTP retry 竞态） | 3/3 | 3/3 |
| 完整真实进程拓扑演练 | 1/1 | 1/1 |
| 完整 PostgreSQL integration phase | 44/44 | 44/44 |

真实 PostgreSQL 竞态通过外部 subscription barrier 构造可观察等待链：canonical retry 已持有目标 Agent advisory lock 并等待 subscription，定时调度随后等待同一 Agent；释放 barrier 后 retry 完成，调度返回 Agent busy。新增 legacy finish 用例在 finish 等待 subscription 时，由 barrier 事务对 execution 执行 `FOR UPDATE NOWAIT` 并成功，直接证明 finish 尚未持有 execution；释放后 metrics、cursor 与 subscription 时钟均正确提交。测试同时断言只有一个 retry task/Command/event、一个 active monitor execution、幂等重放不新增状态，并核对所有测试会话与 advisory lock 残留清理。

Node 24 完整 PostgreSQL 首轮中，本轮新增竞态均已通过，但既有 `process-runtime-split` 在等待子进程退出时偶发超时，整轮为 43/44；该用例随后在全新空库单独复跑为 1/1，并再次使用第三个全新空库完成完整 runner，最终为 topology 1/1、integration 44/44。Node 18.20.8 的独立空库首轮即为 1/1、44/44。所有专用数据库、相关会话与 advisory lock 最终均为 0 并已删除；95 文件 production Extension snapshot 只用于一致性校验，验证后已移出 worktree，未修改 Extension 源码、版本或交付物。
