## 1. 稳定版运行边界

### 1.1 当前由哪些运行面组成

| 运行面 | 源码/产物 | 本地入口 | 生产入口或用途 |
|---|---|---|---|
| Node.js 后端 | `server/` | `http://localhost:3001`（集成联调约定） | `https://voice.minilife.online/api/*` |
| 管理端 | `web/admin/` | `http://localhost:5173` | `https://voice.minilife.online/admin/` |
| 数据看板 | `web/dashboard/` | `http://localhost:5174` | `https://voice.minilife.online/dashboard/` |
| Extension 源码 | 根目录脚本、`sidebar/`、`utils/` 等 | 不直接加载 | 构建输入 |
| Extension 可加载快照 | `extension-build/` | 浏览器“加载已解压的扩展程序” | 本地联调或打包输入 |
| Extension 客户包 | 打包脚本生成的 ZIP | 不用于开发 | 交付客户安装/升级 |
| PostgreSQL | `server/db/` 迁移驱动 | 本地数据库 | 生产独立数据库 `onstarvoice` |
| 运行时媒体 | `MEDIA_DIR` | 默认仓库外或本地配置目录 | `/opt/onstarvoice/media` |

### 1.2 三套端口口径

这三个端口不能混为一谈：

| 场景 | 端口 | 原因 |
|---|---:|---|
| 后端代码在没有 `PORT` 时的兜底值 | `3000` | `server/index.js` 的默认值 |
| 本地完整联调 | `3001` | 管理端、数据看板的 Vite 代理和本地 Extension 配置均指向 `3001` |
| 生产 PM2 进程 | `3002` | Nginx 将生产域名反向代理到本机 `3002` |

因此：

- 单独验证 Express 启动时可以使用代码兜底的 `3000`；
- 同时联调管理端、数据看板或 Extension 时，后端必须设置为 `3001`；
- 生产环境文件必须使用 `PORT=3002`；
- 不要通过临时修改源码中的端口来切换环境，应使用环境变量。

### 1.3 旧库存发布脚本的明确边界

> `deploy/deploy.sh` 已退役为 fail-closed 墓碑入口：首个可执行动作只打印 `[DeployBlocked]` 并退出 64，不构建、不联网、不读发布输入、不写文件。下面保留的是退役前实现的历史风险审计，**不是当前行为，也不是生产发布指令**。生产现状包含 hotfix 基线上的限定文件覆盖；任何新发布自动化都必须另行设计、评审并演练，不能恢复这段旧实现。

退役前的历史实现曾尝试发布：

- `server/`；
- `web/admin/dist/`；
- 仓库中的 `images/`；
- `server/.env.production`；
- 数据库迁移；
- PM2 进程 `onstarvoice`。

该历史实现当时**不会**：

- 自动备份生产数据库；
- 构建或同步 `web/dashboard/dist/`；
- 打包或升级客户浏览器中的 Extension；
- 做零停机或滚动重启；
- 在迁移和进程启动后自动执行完整健康门禁；
- 自动把数据库回退到发布前状态；
- 保证一定使用 Node.js 24 或 20。

脚本只会尝试把若干本机常见的 Node 24/20 安装路径放到 `PATH`；如果这些
目录不存在，它仍会使用调用者当前 `PATH` 中的 `node`。所以发布前必须人工
执行 `node --version`，不能把脚本中的路径探测当作版本保证。

## 3. 首次启动

### 3.1 安装后端依赖并迁移

```bash
cd server
npm ci
PROCESS_ROLE=maintenance npm run maintenance -- migrate
```

P2-D 主线代码的迁移执行器会取得数据库级 advisory lock，读取 `server/db/migrations/*.sql`，按文件名排序，在 `schema_migrations` 中记录版本与 checksum。直接运行 `node db/migrate.js` 已禁用。正常开发应保持：

```dotenv
ALLOW_RESET_MIGRATIONS=0
```

包含 `reset` 的迁移不会从普通路径执行；把 `ALLOW_RESET_MIGRATIONS` 设为 `1` 会 fail-closed，而不是解锁 reset。更详细的迁移规则、v066 adoption 和恢复边界见
[数据库与迁移说明](./数据库与迁移说明.md)。

已有 v066 本地/隔离数据库首次进入 P2-D 主线代码时，必须先核对备份和冻结基线，再显式执行：

```bash
PROCESS_ROLE=maintenance npm run maintenance -- migrate --adopt-v066-checksums
PROCESS_ROLE=maintenance npm run maintenance -- verify
```

首次 adoption 只把 `main@c47800f` 的冻结 SQL 字节设为后续比较锚点，不能证明旧数据库当年实际执行的字节完全相同。不要在生产或来源不明的数据库上把该命令当成自动修复。

生产 Maintenance 必须同时获得显式 `PROCESS_ROLE=maintenance` 和受控环境中的非空 `DATABASE_URL`。缺失或只含空白的连接串会在取得任何角色锁、迁移锁或访问数据库前以 `MAINTENANCE_DATABASE_URL_REQUIRED` 拒绝，不会回落到本地默认库。

### 3.2 启动后端

开发监听：

```bash
cd server
npm run dev
```

非 watch 方式：

```bash
cd server
npm start
```

验证：

```bash
curl --fail --silent --show-error http://localhost:3001/api/health
```

预期返回 JSON，且 `ok` 为 `true`。健康接口只证明进程可响应，不证明数据库
业务、AI、邮件或 Extension 全链路已经可用。

`main@c47800f` 提供以下拆分候选入口；拆分联调时应在三个独立终端分别运行：

```bash
cd server
PROCESS_ROLE=api PORT=3001 npm run start:api
PROCESS_ROLE=scheduler npm run start:scheduler
PROCESS_ROLE=ai-media npm run start:ai-media
```

三个入口只面向已经完成迁移与 checksum adoption 的本地/隔离数据库；独立角色会把仓库内全部非 reset 迁移文件与 `schema_migrations` 做只读版本/checksum 全集核对，缺少版本、checksum 或发生不匹配都会拒绝启动，不运行迁移或 bootstrap。API 提供 `/api/health`、`/api/health/live` 和 `/api/health/ready`，Worker 不监听公网 HTTP。P2-C/P2-D 虽已进入主线，但尚未部署。这些都不是生产启动指令，本地拆分联调必须显式使用非生产数据库并为每个进程设置匹配的单一角色。

## 4. 本地联调顺序

建议固定顺序，减少“页面在线但任务不执行”的误判：

1. 启动 PostgreSQL；
2. 运行数据库迁移；
3. 以 `PORT=3001` 启动后端；
4. 验证 `/api/health`；
5. 启动管理端；
6. 需要时启动数据看板；
7. 生成本地 Extension 快照并在浏览器 Reload；
8. 登录目标租户；
9. 验证 Agent 心跳和在线状态；
10. 用少量、低风险数据做完整业务冒烟。

本地联调不是生产演练。尤其不要用真实客户账号做高频搜索、增强或评论读取
压力测试。

## 5. Extension 开发、加载与打包

### 5.1 不要直接加载源码根目录

当前可加载、可交付的 Extension 运行面是 `extension-build/`。根目录中的
`background.js`、`sidebar/`、`utils/`、`manifest.json` 等是构建输入。
修改源文件后必须重新同步快照。

### 5.2 生成本地联调快照

在仓库根目录：

```bash
scripts/sync-extension-build.zsh local
```

该命令会：

- 从当前源码重建 `extension-build/`；
- 写入本地 API 地址；
- 校验快照结构和 JSON；
- 检查不应进入交付包的敏感或开发文件。

随后在 `chrome://extensions` 或 `edge://extensions`：

1. 开启开发者模式；
2. 选择“加载已解压的扩展程序”，目录为 `extension-build/`；
3. 已加载时点击 Reload；
4. 重新打开目标平台页面。

只重启后端不会自动让已加载 Extension 使用新代码。

### 5.3 生成生产快照

```bash
scripts/sync-extension-build.zsh production
```

生产快照必须只指向：

```text
https://voice.minilife.online
```

发布给客户前必须确认快照中没有 `localhost`、本地 Token、测试激活码或客户
业务数据。

### 5.4 生成客户 ZIP

```bash
scripts/package-extension.zsh
```

脚本会重新生成并校验生产快照，再输出客户安装包。不要把旧 ZIP 手工改名
冒充新版本。

每次交付记录：

- `manifest.json` 版本；
- Git 提交；

#### 9.4.1 P2-B 已合并代码的角色与拓扑前置条件

P2-B 已于 2026-08-15 通过 PR #21 合并到主线，merge commit 为 `7c3e47ef1717a3fc498d63a1e3b7952e9100ecee`，但**尚未部署**。生产仍按 1.4 节的 P2-A1 限定快照运行，也不能假定线上已经配置 `PROCESS_ROLE` 或持有角色锁。仓库内 `deploy/process-topology.production.json` 是可审查、可由 CI 校验的**期望发布拓扑**，不会读取 PM2、线上 `.env` 或父进程覆盖值。

未来只有在另行获得生产授权后，才按以下顺序执行：

1. 在旧代码仍运行时，先把有效生产环境预置为 `PROCESS_ROLE=all`；旧版本会忽略它；
2. 同时核对 `.env`、PM2 配置和父进程环境，确保没有空值或其他角色覆盖；
3. 对 staging 中的发布清单执行 `node scripts/check-process-topology.mjs deploy/process-topology.production.json`；
4. 独立读取真实 PM2 配置，确认只有一个名为 `onstarvoice` 的实例；静态 JSON 通过不能替代此项；
5. 首次从旧 P2-A 运行面切到 P2-B 时，旧进程本身不持角色锁；必须先停止旧进程并确认旧 PID 完全退出，再启动新进程，严禁重叠式 reload。P2-B 上线后的后续切换中，新旧 P2-B 进程才会通过角色锁拒绝重叠执行权；
6. 启动日志必须确认 `role=all` 且 `executionLocks=scheduler,ai-media`，并在数据库中只读确认只有一个角色锁会话；

角色锁会额外长期占用一个 PostgreSQL 连接，只防止跨进程重复拥有 Scheduler/AI 执行权；它不解决同一 Cron 回调自身重叠、迁移并发或完整 readiness。P2-B 无迁移，失败时回切完整旧应用目录并保留数据库；不要因本批代码失败恢复数据库。

   ```bash

   ```

`--adopt-v066-checksums` 只把 `main@c47800f` 中冻结的 SQL 字节登记为后续比较锚点，不能证明生产当年执行的历史字节。adoption 前必须人工比对已登记版本、发布档案和冻结清单。

`maintenance run <allowlisted-task-id>` 与 `startup-reconcile` 涉及 runtime-owned 数据时，还要求 `MAINTENANCE_OFFLINE_CONFIRMED=1`，并尝试取得 Scheduler 与 AI/Media 执行权锁：

```bash

  npm --prefix server run maintenance -- startup-reconcile
```

该变量只是操作者确认，锁也只能排斥持同类锁的新进程；它们都不能自动证明旧 API/Worker/migrator、外部请求或人工脚本已停止。必须在命令外人工确认。P2-D 兼容 `all` 已保留受锁迁移、阻塞式 publish timestamp 维护与 immediate/15 秒/25 秒 adapter，因此首次发布不应为了“保险”额外执行 `startup-reconcile`；只有某个明确维护任务另行获批时才运行相应 allowlisted 命令。

三个既有 once（publish timestamp、comment safety、SAIC-GM relabel）保留固定 rollback bridge：新任务成功时，runner 用同一条 SQL 原子更新 `maintenance_runs=succeeded` 并写对应 legacy marker，使旧版本回滚后不会把它当作从未执行；旧 marker 已存在时则 adoption 为新 ledger。新维护任务不得沿用该机制。未来上线观察要同时核对 ledger 和这三个 marker，不能只看其中一侧。

SAIC-GM relabel 的部分失败现在 fail-closed：任一记录失败会让 run 记为 `failed` 并保持无 success/rollback marker，但此前已成功处理的记录不会自动反向回滚。该 once 的任何 prior failed 或遗留 running 都会让下一次兼容启动/CLI 调用以 `MAINTENANCE_TASK_RESTORE_REQUIRED` 拒绝。上线观察必须检查 `MAINTENANCE_TASK_PARTIAL_FAILURE`、`maintenance_runs.error_summary` 和 `[Relabel]` 日志；发现异常后立即保持旧/新长期进程和写入入口停止，恢复任务前整库备份，确认 ledger 与业务数据一同回退，再重新申请执行授权。禁止自动重跑、手工补 marker/ledger，尤其禁止为了“快速恢复服务”回滚代码并启动旧 `all`，因为旧代码可能在缺失 marker 时再次执行该任务。

历史 sql.js 导入与评论 workflow backfill 已经收口到 Maintenance allowlist。前者是 once `legacy-sqljs-import`，后者是 repeatable `comments-workflow-backfill`；两者都是 offline task，执行前必须完成同样的人工停机确认：

```bash
MAINTENANCE_OFFLINE_CONFIRMED=1 PROCESS_ROLE=maintenance \
  npm --prefix server run migrate:legacy

MAINTENANCE_OFFLINE_CONFIRMED=1 PROCESS_ROLE=maintenance \
  npm --prefix server run comments:backfill
```

这两条路径经过生产 `DATABASE_URL` 门禁、Scheduler/AI 执行权锁、task lock、schema/checksum readiness 与 `maintenance_runs`。legacy import 只接受代码固定路径的 sql.js 文件；文件缺失以 `LEGACY_SQLJS_DATABASE_NOT_FOUND` 记为 failed 且不记 success，补齐并复核固定文件后可重新授权重试。任何其他 legacy failed 或遗留 running 都会以 `MAINTENANCE_TASK_RESTORE_REQUIRED` 阻止直接重试，必须恢复任务前整库备份、确认失败 ledger 随恢复消失、重新核对并再次授权。alerts 的确定性 UUID 幂等 upsert 只降低重复写入风险，不代表任意失败可安全重试。legacy record upsert 使用 `localizeMedia: false`，不会把媒体下载/落库留到锁释放后；需要媒体落地时另行批准受审计的 `recent-media-backfill`。直接执行 `server/scripts/migrate-sqljs-to-postgres.js` 或 `server/scripts/backfill-comments-workflow.js` 会以退出码 2 拒绝。它们不会被 `startup-reconcile` 自动运行，必须分别获得数据范围、备份和执行授权。

`PROCESS_ROLE=maintenance npm --prefix server run user:create-admin -- <email> <password> [name]` 仍是参数化入口，不写 `maintenance_runs`；它强制 maintenance role，生产强制显式非空 `DATABASE_URL`，并通过 schema/checksum readiness。创建管理员是单独授权的数据/权限操作；不要把密码留在 shell history、日志或交接文档中。

`server/scripts/import-extension-csv.js` 仍是带来源和租户参数的独立 importer，不写 `maintenance_runs`。帮助和省略 `--commit` 的 dry-run 不连接数据库，只验证 CSV 解析与预览；它们不验证目标库、锁或 checksum。P2-D 主线代码的 `--commit` 写入路径必须显式设置 `PROCESS_ROLE=maintenance`，生产必须使用受控环境中的非空 `DATABASE_URL`，并设置 `MAINTENANCE_OFFLINE_CONFIRMED=1`；代码会先取得 `all` 的 Scheduler/AI 执行权锁，再通过 `connectRuntimeDb()` 校验 schema/checksum readiness，退出时先关数据库再释放锁。CSV record upsert 同样使用 `localizeMedia: false`；需要媒体下载/落库时另行批准 `recent-media-backfill`，避免锁释放后残留后台外连/写库。

该 importer 不属于 allowlist task，来源文件、目标租户、预计影响、备份和执行窗口必须单独授权。它也不是全量单事务：某行失败不会撤销之前已成功的写入。执行 `--commit` 前仍须人工确认旧 API/Worker 和其他写入入口停止；结束后保存统计/失败清单并核对目标租户数据，不能只看退出码或取得锁就认定完整成功。

仓库中的 `server/scripts/repair-*.sql` 和 tenant-specific repair SQL 仅作为历史证据保留，禁止直接在生产执行。Maintenance CLI 不接受任意 SQL 或文件路径；新的 repair 必须先做目标固定的 allowlist task/迁移、隔离验证、备份和独立审批。

##### P2-E-L 自动化顺序与断言

入口为 `tests/integration/postgres/process-topology-rehearsal.integration.mjs`，并纳入 `scripts/run-postgres-integration-tests.mjs`。由于 Node `--test` 会在单次多文件调用中自行按路径重排，完整 runner 不能只调整参数顺序；它必须使用两个独立子进程分阶段执行：第一阶段只运行 topology rehearsal，并通过严格空库门禁；第一阶段成功退出后，第二阶段才运行其余可能创建用户 relations 的 integration。任一阶段失败都令完整 runner 失败。最终可汇总为完整总数，但原始 TAP 必须分别保留第一阶段 `1/1` 与第二阶段 `25/25`，不能伪装成单次 TAP。不得先在同一专用库运行其他 integration 再执行完整 runner。

定向命令只用于单独诊断，不替代完整门禁；最终验证应在重新确认满足严格空库门禁的专用库上执行完整 runner。Node 24 与生产兼容 Node 18 分别使用独立或重新确认完全空闲的专用库，不复用另一版本的结果。

```bash
# 可选：定向诊断
node --test tests/integration/postgres/process-topology-rehearsal.integration.mjs

# 最终门禁：内部按 topology 1/1 → 其余 integration 25/25 两阶段执行
node scripts/run-postgres-integration-tests.mjs
```

自动化必须按下列顺序完成，任何一步失败都不得跳到“通过”：

1. 自动核对启动前专用库没有用户 relations 或 advisory lock，并在有界等待内取得连续 5 次稳定无其他 session 快照；瞬时 CI 探测可消退后重试，持久会话必须令门禁失败；
2. 以 `PROCESS_ROLE=all` 启动真实 `server/index.js`，等待迁移/bootstrap 完成并进入 ready，立即把隔离库默认租户的 daily/weekly/monthly report schedule 置为 `false`；随后确认 `/api/health/live` 与 `/api/health/ready` 成功、兼容进程同时拥有 Scheduler 与 AI/Media 两类执行权，且没有第二持有者；
3. 向 `all` 发送普通终止信号，等待完整 drain 和退出；确认 API 端口可重新绑定、普通连接关闭、两类角色锁均为零；
4. 分别以 `PROCESS_ROLE=api`、`scheduler`、`ai-media` 启动三个真实独立入口；确认 API 的 live/ready 成功，两个 Worker 不监听 HTTP，Scheduler 与 AI/Media 各恰好一个锁持有者；
5. 尝试启动重复 Worker，必须在业务循环开始前 fail-closed；任何 `all + split` 混合执行权也必须被拒绝；
6. 普通信号停止全部 split 子进程，等待完整 drain；确认端口可重新绑定、两类角色锁再次归零；
7. 再次以 `PROCESS_ROLE=all` 启动兼容入口并通过 live/ready，随后完整停止并确认端口、连接与角色锁清零；
8. 每个真实子进程报告 `exit` 后，必须继续等待 ChildProcess `close`，确认 stdout/stderr 已完全排空后，才对被标记为成功的 runtime 输出执行自动扫描；不得仅凭退出码提前截断日志。大小写不敏感匹配 `unhandled`、`uncaught`、`error`、`failed` 和带凭据的 URL 均令用例失败。预期的重复 Worker fail-closed 输出单独按错误码/退出行为断言，不混入“成功输出无异常”结论；该扫描只覆盖本用例完整收集到的成功 runtime 输出，不证明所有业务错误不存在，也不替代真实 PM2、流量和业务日志验收；
9. 核对没有 outbound guard 拦截记录，最后清理随机 schema、临时媒体目录和子进程。

失败即停止的条件包括：检测到非本机数据库或外部目标、数据库存在用户 relations/advisory lock、无法在有界等待内取得连续 5 次稳定无其他 session 快照、角色锁未释放、重复 Worker 获得执行权、Worker 监听 HTTP、readiness 误报、子进程无法有界退出、端口不能重绑、出现非本机 outbound 尝试、成功 runtime 输出命中上述异常/凭据模式，或清理后仍有测试子进程/连接残留。

## 10. 执行生产发布

当前生产发布仍是人工受控流程，尚未封装为可无条件执行的一键脚本。`deploy/deploy.sh` 只是会立即退出 64 的退役墓碑；它的历史行为仅在 1.3 节保留作风险审计，不能把移除 guard 当成恢复发布能力。

每次发布按以下顺序执行并保存证据：

1. **锁定有效生产清单**：记录完整生产基线、此后已覆盖的文件、当前环境与依赖状态；限定发布不能只读取 `RELEASE_COMMIT` 推导整棵生产树。
2. **固定发布白名单与排除项**：逐项列出 Server、Admin、Dashboard、Extension、依赖和迁移是否在范围内；未列入白名单的运行面不得被同步、删除或重建。
3. **建立可恢复材料**：生成新的数据库 custom dump 并用 `pg_restore --list` 校验；在与活动目录同一文件系统创建完整应用目录副本。环境文件、`node_modules`、属主和权限从活动目录保留，不用代码包覆盖。
4. **准备 staging**：只向完整副本覆盖白名单文件，逐文件核对 SHA-256；用生产同版 Node 做语法/启动前检查，并确认 `.env` 哈希与 `600` 权限、依赖锁文件和迁移清单没有越界变化。
5. **单独处理获批的数据库变化**：只有发布清单明确包含迁移时，才允许新增/上传迁移文件或单独手工运行迁移、回填与数据修复；迁移必须已在隔离数据库验证并与代码保持向前/向后兼容。`server/index.js` 正常启动仍会调用 `runMigrations()`，无迁移批次应通过冻结前后清单和启动日志确认没有新 migration applied，而不是绕过正常初始化。
6. **切换与健康门禁**：在同一文件系统原子交换 staging 与活动目录，再重启既有 PM2 应用；在限定时间内先验证本机和公网 `/api/health` 启动健康，再分别核对 PM2 不循环重启、数据库连接与迁移版本、严重日志、认证、Agent/队列和本批业务冒烟。当前生产 `/api/health` 只证明进程能响应，不是完整 readiness 或业务推进证明；主线已有但尚未部署的 `/api/health/live`、`/api/health/ready` 不能加入现行生产门禁。目录交换是原子的，但单实例 PM2 重启仍可能有短暂不可用，不能宣称零停机。
7. **失败即回切**：任何门禁失败都先保存日志，再原子交换回完整旧目录、重启并重新验证；没有数据库变化的批次禁止恢复数据库。
8. **成功后封存证据**：健康与业务验证全部通过后才保存 PM2 状态，保留完整旧目录和数据库备份；发布标记必须同时说明是“完整树提交”还是“限定文件来源”，不能让一个 SHA 冒充有效生产清单。

Dashboard 与 Extension 仍是独立发布面。只有它们明确进入发布白名单时，才执行各自的构建、备份、切换和客户浏览器验证。

即使 Extension 不在发布白名单，每次生产更新仍要先备份并从发布来源重建本机实际加载的 `extension-build`，核对 manifest/version、文件数量、生产 API、禁入文件与快照哈希。发布后必须核对 Chrome 和 Edge 的版本/心跳；若本批确实需要 Extension 更新，则还要逐浏览器/Profile 完成 Reload，或把未 Reload 清单明确交接，不能用服务端健康替代。

## 12. 回滚

### 12.1 为什么旧脚本不能提供原子回滚

当前发布顺序包含：

```text
文件同步 → 依赖安装 → 数据库迁移 → 删除旧进程 → 启动新进程
```

这些步骤不在同一个事务内。任何中间失败都可能产生：

- 新代码已同步但进程未启动；
- 数据库已迁移但旧代码无法兼容；
- 管理端产物已更新但后端仍不可用；
- PM2 短暂停止；
- 发布后的新业务写入已经进入数据库。

因此不能把“重新部署旧提交”描述为完整原子回滚。第 10 节的受控流程通过完整目录副本和同盘交换保证应用文件集可立即回切，但 PM2 重启、数据库和外部浏览器不在同一个事务中，仍不能把整次业务发布称为全链路原子事务。

### 12.2 仅应用回退

只在本批没有数据库变化，或已确认现有数据库仍与旧应用兼容时执行：

1. 暂停新工作并记录故障时间、发布清单、PM2/日志和当前活动目录；
2. 从本次发布记录定位同一文件系统上的**完整旧应用目录**，核对其环境文件、依赖、属主、权限和关键文件哈希；
3. 原子交换完整旧目录与活动目录，重启既有 PM2 应用；
4. 依次验证本机和公网 `/api/health`、PM2 不循环重启、数据库连接与迁移版本、严重日志、Admin/认证、关键业务、Agent 心跳与相关队列；`/api/health` 仅是启动健康，不得当作完整 readiness；
5. 保留故障目录、日志和发布后数据库快照用于分析，不在回退过程中删除证据；
6. 如果没有可验证的完整旧目录，停止操作并重新制定精确 staging 清单；不得用 Git checkout 后直接运行旧 `deploy/deploy.sh` 代替回滚。

若本批包含数据库迁移或数据操作，还必须先确认旧应用兼容边界；需要数据库恢复时转入 12.3 节，不能在应用回切过程中顺手恢复数据库。

### 12.3 数据库降级

数据库结构或数据需要降级时，必须走发布前备份恢复。Git 回退不会撤销迁移。

#### A. 冻结并保留证据

1. 通知业务负责人进入事故恢复窗口；
2. 停止会产生新写入的入口，必要时停止 PM2 应用：

   ```bash
   ssh root@47.103.125.200 'pm2 stop onstarvoice'
   ```

3. 保存故障时间、当前提交、PM2 日志、当前数据库完整备份和当前
   `server/.env` 的受控副本；
4. 不删除原数据库，也不要直接在唯一生产库上运行 `pg_restore --clean`；
5. 明确恢复点之后可能已经产生的任务、工单、评论、快照等新写入。它们不会
   自动合并到旧备份，后续必须单独重放或人工对账。

#### B. 恢复到独立验证库

每次事故使用带 release ID 的唯一新库名，例如 `onstarvoice_restore_<release_id>`。先只读查询 `pg_database` 并确认该名称不存在；若已存在就停止并换新名称，禁止 `dropdb --if-exists` 清理前一次事故的验证/证据库。随后创建新库，用 `pg_restore --exit-on-error --clean --if-exists --no-owner --no-acl` 恢复指定备份；这里的 `--clean` 只作用于刚创建且确认为空的新验证库，不得指向生产库。

用目标旧版本和独立环境文件连接该唯一验证库，至少验证：

- 平台管理员登录和租户切换；
- 目标租户、Agent、任务和内容数量；
- 调度、工单、评论和快照的关键关联；
- 目标旧版本能读取该结构且不会再次执行不兼容迁移；
- 恢复点时间和业务可接受的数据损失范围。

#### C. 经批准后受控切换

1. 取得业务负责人对恢复点、新写入损失范围和维护窗口的明确确认；
2. 复制当前远端环境文件为带时间戳的只读备份；
3. 准备新的环境文件，只修改 `DATABASE_URL` 指向已验证恢复库；
4. 将新环境文件设置为 `root:root`、权限 `600`；
5. 按第 10 节准备完整旧版本 staging，以同盘目录交换切换代码与经审查的环境文件，并使用本次发布记录中的既有 PM2 配置重启；
6. 不删除原生产数据库，保留为反向切换点。

这一切换没有可通用于所有恢复点的复制即执行命令。新环境文件必须在活动目录外审查，除 `DATABASE_URL` 外不得意外改变域名、租户、媒体目录、AI、SMTP 或初始化管理员配置；它应随完整 staging 一起原子安装，保持 `root:root 600`。禁止 `pm2 delete` 后临时手写 `pm2 start` 参数；若本次发布记录、PM2 dump 或既有进程配置不足以精确恢复 cwd、入口、环境和内存参数，应停止切换并先恢复发布证据。全部验证通过后才允许 `pm2 save`。

#### D. 切换后验证

依次执行：

1. `/api/health`；
2. 管理端登录与租户切换；
3. 数据量和恢复点核对；
4. 一个低风险、少量数据的完整业务闭环；
5. PM2 日志和数据库错误检查；
6. 对恢复点之后的新写入建立重放或人工对账清单。

#### E. 验证失败时反向切换

立即停止恢复库上的新写入，恢复切换前保存的环境文件，重新启动原版本并验证。
任何在恢复库上产生的新写入都要单独记录，不能假设两边数据库会自动合并。

## 13. 常见故障定位

### 13.1 管理端打开但 API 失败

检查：

1. 本地后端是否在 `3001`；
2. `/api/health` 是否返回；
3. Vite 代理是否仍指向 `3001`；
4. CORS 是否允许当前源；
5. 登录 Cookie、租户和 Token 是否属于当前环境。

### 13.2 Agent 显示在线但不执行

检查：

1. Extension 是否真的打开并持续心跳；
2. Agent 是否属于当前租户；
3. 平台能力是否匹配；
4. 是否已有占用槽位；
5. 云端命令是否仍在有效期；
6. 本地任务锁是否遗留；
7. 浏览器配置文件是否与后台显示节点一致。

### 13.3 数据库迁移失败

检查：

1. `DATABASE_URL`；
2. 生产 Maintenance 是否出现 `MAINTENANCE_DATABASE_URL_REQUIRED`；不要因此临时写入本地兜底连接串；
3. PostgreSQL 权限；
4. `schema_migrations` 当前版本；
5. 是否出现 `DATABASE_MIGRATION_LOCK_TIMEOUT`、`DATABASE_MIGRATION_CHECKSUMS_NOT_READY`、`DATABASE_MIGRATION_CHECKSUM_MISMATCH` 或 baseline 文件错误；
6. SQL 是否在事务中失败；
7. 是否误把 reset 迁移放入普通发布，或把 `ALLOW_RESET_MIGRATIONS=1` 带入环境导致 fail-closed；
8. 备份是否可恢复；
9. 首次 P2-D 发布时旧 migrator/旧进程是否真的已经停止，是否误做了滚动混跑。

不要在生产库手工标记迁移“已执行”、补写 checksum、删除 legacy marker、打开 reset 或改冻结 baseline 来绕过错误。checksum adoption 只能在完整备份、旧进程停止和明确授权后通过 Maintenance CLI 完成。

### 13.4 AI 没有介入

检查：

1. 租户级 AI 配置；
2. 进程级默认 LLM 配置；
3. API Key 和模型名；
4. 预筛选模式、每日限额和租户并发；
5. 超时与服务商返回；
6. 是同步预筛选、异步评论分析还是异步舆情剖析；
7. 页面展示的是最新任务还是旧快照。

具体降级口径见 [AI 与通知机制](./AI与通知机制.md)。

### 13.5 邮件没有发送

检查：

1. SMTP 主机、端口和 `SMTP_SECURE`；
2. 用户名、密码、发件人和收件人；
3. 通知队列状态；
4. 重试次数和最后错误；
5. 是否只配置了未被代码消费的渠道。

当前实现的安全事件通知通道是 SMTP 邮件；飞书、企业微信、短信和电话不能
仅靠环境变量启用。

### 13.6 Dashboard 是旧版本

退役的 `deploy/deploy.sh` 不会发布任何产物；其历史实现也未包含 Dashboard。确认是否按受控发布清单单独构建、staging 并切换了
`web/dashboard/dist/`。不要通过反复重启后端期待 dashboard 自动更新。发布和
回退命令见 [10.1 Dashboard 独立发布](#101-dashboard-独立发布)。

## 15. 发布纪律

- 不在客户正在高强度使用时做未经演练的迁移；
- 不把“PM2 online”当成发布成功；
- 不在没有备份时执行 reset、覆盖租户或批量清理；
- 不在生产发布前强制升级全部依赖；
- 不把本地 Extension 包发给客户；
- 不把旧版 Extension 与新版服务端的偶然兼容当作长期合同；
- 不把静态构建通过当作真实浏览器流程通过；
- 不隐藏未运行、失败或被跳过的检查项；
- 不为追求“部署完成”而跳过租户隔离和数据归属验证。
