## 1. 稳定版运行边界

### 1.1 当前由哪些运行面组成

| 运行面 | 源码/产物 | 本地入口 | 生产入口或用途 |
|---|---|---|---|
| Node.js 后端 | `server/` | `http://localhost:3001`（集成联调约定） | `https://voice.minilife.online/api/*` |
| 管理端 | `web/admin/` | `http://localhost:5173` | `https://voice.minilife.online/admin/` |
| 数据看板 | `web/dashboard/` | `http://localhost:5174` | `https://voice.minilife.online/dashboard/` |
| Extension 源码 | 根目录脚本、`sidebar/`、`utils/` 等 | 不直接加载 | 构建输入 |
| Extension 可加载快照 | `extension-build/` | 浏览器“加载已解压的扩展程序” | 本地联调或打包输入 |
| Extension 客户包 | 打包脚本生成的 ZIP | 不用于开发 | 交付客户安装/升级 |
| PostgreSQL | `server/db/` 迁移驱动 | 本地数据库 | 生产独立数据库 `onstarvoice` |
| 运行时媒体 | `MEDIA_DIR` | 默认仓库外或本地配置目录 | `/opt/onstarvoice/media` |

### 1.2 三套端口口径

这三个端口不能混为一谈：

| 场景 | 端口 | 原因 |
|---|---:|---|
| 后端代码在没有 `PORT` 时的兜底值 | `3000` | `server/index.js` 的默认值 |
| 本地完整联调 | `3001` | 管理端、数据看板的 Vite 代理和本地 Extension 配置均指向 `3001` |
| 生产 PM2 进程 | `3002` | Nginx 将生产域名反向代理到本机 `3002` |

因此：

- 单独验证 Express 启动时可以使用代码兜底的 `3000`；
- 同时联调管理端、数据看板或 Extension 时，后端必须设置为 `3001`；
- 生产环境文件必须使用 `PORT=3002`；
- 不要通过临时修改源码中的端口来切换环境，应使用环境变量。

### 1.3 旧库存发布脚本的明确边界

> 本节只记录旧脚本的真实行为，**不是当前生产发布指令**。生产现状包含 hotfix 基线上的限定文件覆盖；直接运行旧脚本会扩大范围并可能覆盖有效生产文件。旧脚本在完成原子切换、完整备份、明确的启动健康/数据库/业务门禁与失败回切改造并通过演练前，不得直接用于当前生产。

`deploy/deploy.sh` 当前会发布：

- `server/`；
- `web/admin/dist/`；
- 仓库中的 `images/`；
- `server/.env.production`；
- 数据库迁移；
- PM2 进程 `onstarvoice`。

它当前**不会**：

- 自动备份生产数据库；
- 构建或同步 `web/dashboard/dist/`；
- 打包或升级客户浏览器中的 Extension；
- 做零停机或滚动重启；
- 在迁移和进程启动后自动执行完整健康门禁；
- 自动把数据库回退到发布前状态；
- 保证一定使用 Node.js 24 或 20。

脚本只会尝试把若干本机常见的 Node 24/20 安装路径放到 `PATH`；如果这些
目录不存在，它仍会使用调用者当前 `PATH` 中的 `node`。所以发布前必须人工
执行 `node --version`，不能把脚本中的路径探测当作版本保证。

## 2. 开发环境准备

### 2.1 建议工具

- 开发、前端构建和主质量门禁使用 `.nvmrc` 固定的 Node.js 24.12.0；
- 生产 Server 当前仍为 Node.js 18.20.8，仓库另设同版本兼容门禁；运行时升级必须单独发布；
- npm；
- PostgreSQL；
- Git；
- 浏览器（Chrome 或 Edge）；
- Extension 打包时需要 `zip`、`rsync`、`python3`；
- 生产发布时需要 SSH、`rsync`、PM2 和 Nginx。

根级 `package.json` 只声明 Extension 源码的 ESM 语义，不管理依赖。后端、管理端和数据看板仍需分别使用各自的 lockfile 与 `npm --prefix ... ci` 安装，禁止在仓库根目录执行依赖安装。

确认基本工具：

```bash
node --version
npm --version
psql --version
git --version
```

### 2.2 本地 PostgreSQL

下面是示例，不应覆盖已有数据库：

```bash
createdb onstarvoice_dev
```

若本机需要专用角色，应由开发者按本机 PostgreSQL 权限模型创建。不要把生产
账号、生产密码或生产数据库下载到日常开发环境。

### 2.3 后端环境文件

```bash
cp server/.env.example server/.env
```

本地完整联调至少确认：

```dotenv
NODE_ENV=development
PORT=3001
DATABASE_URL=postgresql://USER:PASSWORD@127.0.0.1:5432/onstarvoice_dev
CORS_ORIGINS=http://localhost:3000,http://localhost:3001,http://localhost:5173,http://localhost:5174
ADMIN_PUBLIC_URL=http://localhost:5173
PUBLIC_BASE_URL=http://localhost:3001
```

AI、OCR、ASR 和 SMTP 没有配置时，不应假定相关能力可用。详细变量和降级
行为见 [AI 与通知机制](./AI与通知机制.md)。

安全要求：

- `server/.env` 与 `server/.env.production` 都是机密文件；
- 不提交数据库密码、Agent Token、激活码、LLM/OCR/ASR Key 和 SMTP 密码；
- 不把生产环境文件复制给客户或写进截图；
- 不用生产数据库做迁移开发和 destructive 测试。

## 3. 首次启动

### 3.1 安装后端依赖并迁移

```bash
cd server
npm ci
npm run migrate
```

迁移执行器会读取 `server/db/migrations/*.sql`，按文件名排序，在
`schema_migrations` 中记录已应用版本。正常开发应保持：

```dotenv
ALLOW_RESET_MIGRATIONS=0
```

包含 `reset` 的迁移不会在默认配置下执行。更详细的迁移规则和恢复边界见
[数据库与迁移说明](./数据库与迁移说明.md)。

### 3.2 启动后端

开发监听：

```bash
cd server
npm run dev
```

非 watch 方式：

```bash
cd server
npm start
```

验证：

```bash
curl --fail --silent --show-error http://localhost:3001/api/health
```

预期返回 JSON，且 `ok` 为 `true`。健康接口只证明进程可响应，不证明数据库
业务、AI、邮件或 Extension 全链路已经可用。

### 3.3 启动管理端

新终端执行：

```bash
cd web/admin
npm ci
npm run dev
```

浏览器访问：

```text
http://localhost:5173
```

Vite 会把 `/api` 和 `/images` 代理到 `http://localhost:3001`。如果页面能打开
但 API 全部失败，先检查后端是否真的在 `3001`。

### 3.4 启动数据看板

新终端执行：

```bash
cd web/dashboard
npm ci
npm run dev
```

浏览器访问：

```text
http://localhost:5174
```

数据看板的开发代理同样指向 `http://localhost:3001`。

### 3.5 首个平台管理员

全新数据库可以通过环境变量提供一次性引导管理员：

```dotenv
BOOTSTRAP_ADMIN_EMAIL=admin@example.com
BOOTSTRAP_ADMIN_PASSWORD=至少12位的强密码
BOOTSTRAP_ADMIN_NAME=Platform Admin
```

启动成功并确认管理员已创建后，应从长期环境文件移除
`BOOTSTRAP_ADMIN_PASSWORD`。后端也提供：

```bash
cd server
npm run user:create-admin
```

使用该脚本前应先阅读脚本的当前参数与交互，不要在文档之外假定固定命令行
参数。

## 4. 本地联调顺序

建议固定顺序，减少“页面在线但任务不执行”的误判：

1. 启动 PostgreSQL；
2. 运行数据库迁移；
3. 以 `PORT=3001` 启动后端；
4. 验证 `/api/health`；
5. 启动管理端；
6. 需要时启动数据看板；
7. 生成本地 Extension 快照并在浏览器 Reload；
8. 登录目标租户；
9. 验证 Agent 心跳和在线状态；
10. 用少量、低风险数据做完整业务冒烟。

本地联调不是生产演练。尤其不要用真实客户账号做高频搜索、增强或评论读取
压力测试。

## 5. Extension 开发、加载与打包

### 5.1 不要直接加载源码根目录

当前可加载、可交付的 Extension 运行面是 `extension-build/`。根目录中的
`background.js`、`sidebar/`、`utils/`、`manifest.json` 等是构建输入。
修改源文件后必须重新同步快照。

### 5.2 生成本地联调快照

在仓库根目录：

```bash
scripts/sync-extension-build.zsh local
```

该命令会：

- 从当前源码重建 `extension-build/`；
- 写入本地 API 地址；
- 校验快照结构和 JSON；
- 检查不应进入交付包的敏感或开发文件。

随后在 `chrome://extensions` 或 `edge://extensions`：

1. 开启开发者模式；
2. 选择“加载已解压的扩展程序”，目录为 `extension-build/`；
3. 已加载时点击 Reload；
4. 重新打开目标平台页面。

只重启后端不会自动让已加载 Extension 使用新代码。

### 5.3 生成生产快照

```bash
scripts/sync-extension-build.zsh production
```

生产快照必须只指向：

```text
https://voice.minilife.online
```

发布给客户前必须确认快照中没有 `localhost`、本地 Token、测试激活码或客户
业务数据。

### 5.4 生成客户 ZIP

```bash
scripts/package-extension.zsh
```

脚本会重新生成并校验生产快照，再输出客户安装包。不要把旧 ZIP 手工改名
冒充新版本。

每次交付记录：

- `manifest.json` 版本；
- Git 提交；
- 生成时间；
- 校验和；
- API 基址；
- 权限变化；
- 冒烟结果。

后端部署与 Extension 升级是两个独立发布面。仅发布后端不会升级客户浏览器
中的 Extension。

## 6. 构建与静态产物

### 6.1 管理端

在仓库根目录执行：

```bash
npm --prefix web/admin ci
node scripts/check-admin-lint-baseline.mjs
npm --prefix web/admin run build
```

Admin 当前存在 288 个已记录的 lint 存量错误；基线门禁同时检查全局总数与逐文件上限，
只允许存量下降，不允许新错误被其他文件的减少掩盖。在存量债务清零前，不得把直接执行 `npm run lint` 的预期失败
冒充为新回归。

产物位于：

```text
web/admin/dist/
```

### 6.2 数据看板

```bash
cd web/dashboard
npm ci
npm run lint
npm run build
```

产物位于：

```text
web/dashboard/dist/
```

后端会尝试从这两个 `dist/` 目录提供 `/admin` 和 `/dashboard`。但是旧库存
`deploy/deploy.sh` 只构建并同步管理端，不会发布数据看板。因此：

- 数据看板修改不能依赖旧库存脚本上线；
- 发布数据看板前要按 10.1 节单独构建、核对、完整备份、staging 和原子切换；
- 单独发布步骤必须经过与管理端相同的构建和页面冒烟；
- 在安全发布自动化正式纳入数据看板前，不应对外宣称“一键发布包含 dashboard”。

## 7. 测试与验收

### 7.0 CI 工程门禁

仓库工作流位于 `.github/workflows/ci.yml`，分为：

- `quality`：锁定依赖安装、仓库卫生、版本化生产拓扑、服务端语法、当前不少于 1205 项合同/回归测试、Admin lint 存量门禁、Admin/Dashboard 构建、Dashboard lint，以及仓库源码到本地 `extension-build/` 的交付快照检查；
- `production-runtime-compatibility`：使用与生产一致的 Node 18.20.8 安装 Server 锁定依赖、检查 Server 语法并执行相同的 1205 项全量回归；
- `postgres-integration`：在 CI 临时 PostgreSQL 14/Node 24、PostgreSQL 16/Node 24、PostgreSQL 16/Node 18 三组环境执行迁移、认证/租户 HTTP、真实入口和多进程角色锁测试。

`quality` 和两个 PostgreSQL 任务使用 `.nvmrc` 的 Node 24.12.0。Node 18 兼容任务只证明当前生产 Server 运行面仍兼容，不允许在生产机上构建 Admin/Dashboard，也不替代后续独立的生产 Node 升级。

工作流不读取生产密钥，不连接生产数据库，也不访问客户浏览器。提交、推送和远端 CI 仍需分别授权；本地测试通过不能冒充远端干净 checkout 证据。

### 7.1 后端/Extension 合同测试

仓库中的主要自动化测试位于 `tests/**/*.test.mjs`。完整执行：

```bash
npm --prefix server test
```

该标准入口会先生成并核验本地 Extension 交付快照，再执行全量 Node 测试；
这不会访问生产、客户浏览器或外部系统。

如果改动范围明确，应先执行相关测试，再执行完整测试。例如任务编排、抖音
详情身份校验、评论巡查、负面巡查和通知都有独立合同测试。

测试失败时：

- 不通过删除断言来“修复”；
- 先判断是行为回归、测试环境缺失，还是合同已被明确修改；
- 记录失败用例、错误信息和是否影响生产路径；
- 不把“其余测试没跑”写成“测试通过”。

### 7.1.1 PostgreSQL 集成测试

真实数据库测试约定见 `tests/integration/README.md`。统一入口：

```bash
TEST_DATABASE_URL=postgresql://USER:PASSWORD@127.0.0.1:5432/onstarvoice_test \
  npm --prefix server run test:integration
```

Runner 只接受 localhost 且数据库名以 `onstarvoice_ci` 或 `onstarvoice_test` 开头的连接；不创建、不删除数据库，也拒绝 `DATABASE_URL` 与 `TEST_DATABASE_URL` 指向不同目标。P2-A1 已提取不负责监听、数据库初始化和后台循环的 `createApp()`；首批真实 HTTP 用例位于 `tests/integration/http/app.test.mjs`，在不可达本地测试库和禁止非本地 HTTP 请求的保护下纳入默认 Node 回归。需要数据库的认证成功与跨租户用例仍必须通过上述隔离连接保护。

### 7.2 前端检查

```bash
node scripts/check-admin-lint-baseline.mjs
npm --prefix web/admin run build
npm --prefix web/dashboard run lint
```

## 10. 执行生产发布

当前生产发布仍是人工受控流程，尚未封装为可无条件执行的一键脚本。**不要直接运行 `deploy/deploy.sh`**；它的旧行为仅在 1.3 节保留作风险审计。

每次发布按以下顺序执行并保存证据：

1. **锁定有效生产清单**：记录完整生产基线、此后已覆盖的文件、当前环境与依赖状态；限定发布不能只读取 `RELEASE_COMMIT` 推导整棵生产树。
2. **固定发布白名单与排除项**：逐项列出 Server、Admin、Dashboard、Extension、依赖和迁移是否在范围内；未列入白名单的运行面不得被同步、删除或重建。
3. **建立可恢复材料**：生成新的数据库 custom dump 并用 `pg_restore --list` 校验；在与活动目录同一文件系统创建完整应用目录副本。环境文件、`node_modules`、属主和权限从活动目录保留，不用代码包覆盖。
4. **准备 staging**：只向完整副本覆盖白名单文件，逐文件核对 SHA-256；用生产同版 Node 做语法/启动前检查，并确认 `.env` 哈希与 `600` 权限、依赖锁文件和迁移清单没有越界变化。
5. **单独处理获批的数据库变化**：只有发布清单明确包含迁移时，才允许新增/上传迁移文件或单独手工运行迁移、回填与数据修复；迁移必须已在隔离数据库验证并与代码保持向前/向后兼容。`server/index.js` 正常启动仍会调用 `runMigrations()`，无迁移批次应通过冻结前后清单和启动日志确认没有新 migration applied，而不是绕过正常初始化。
6. **切换与健康门禁**：在同一文件系统原子交换 staging 与活动目录，再重启既有 PM2 应用；在限定时间内先验证本机和公网 `/api/health` 启动健康，再分别核对 PM2 不循环重启、数据库连接与迁移版本、严重日志、认证、Agent/队列和本批业务冒烟。当前 `/api/health` 只证明进程能响应，不是完整 readiness 或业务推进证明。目录交换是原子的，但单实例 PM2 重启仍可能有短暂不可用，不能宣称零停机。
7. **失败即回切**：任何门禁失败都先保存日志，再原子交换回完整旧目录、重启并重新验证；没有数据库变化的批次禁止恢复数据库。
8. **成功后封存证据**：健康与业务验证全部通过后才保存 PM2 状态，保留完整旧目录和数据库备份；发布标记必须同时说明是“完整树提交”还是“限定文件来源”，不能让一个 SHA 冒充有效生产清单。

Dashboard 与 Extension 仍是独立发布面。只有它们明确进入发布白名单时，才执行各自的构建、备份、切换和客户浏览器验证。

即使 Extension 不在发布白名单，每次生产更新仍要先备份并从发布来源重建本机实际加载的 `extension-build`，核对 manifest/version、文件数量、生产 API、禁入文件与快照哈希。发布后必须核对 Chrome 和 Edge 的版本/心跳；若本批确实需要 Extension 更新，则还要逐浏览器/Profile 完成 Reload，或把未 Reload 清单明确交接，不能用服务端健康替代。

### 10.1 Dashboard 独立发布

旧库存 `deploy/deploy.sh` 不发布 `web/dashboard/dist/`。数据看板必须按独立静态产物发布，
并在切换前保存可识别的完整远端目录。当前没有经过演练的一键 Dashboard 发布脚本，以下流程需人工受控执行。

## 12. 回滚

### 12.1 为什么旧脚本不能提供原子回滚

当前发布顺序包含：

```text
文件同步 → 依赖安装 → 数据库迁移 → 删除旧进程 → 启动新进程
```

这些步骤不在同一个事务内。任何中间失败都可能产生：

- 新代码已同步但进程未启动；
- 数据库已迁移但旧代码无法兼容；
- 管理端产物已更新但后端仍不可用；
- PM2 短暂停止；
- 发布后的新业务写入已经进入数据库。

因此不能把“重新部署旧提交”描述为完整原子回滚。第 10 节的受控流程通过完整目录副本和同盘交换保证应用文件集可立即回切，但 PM2 重启、数据库和外部浏览器不在同一个事务中，仍不能把整次业务发布称为全链路原子事务。

### 12.2 仅应用回退

只在本批没有数据库变化，或已确认现有数据库仍与旧应用兼容时执行：

1. 暂停新工作并记录故障时间、发布清单、PM2/日志和当前活动目录；
2. 从本次发布记录定位同一文件系统上的**完整旧应用目录**，核对其环境文件、依赖、属主、权限和关键文件哈希；
3. 原子交换完整旧目录与活动目录，重启既有 PM2 应用；
4. 依次验证本机和公网 `/api/health`、PM2 不循环重启、数据库连接与迁移版本、严重日志、Admin/认证、关键业务、Agent 心跳与相关队列；`/api/health` 仅是启动健康，不得当作完整 readiness；
5. 保留故障目录、日志和发布后数据库快照用于分析，不在回退过程中删除证据；
6. 如果没有可验证的完整旧目录，停止操作并重新制定精确 staging 清单；不得用 Git checkout 后直接运行旧 `deploy/deploy.sh` 代替回滚。

若本批包含数据库迁移或数据操作，还必须先确认旧应用兼容边界；需要数据库恢复时转入 12.3 节，不能在应用回切过程中顺手恢复数据库。

### 12.3 数据库降级

数据库结构或数据需要降级时，必须走发布前备份恢复。Git 回退不会撤销迁移。

#### A. 冻结并保留证据

1. 通知业务负责人进入事故恢复窗口；
2. 停止会产生新写入的入口，必要时停止 PM2 应用：

   ```bash
   ssh root@47.103.125.200 'pm2 stop onstarvoice'
   ```

3. 保存故障时间、当前提交、PM2 日志、当前数据库完整备份和当前
   `server/.env` 的受控副本；
4. 不删除原数据库，也不要直接在唯一生产库上运行 `pg_restore --clean`；
5. 明确恢复点之后可能已经产生的任务、工单、评论、快照等新写入。它们不会
   自动合并到旧备份，后续必须单独重放或人工对账。

#### B. 恢复到独立验证库

每次事故使用带 release ID 的唯一新库名，例如 `onstarvoice_restore_<release_id>`。先只读查询 `pg_database` 并确认该名称不存在；若已存在就停止并换新名称，禁止 `dropdb --if-exists` 清理前一次事故的验证/证据库。随后创建新库，用 `pg_restore --exit-on-error --clean --if-exists --no-owner --no-acl` 恢复指定备份；这里的 `--clean` 只作用于刚创建且确认为空的新验证库，不得指向生产库。

用目标旧版本和独立环境文件连接该唯一验证库，至少验证：

- 平台管理员登录和租户切换；
- 目标租户、Agent、任务和内容数量；
- 调度、工单、评论和快照的关键关联；
- 目标旧版本能读取该结构且不会再次执行不兼容迁移；
- 恢复点时间和业务可接受的数据损失范围。

#### C. 经批准后受控切换

1. 取得业务负责人对恢复点、新写入损失范围和维护窗口的明确确认；
2. 复制当前远端环境文件为带时间戳的只读备份；
3. 准备新的环境文件，只修改 `DATABASE_URL` 指向已验证恢复库；
4. 将新环境文件设置为 `root:root`、权限 `600`；
5. 按第 10 节准备完整旧版本 staging，以同盘目录交换切换代码与经审查的环境文件，并使用本次发布记录中的既有 PM2 配置重启；
6. 不删除原生产数据库，保留为反向切换点。

这一切换没有可通用于所有恢复点的复制即执行命令。新环境文件必须在活动目录外审查，除 `DATABASE_URL` 外不得意外改变域名、租户、媒体目录、AI、SMTP 或初始化管理员配置；它应随完整 staging 一起原子安装，保持 `root:root 600`。禁止 `pm2 delete` 后临时手写 `pm2 start` 参数；若本次发布记录、PM2 dump 或既有进程配置不足以精确恢复 cwd、入口、环境和内存参数，应停止切换并先恢复发布证据。全部验证通过后才允许 `pm2 save`。

#### D. 切换后验证

依次执行：

1. `/api/health`；
2. 管理端登录与租户切换；
3. 数据量和恢复点核对；
4. 一个低风险、少量数据的完整业务闭环；
5. PM2 日志和数据库错误检查；
6. 对恢复点之后的新写入建立重放或人工对账清单。

#### E. 验证失败时反向切换

立即停止恢复库上的新写入，恢复切换前保存的环境文件，重新启动原版本并验证。
任何在恢复库上产生的新写入都要单独记录，不能假设两边数据库会自动合并。

## 13. 常见故障定位

### 13.1 管理端打开但 API 失败

检查：

1. 本地后端是否在 `3001`；
2. `/api/health` 是否返回；
3. Vite 代理是否仍指向 `3001`；
4. CORS 是否允许当前源；
5. 登录 Cookie、租户和 Token 是否属于当前环境。

### 13.2 Agent 显示在线但不执行

检查：

1. Extension 是否真的打开并持续心跳；
2. Agent 是否属于当前租户；
3. 平台能力是否匹配；
4. 是否已有占用槽位；
5. 云端命令是否仍在有效期；
6. 本地任务锁是否遗留；
7. 浏览器配置文件是否与后台显示节点一致。

### 13.3 数据库迁移失败

检查：

1. `DATABASE_URL`；
2. PostgreSQL 权限；
3. `schema_migrations` 当前版本；
4. SQL 是否在事务中失败；
5. 是否误把 reset 迁移放入普通发布；
6. 备份是否可恢复。

不要在生产库手工标记迁移“已执行”来绕过错误。

### 13.4 AI 没有介入

检查：

1. 租户级 AI 配置；
2. 进程级默认 LLM 配置；
3. API Key 和模型名；
4. 预筛选模式、每日限额和租户并发；
5. 超时与服务商返回；
6. 是同步预筛选、异步评论分析还是异步舆情剖析；
7. 页面展示的是最新任务还是旧快照。

具体降级口径见 [AI 与通知机制](./AI与通知机制.md)。

### 13.5 邮件没有发送

检查：

1. SMTP 主机、端口和 `SMTP_SECURE`；
2. 用户名、密码、发件人和收件人；
3. 通知队列状态；
4. 重试次数和最后错误；
5. 是否只配置了未被代码消费的渠道。

当前实现的安全事件通知通道是 SMTP 邮件；飞书、企业微信、短信和电话不能
仅靠环境变量启用。

### 13.6 Dashboard 是旧版本

这是旧库存 `deploy/deploy.sh` 的已知边界。确认是否按受控发布清单单独构建、staging 并切换了
`web/dashboard/dist/`。不要通过反复重启后端期待 dashboard 自动更新。发布和
回退命令见 [10.1 Dashboard 独立发布](#101-dashboard-独立发布)。

## 15. 发布纪律

- 不在客户正在高强度使用时做未经演练的迁移；
- 不把“PM2 online”当成发布成功；
- 不在没有备份时执行 reset、覆盖租户或批量清理；
- 不在生产发布前强制升级全部依赖；
- 不把本地 Extension 包发给客户；
- 不把旧版 Extension 与新版服务端的偶然兼容当作长期合同；
- 不把静态构建通过当作真实浏览器流程通过；
- 不隐藏未运行、失败或被跳过的检查项；
- 不为追求“部署完成”而跳过租户隔离和数据归属验证。
