## 1. 稳定版运行边界

### 1.1 当前由哪些运行面组成

| 运行面 | 源码/产物 | 本地入口 | 生产入口或用途 |
|---|---|---|---|
| Node.js 后端 | `server/` | `http://localhost:3001`（集成联调约定） | `https://voice.minilife.online/api/*` |
| 管理端 | `web/admin/` | `http://localhost:5173` | `https://voice.minilife.online/admin/` |
| 数据看板 | `web/dashboard/` | `http://localhost:5174` | `https://voice.minilife.online/dashboard/` |
| Extension 源码 | 根目录脚本、`sidebar/`、`utils/` 等 | 不直接加载 | 构建输入 |
| Extension 可加载快照 | `extension-build/` | 浏览器“加载已解压的扩展程序” | 本地联调或打包输入 |
| Extension 客户包 | 打包脚本生成的 ZIP | 不用于开发 | 交付客户安装/升级 |
| PostgreSQL | `server/db/` 迁移驱动 | 本地数据库 | 生产独立数据库 `onstarvoice` |
| 运行时媒体 | `MEDIA_DIR` | 默认仓库外或本地配置目录 | `/opt/onstarvoice/media` |

### 1.2 三套端口口径

这三个端口不能混为一谈：

| 场景 | 端口 | 原因 |
|---|---:|---|
| 后端代码在没有 `PORT` 时的兜底值 | `3000` | `server/index.js` 的默认值 |
| 本地完整联调 | `3001` | 管理端、数据看板的 Vite 代理和本地 Extension 配置均指向 `3001` |
| 生产 PM2 进程 | `3002` | Nginx 将生产域名反向代理到本机 `3002` |

因此：

- 单独验证 Express 启动时可以使用代码兜底的 `3000`；
- 同时联调管理端、数据看板或 Extension 时，后端必须设置为 `3001`；
- 生产环境文件必须使用 `PORT=3002`；
- 不要通过临时修改源码中的端口来切换环境，应使用环境变量。

### 1.3 当前发布脚本的明确边界

`deploy/deploy.sh` 当前会发布：

- `server/`；
- `web/admin/dist/`；
- 仓库中的 `images/`；
- `server/.env.production`；
- 数据库迁移；
- PM2 进程 `onstarvoice`。

它当前**不会**：

- 自动备份生产数据库；
- 构建或同步 `web/dashboard/dist/`；
- 打包或升级客户浏览器中的 Extension；
- 做零停机或滚动重启；
- 在迁移和进程启动后自动执行完整健康门禁；
- 自动把数据库回退到发布前状态；
- 保证一定使用 Node.js 24 或 20。

脚本只会尝试把若干本机常见的 Node 24/20 安装路径放到 `PATH`；如果这些
目录不存在，它仍会使用调用者当前 `PATH` 中的 `node`。所以发布前必须人工
执行 `node --version`，不能把脚本中的路径探测当作版本保证。

## 2. 开发环境准备

### 2.1 建议工具

- Node.js 20 LTS 或经过项目构建验证的更高版本；
- npm；
- PostgreSQL；
- Git；
- 浏览器（Chrome 或 Edge）；
- Extension 打包时需要 `zip`、`rsync`、`python3`；
- 生产发布时需要 SSH、`rsync`、PM2 和 Nginx。

仓库没有根级 `package.json`，后端、管理端和数据看板需要分别安装依赖。

确认基本工具：

```bash
node --version
npm --version
psql --version
git --version
```

### 2.2 本地 PostgreSQL

下面是示例，不应覆盖已有数据库：

```bash
createdb onstarvoice_dev
```

若本机需要专用角色，应由开发者按本机 PostgreSQL 权限模型创建。不要把生产
账号、生产密码或生产数据库下载到日常开发环境。

### 2.3 后端环境文件

```bash
cp server/.env.example server/.env
```

本地完整联调至少确认：

```dotenv
NODE_ENV=development
PORT=3001
DATABASE_URL=postgresql://USER:PASSWORD@127.0.0.1:5432/onstarvoice_dev
CORS_ORIGINS=http://localhost:3000,http://localhost:3001,http://localhost:5173,http://localhost:5174
ADMIN_PUBLIC_URL=http://localhost:5173
PUBLIC_BASE_URL=http://localhost:3001
```

AI、OCR、ASR 和 SMTP 没有配置时，不应假定相关能力可用。详细变量和降级
行为见 [AI 与通知机制](./AI与通知机制.md)。

安全要求：

- `server/.env` 与 `server/.env.production` 都是机密文件；
- 不提交数据库密码、Agent Token、激活码、LLM/OCR/ASR Key 和 SMTP 密码；
- 不把生产环境文件复制给客户或写进截图；
- 不用生产数据库做迁移开发和 destructive 测试。

## 3. 首次启动

### 3.1 安装后端依赖并迁移

```bash
cd server
npm ci
npm run migrate
```

迁移执行器会读取 `server/db/migrations/*.sql`，按文件名排序，在
`schema_migrations` 中记录已应用版本。正常开发应保持：

```dotenv
ALLOW_RESET_MIGRATIONS=0
```

包含 `reset` 的迁移不会在默认配置下执行。更详细的迁移规则和恢复边界见
[数据库与迁移说明](./数据库与迁移说明.md)。

### 3.2 启动后端

开发监听：

```bash
cd server
npm run dev
```

非 watch 方式：

```bash
cd server
npm start
```

验证：

```bash
curl --fail --silent --show-error http://localhost:3001/api/health
```

预期返回 JSON，且 `ok` 为 `true`。健康接口只证明进程可响应，不证明数据库
业务、AI、邮件或 Extension 全链路已经可用。

### 3.3 启动管理端

新终端执行：

```bash
cd web/admin
npm ci
npm run dev
```

浏览器访问：

```text
http://localhost:5173
```

Vite 会把 `/api` 和 `/images` 代理到 `http://localhost:3001`。如果页面能打开
但 API 全部失败，先检查后端是否真的在 `3001`。

### 3.4 启动数据看板

新终端执行：

```bash
cd web/dashboard
npm ci
npm run dev
```

浏览器访问：

```text
http://localhost:5174
```

数据看板的开发代理同样指向 `http://localhost:3001`。

### 3.5 首个平台管理员

全新数据库可以通过环境变量提供一次性引导管理员：

```dotenv
BOOTSTRAP_ADMIN_EMAIL=admin@example.com
BOOTSTRAP_ADMIN_PASSWORD=至少12位的强密码
BOOTSTRAP_ADMIN_NAME=Platform Admin
```

启动成功并确认管理员已创建后，应从长期环境文件移除
`BOOTSTRAP_ADMIN_PASSWORD`。后端也提供：

```bash
cd server
npm run user:create-admin
```

使用该脚本前应先阅读脚本的当前参数与交互，不要在文档之外假定固定命令行
参数。

## 4. 本地联调顺序

建议固定顺序，减少“页面在线但任务不执行”的误判：

1. 启动 PostgreSQL；
2. 运行数据库迁移；
3. 以 `PORT=3001` 启动后端；
4. 验证 `/api/health`；
5. 启动管理端；
6. 需要时启动数据看板；
7. 生成本地 Extension 快照并在浏览器 Reload；
8. 登录目标租户；
9. 验证 Agent 心跳和在线状态；
10. 用少量、低风险数据做完整业务冒烟。

本地联调不是生产演练。尤其不要用真实客户账号做高频搜索、增强或评论读取
压力测试。

## 5. Extension 开发、加载与打包

### 5.1 不要直接加载源码根目录

当前可加载、可交付的 Extension 运行面是 `extension-build/`。根目录中的
`background.js`、`sidebar/`、`utils/`、`manifest.json` 等是构建输入。
修改源文件后必须重新同步快照。

### 5.2 生成本地联调快照

在仓库根目录：

```bash
scripts/sync-extension-build.zsh local
```

该命令会：

- 从当前源码重建 `extension-build/`；
- 写入本地 API 地址；
- 校验快照结构和 JSON；
- 检查不应进入交付包的敏感或开发文件。

随后在 `chrome://extensions` 或 `edge://extensions`：

1. 开启开发者模式；
2. 选择“加载已解压的扩展程序”，目录为 `extension-build/`；
3. 已加载时点击 Reload；
4. 重新打开目标平台页面。

只重启后端不会自动让已加载 Extension 使用新代码。

### 5.3 生成生产快照

```bash
scripts/sync-extension-build.zsh production
```

生产快照必须只指向：

```text
https://voice.minilife.online
```

发布给客户前必须确认快照中没有 `localhost`、本地 Token、测试激活码或客户
业务数据。

### 5.4 生成客户 ZIP

```bash
scripts/package-extension.zsh
```

脚本会重新生成并校验生产快照，再输出客户安装包。不要把旧 ZIP 手工改名
冒充新版本。

每次交付记录：

- `manifest.json` 版本；
- Git 提交；
- 生成时间；
- 校验和；
- API 基址；
- 权限变化；
- 冒烟结果。

后端部署与 Extension 升级是两个独立发布面。仅发布后端不会升级客户浏览器
中的 Extension。

## 6. 构建与静态产物

### 6.1 管理端

```bash
cd web/admin
npm ci
npm run lint
npm run build
```

产物位于：

```text
web/admin/dist/
```

### 6.2 数据看板

```bash
cd web/dashboard
npm ci
npm run lint
npm run build
```

产物位于：

```text
web/dashboard/dist/
```

后端会尝试从这两个 `dist/` 目录提供 `/admin` 和 `/dashboard`。但是当前
`deploy/deploy.sh` 只构建并同步管理端，不会发布数据看板。因此：

- 发布数据看板前要单独构建、核对目标目录、备份旧产物并同步；
- 单独发布步骤必须经过与管理端相同的构建和页面冒烟；
- 在发布脚本正式纳入数据看板前，不应对外宣称“一键发布包含 dashboard”。

## 7. 测试与验收

### 7.1 后端/Extension 合同测试

仓库中的主要自动化测试位于 `tests/**/*.test.mjs`。完整执行：

```bash
find tests -name '*.test.mjs' -print0 | xargs -0 node --test
```

如果改动范围明确，应先执行相关测试，再执行完整测试。例如任务编排、抖音
详情身份校验、评论巡查、负面巡查和通知都有独立合同测试。

测试失败时：

- 不通过删除断言来“修复”；
- 先判断是行为回归、测试环境缺失，还是合同已被明确修改；
- 记录失败用例、错误信息和是否影响生产路径；
- 不把“其余测试没跑”写成“测试通过”。

### 7.2 前端检查

```bash
cd web/admin
npm run lint
npm run build

cd ../dashboard
npm run lint
npm run build
```

构建成功只证明编译和打包通过。还要人工检查：

- 登录和租户切换；
- 调度中心列表、详情和状态；
- 内容分诊的转单、工单进展、结案归档和巡查页面；
- AI、通知、报告相关配置；
- 桌面尺寸和关键窄屏尺寸；
- 页面刷新与深链路。

### 7.3 Extension 浏览器快照测试

先生成与目标环境一致的快照，再运行浏览器验证：

```bash
scripts/sync-extension-build.zsh local
node tests/capture/extension-snapshot.browser.mjs
```

如果本机浏览器运行依赖缺失，应记录为环境阻塞，不能用静态测试结果替代真实
浏览器冒烟。

### 7.4 发布前最小业务冒烟

每次生产发布至少验证：

1. 管理员登录；
2. 正确租户可见；
3. Agent 在线状态符合两分钟心跳口径；
4. 创建一个少量数据的一次性任务；
5. Agent 领取命令并显示暗色任务状态页；
6. 任务进度、检查点和完成状态回传；
7. 数据入库并可在管理端打开；
8. 若涉及评论，评论数量和实际采样数量分开显示；
9. 若涉及 AI/OCR/ASR/邮件，执行受控样例；
10. 任务结束后浏览器不会遗留自动播放或错误页面。

## 8. 数据库变更开发流程

### 8.1 新迁移

1. 在 `server/db/migrations/` 新增未使用的递增编号；
2. SQL 尽量可重复验证、向前兼容；
3. 明确锁表、耗时、默认值和回填影响；
4. 在独立测试库执行；
5. 再次执行迁移，验证幂等跳过；
6. 检查 `schema_migrations`；
7. 为读写路径补合同测试；
8. 生产发布前生成可恢复备份。

### 8.2 禁止行为

- 不修改已在生产执行过的迁移来“覆盖历史”；
- 不在没有备份时启用 reset 迁移；
- 不把 Git 回滚当成数据库回滚；
- 不在应用仍持续写入时直接覆盖生产租户数据；
- 不把租户复制当作普通 SQL 复制；Agent、命令、Token 和运行中状态需要隔离。

## 9. 生产发布前置检查

### 9.1 确认发布范围

```bash
git status --short
git branch --show-current
git rev-parse HEAD
git log -1 --oneline
```

确认：

- 发布提交已经评审；
- 没有混入其他人的未提交改动；
- 没有 `.env`、客户导出、截图中的密钥或 ZIP/CRX 二进制；
- 数据库迁移已经单独审查；
- 是否需要 Extension 新包已经明确；
- 是否包含 dashboard 修改已经明确。

### 9.2 构建和测试

至少完成：

```bash
cd web/admin && npm ci && npm run lint && npm run build
cd ../../web/dashboard && npm ci && npm run lint && npm run build
cd ../..
find tests -name '*.test.mjs' -print0 | xargs -0 node --test
```

### 9.3 依赖安全检查

```bash
cd server
npm ci
npm audit --omit=dev
```

依赖扫描是需要解释和排期的风险清单，不是自动变更授权。禁止在临近生产发布
时直接执行：

```text
npm audit fix --force
```

强制升级可能跨主版本改变邮件、定时任务、Excel 导出或其他运行路径。应先定位
直接/传递依赖、确认实际暴露路径、在独立分支升级并做兼容性验证。

### 9.4 环境文件

生产权威模板：

```text
deploy/onstarvoice.env.production.example
```

复制为：

```text
server/.env.production
```

至少确认：

- `NODE_ENV=production`；
- `PORT=3002`；
- 独立生产 `DATABASE_URL`，新环境使用 `onstarvoice` 登录角色和同名数据库；
- 正确生产域名；
- 生产媒体目录；
- 当前有效的 AI/OCR/ASR 配置；
- SMTP 配置；
- `ALLOW_RESET_MIGRATIONS=0`；
- 已有管理员的数据库让三项 `BOOTSTRAP_ADMIN_*` 保持为空；
- 只有全新数据库首次创建平台管理员时才临时填写 `BOOTSTRAP_ADMIN_*`，创建
  成功后立即清空并重新发布；
- 本机 `server/.env.production` 只允许当前操作者读取，远端
  `/opt/onstarvoice/server/.env` 必须是 `root:root`、权限 `600`。

已有生产环境不得为了匹配模板而重置数据库密码、角色或所有者。先用受控环境
文件和只读查询确认当前 `DATABASE_URL`、数据库名及所有者；若历史环境采用其他
独立角色，备份、恢复和验证命令中的 `onstarvoice` 必须整体替换为该角色。

### 9.5 备份

发布脚本不做备份。运行迁移前必须人工备份：

```bash
ssh root@47.103.125.200 '
  set -e
  mkdir -p /opt/backups/onstarvoice
  backup=/opt/backups/onstarvoice/onstarvoice-$(date +%Y%m%d-%H%M%S).dump
  sudo -u postgres pg_dump --format=custom --no-owner --no-acl \
    onstarvoice > "$backup"
  test -s "$backup"
  chmod 600 "$backup"
  pg_restore --list "$backup" >/dev/null
  printf "%s\n" "$backup"
'
```

还要记录：

- 备份文件名；
- 文件大小；
- 备份完成时间；
- 当前 Git 提交；
- 当前远端管理端产物；
- 如涉及媒体结构，媒体目录备份位置。

只有“命令执行结束”不等于备份可恢复。重要迁移应在非生产数据库做恢复演练。

## 10. 执行生产发布

从仓库根目录：

```bash
node --version
bash deploy/deploy.sh 47.103.125.200
```

当前脚本会：

1. 尝试选用本机常见路径中的 Node 24/20；找不到时沿用当前 `PATH`；
2. 构建管理端；
3. 检查 `server/.env.production`；
4. 同步后端、管理端产物和 `images/`；
5. 上传生产环境文件，强制设置 `root:root`、权限 `600` 并校验；
6. 在远端安装生产依赖；
7. 执行迁移；
8. 删除旧 PM2 进程；
9. 启动新 PM2 进程；
10. 保存 PM2 状态。

风险边界：

- `rsync --delete` 会清理目标代码目录中仓库已删除的文件；
- `pm2 delete` 到 `pm2 start` 之间存在服务中断；
- 迁移和代码发布不是一个数据库事务；
- 迁移成功、应用失败时，数据库不会自动降级；
- 当前脚本只发布管理端，不发布数据看板；
- 当前脚本不做发布后 HTTP 健康门禁。

### 10.1 Dashboard 独立发布

主部署脚本不发布 `web/dashboard/dist/`。数据看板必须按独立静态产物发布，
并在覆盖前保存可识别的远端备份目录。

本地构建：


## 12. 回滚

### 12.1 为什么当前回滚不是原子的

当前发布顺序包含：

```text
文件同步 → 依赖安装 → 数据库迁移 → 删除旧进程 → 启动新进程
```

这些步骤不在同一个事务内。任何中间失败都可能产生：

- 新代码已同步但进程未启动；
- 数据库已迁移但旧代码无法兼容；
- 管理端产物已更新但后端仍不可用；
- PM2 短暂停止；
- 发布后的新业务写入已经进入数据库。

因此不能把“重新部署旧提交”描述为完整原子回滚。

### 12.2 仅应用回退

只在迁移向后兼容时：

1. 记录故障时间和当前状态；
2. 切回已验证 Git 提交；
3. 重新构建；
4. 重新运行部署；
5. 验证健康接口；
6. 验证关键业务；
7. 检查迁移后的数据库仍与旧代码兼容。

### 12.3 数据库降级

数据库结构或数据需要降级时，必须走发布前备份恢复。Git 回退不会撤销迁移。

#### A. 冻结并保留证据

1. 通知业务负责人进入事故恢复窗口；
2. 停止会产生新写入的入口，必要时停止 PM2 应用：

   ```bash
   ssh root@47.103.125.200 'pm2 stop onstarvoice'
   ```

3. 保存故障时间、当前提交、PM2 日志、当前数据库完整备份和当前
   `server/.env` 的受控副本；
4. 不删除原数据库，也不要直接在唯一生产库上运行 `pg_restore --clean`；
5. 明确恢复点之后可能已经产生的任务、工单、评论、快照等新写入。它们不会
   自动合并到旧备份，后续必须单独重放或人工对账。

#### B. 恢复到独立验证库

下例仅恢复到新库，不覆盖生产库：

```bash
ssh root@47.103.125.200 '
  set -e
  sudo -u postgres dropdb --if-exists onstarvoice_restore_check
  sudo -u postgres createdb --owner=onstarvoice onstarvoice_restore_check
  sudo -u postgres pg_restore --exit-on-error --clean --if-exists \
    --no-owner --no-acl --role=onstarvoice \
    --dbname=onstarvoice_restore_check \
    /opt/backups/onstarvoice/BACKUP.dump
'
```

用目标旧版本和独立环境文件连接 `onstarvoice_restore_check`，至少验证：

- 平台管理员登录和租户切换；
- 目标租户、Agent、任务和内容数量；
- 调度、工单、评论和快照的关键关联；
- 目标旧版本能读取该结构且不会再次执行不兼容迁移；
- 恢复点时间和业务可接受的数据损失范围。

#### C. 经批准后受控切换

1. 取得业务负责人对恢复点、新写入损失范围和维护窗口的明确确认；
2. 复制当前远端环境文件为带时间戳的只读备份；
3. 准备新的环境文件，只修改 `DATABASE_URL` 指向已验证恢复库；
4. 将新环境文件设置为 `root:root`、权限 `600`；
5. 切换到已验证旧版本代码并启动 PM2；
6. 不删除原生产数据库，保留为反向切换点。

环境文件切换示意：

```bash
ssh root@47.103.125.200 '
  set -e
  cd /opt/onstarvoice/server
  cp -a .env /opt/backups/onstarvoice/server.env-before-db-switch-$(date +%Y%m%d-%H%M%S)
  install -o root -g root -m 600 /root/onstarvoice.restore.env .env
  pm2 delete onstarvoice 2>/dev/null || true
  pm2 start index.js --name onstarvoice --max-memory-restart 400M
  pm2 save
'
```

`/root/onstarvoice.restore.env` 必须提前人工审查，除 `DATABASE_URL` 外不得意外
改变域名、租户、媒体目录、AI、SMTP 或初始化管理员配置。

#### D. 切换后验证

依次执行：

1. `/api/health`；
2. 管理端登录与租户切换；
3. 数据量和恢复点核对；
4. 一个低风险、少量数据的完整业务闭环；
5. PM2 日志和数据库错误检查；
6. 对恢复点之后的新写入建立重放或人工对账清单。

#### E. 验证失败时反向切换

立即停止恢复库上的新写入，恢复切换前保存的环境文件，重新启动原版本并验证。
任何在恢复库上产生的新写入都要单独记录，不能假设两边数据库会自动合并。

## 13. 常见故障定位

### 13.1 管理端打开但 API 失败

检查：

1. 本地后端是否在 `3001`；
2. `/api/health` 是否返回；
3. Vite 代理是否仍指向 `3001`；
4. CORS 是否允许当前源；
5. 登录 Cookie、租户和 Token 是否属于当前环境。

### 13.2 Agent 显示在线但不执行

检查：

1. Extension 是否真的打开并持续心跳；
2. Agent 是否属于当前租户；
3. 平台能力是否匹配；
4. 是否已有占用槽位；
5. 云端命令是否仍在有效期；
6. 本地任务锁是否遗留；
7. 浏览器配置文件是否与后台显示节点一致。

### 13.3 数据库迁移失败

检查：

1. `DATABASE_URL`；
2. PostgreSQL 权限；
3. `schema_migrations` 当前版本；
4. SQL 是否在事务中失败；
5. 是否误把 reset 迁移放入普通发布；
6. 备份是否可恢复。

不要在生产库手工标记迁移“已执行”来绕过错误。

### 13.4 AI 没有介入

检查：

1. 租户级 AI 配置；
2. 进程级默认 LLM 配置；
3. API Key 和模型名；
4. 预筛选模式、每日限额和租户并发；
5. 超时与服务商返回；
6. 是同步预筛选、异步评论分析还是异步舆情剖析；
7. 页面展示的是最新任务还是旧快照。

具体降级口径见 [AI 与通知机制](./AI与通知机制.md)。

### 13.5 邮件没有发送

检查：

1. SMTP 主机、端口和 `SMTP_SECURE`；
2. 用户名、密码、发件人和收件人；
3. 通知队列状态；
4. 重试次数和最后错误；
5. 是否只配置了未被代码消费的渠道。

当前实现的安全事件通知通道是 SMTP 邮件；飞书、企业微信、短信和电话不能
仅靠环境变量启用。

### 13.6 Dashboard 是旧版本

这是当前发布脚本的已知边界。确认是否单独构建并同步了
`web/dashboard/dist/`。不要通过反复重启后端期待 dashboard 自动更新。发布和
回退命令见 [10.1 Dashboard 独立发布](#101-dashboard-独立发布)。

## 15. 发布纪律

- 不在客户正在高强度使用时做未经演练的迁移；
- 不把“PM2 online”当成发布成功；
- 不在没有备份时执行 reset、覆盖租户或批量清理；
- 不在生产发布前强制升级全部依赖；
- 不把本地 Extension 包发给客户；
- 不把旧版 Extension 与新版服务端的偶然兼容当作长期合同；
- 不把静态构建通过当作真实浏览器流程通过；
- 不隐藏未运行、失败或被跳过的检查项；
- 不为追求“部署完成”而跳过租户隔离和数据归属验证。
